Part A: from diagram to tables

Start from your milestone 1 diagram, with the feedback on it applied. If you changed the diagram, include the new version and say in a sentence or two what changed and why.

Then list every table as a relation schema, with its primary key underlined and its foreign keys named, like appointment(appt_id, patient_id → patient, doctor_id → doctor, date_time, reason). Use the week 6 mapping rules (slides 21 to 24): one table per strong entity set, the owner's key plus the discriminator for a weak one, a column for a many-to-one relationship, a table for a many-to-many, and a table for each multivalued attribute.

Part B: dependencies and normal forms

For each table, write its non-trivial functional dependencies, as business rules you would defend to a user. Then say whether the table is in BCNF, using closures where it is not obvious (week 7, slides 12 to 17).

  • If a table is not in BCNF, decompose it and show the steps, or keep it in 3NF and explain which rule a BCNF split would lose (slides 20 to 23).
  • At least one table must have a dependency worth discussing: a second candidate key, a composite key, or a rule you chose not to enforce. If your design has none, say which table came closest and why.
  • Data can only disprove a dependency. For one table, write the GROUP BY query that would find rows breaking one of its rules, and run it on your sample data in Part D.

Part C: the CREATE TABLE statements

Write m2_schema.sql: one CREATE TABLE per table, in an order in which every foreign key refers to a table that already exists. It must start by dropping every table it creates, so it can run again (as tutoring.sql in Lab 5 does), and it must run with no errors on PostgreSQL. Include:

  • A primary key on every table, and a foreign key for every reference.
  • A deliberate ON DELETE action on every foreign key: say in a comment why it is NO ACTION, CASCADE or SET NULL (week 5, slide 8).
  • NOT NULL wherever a rule says a value must exist, including total participation.
  • At least one UNIQUE that is not the primary key, and at least three CHECK constraints from your business rules.

Part D: sample data and five queries

Write m2_data.sql with INSERT statements: at least 5 rows in every table and at least 15 in the two or three busiest, enough that each query below returns something interesting. Invent the data; never use real people's personal details.

Then write m2_queries.sql, which loads the other two files and answers five of your milestone 1 questions, each under a comment that quotes the question. Use at least one outer join, one GROUP BY with HAVING, one subquery or CTE, and one window function among the five. Also add the dependency check from Part B, and one INSERT that a constraint should refuse, so the output shows it being refused.

-- m2_queries.sql starts with these lines, then your queries
\ir m2_schema.sql
\ir m2_data.sql

Run it the same way as a lab, and keep the output:

psql -d project -e -f m2_queries.sql > m2_output.txt 2>&1

Create the project database once with createdb project (on Windows, createdb -U postgres project). The week 8 review playground's scratch pad also runs your CREATE TABLE statements, if you want to try them in a browser first.

Part E: CS 5200 only

Turn the NoSQL paragraph from milestone 1 into a first version: add a jsonb column to the table that holds the data whose shape varies, insert at least five rows with documents of at least two different shapes, and add one query that reads a field inside the documents (->> or @>). In the design notes, say which rules the database can no longer check for that data, and how you will handle that by milestone 4. These count toward the DDL and query points; week 15 covers document stores in depth.

Questions people usually ask

  • My milestone 1 feedback says the diagram needs changes. Make them here; that is what this milestone is for. Say what changed in the notes.
  • Do I need surrogate keys like appt_id? Use one when the natural key is long, can change, or is several columns that other tables would have to copy. Say which you chose and why; both are defensible.
  • "relation … does not exist" when creating a table: a foreign key refers to a table created later in the file. Reorder the CREATE TABLE statements.
  • "cannot drop table … because other objects depend on it": drop with DROP TABLE IF EXISTS a, b, c CASCADE; at the top of the schema file.
  • Can I use a different database system? No: milestones 3 and 4 run on PostgreSQL, and the grader runs your files there.
