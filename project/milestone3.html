Part A: the program

Write a Python program that uses psycopg 3, as in Lab 6, and gives one kind of user in your domain a menu of things to do. A command-line menu is enough; a small web page is fine too, but earns nothing extra. Start from your milestone 2 schema, with the feedback applied.

The program offers at least seven features:

  • Four that read, each answering one of your milestone 1 questions. Among them: one that searches by a value the user types, one that lists many rows a page at a time with keyset pagination (week 9), and one report that uses GROUP BY.
  • Three that change data: one INSERT, one UPDATE and one DELETE, each of something a real user would do, like recording a visit or cancelling a booking.

Whatever the program does, three rules hold everywhere:

  • Every value the user types reaches PostgreSQL as a parameter (%s with a tuple of values). No SQL is built with f-strings, + or .format(). The grader searches for them.
  • When PostgreSQL refuses a change, because of a key, a foreign key or a CHECK, the program says so in words the user understands, and carries on. Catch the specific error (for example psycopg.errors.UniqueViolation), not every exception.
  • No password is written in the code. Read the connection settings from environment variables, as Lab 6 did, or let ~/.pgpass supply the password.

Part B: one transaction that keeps a rule

One of the features that change data must make two or more changes that only make sense together, inside one transaction (with conn.transaction():), and check a business rule before it commits. If the rule fails, the whole transaction rolls back and the user is told why. Lab 6's enrollment, which checked prerequisites and logged every request, is the model.

Examples: a pantry visit that records the visit and lowers the stock of each item, refused if any item would go below zero; a booking that inserts the booking and marks the room busy, refused if the times overlap. In the notes, say which rule it keeps and what would go wrong without the transaction.

Part C: loading data from CSV

Milestone 2's hand-written INSERTs are too few for week 12's query plans. Grow your two or three busiest tables to at least 1,000 rows in the busiest and 200 in the others, with invented data, and load them from CSV files with a Python script, m3_load.py:

  • Read each file with Python's csv module and insert the rows with cursor.executemany(…), or stream them with cursor.copy("COPY … FROM STDIN"). Both send the values as data, never as SQL.
  • Load the tables in foreign key order, all in one transaction, so a bad row leaves nothing half loaded.
  • You may write the CSV files by hand, with a spreadsheet, or with a short script of your own. Never use real people's personal details.

The script must run twice in a row and leave the same data: start by emptying the tables it fills, or reload m3_schema.sql first.

Part D: a role with only what it needs

Create a login role for the program, as Lab 6 created registrar_app, and GRANT it only the privileges its features use: SELECT on what it reads, and INSERT, UPDATE or DELETE only on the tables it changes. Put the CREATE ROLE and GRANT statements at the end of m3_schema.sql, and run the program as that role. The loader may run as you.

Part E: CS 5200 only

  • Your milestone 2 jsonb column gets two features of its own in the program: one that stores a new document from what the user types (build it with Python's json module, pass it as a parameter, and use psycopg.types.json.Jsonb), and one that finds rows by a field inside the documents. These count among the seven features.
  • In the notes, name your critique paper: its number and title from the list, in one line.

What to submit and how it is graded

Upload one zip file to the Milestone 3 assignment in Brightspace. Name it m3_lastname_firstname.zip; a team uses both last names, like m3_rivera_nguyen.zip, and only one partner uploads it. Put these files in it:

  • The program: m3_app.py, and any other .py files it imports.
  • m3_load.py and its CSV files, in a folder named data.
  • m3_schema.sql: milestone 2's schema with any changes, and the role at the end.
  • m3_run.txt: a copy of one session at the terminal in which you use all seven features (nine for CS 5200), including one change your rules refuse and one search for ' OR 1=1 -- that finds nothing.
  • m3_notes.pdf: your names; how to run the program, in three or four commands; each feature with the milestone 1 question it answers; the rule Part B keeps; what changed since milestone 2; for CS 5200, your paper; and one line on how you used AI tools, if at all.

Leave out passwords, virtual environment folders and __pycache__.

Questions people usually ask

  • Can I use an ORM, like SQLAlchemy's or Django's? No. The course grades your SQL, so it has to be in your code, sent with psycopg.
  • Can my program be a web app? Yes, with Flask or similar, if you already know how. It earns nothing extra, and the same rules apply: parameters only, and no password in the code.
  • How do I copy a terminal session into m3_run.txt? Select the text in the terminal window and paste it into a plain text file. On macOS and Linux, script m3_run.txt records everything until you type exit.
  • My data generator makes the same rows every time. Is that a problem? No; that is what makes the load rerunnable. Make sure the values vary enough for your report to say something.
  • "permission denied for table …" when the program runs: the role is missing a GRANT for that table. Add only the privilege that feature needs.
