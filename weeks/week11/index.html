  • A plan is a tree of operations, each with a chosen algorithm: not just "join", but "hash join, building on big_student".
  • This week: the algorithms. Next week: the optimizer.

Measuring cost: pages, again

  • The textbook counts block transfers (b) and seeks (S): cost = b × tT + S × tS.
  • On an SSD seeks are cheap, so today we count pages read and written, as EXPLAIN's BUFFERS does.
  • CPU work matters too, but reading pages usually dominates.
  • Worst case, memory holds only a few pages; best case, everything is already in the buffer pool.

Playground example 1.1

Two conditions, two indexes

-- with an index on course_id
-- and another on year
SELECT * FROM big_takes
WHERE course_id = 'MU-199'
  AND year = 2015;

Bitmap Heap Scan on big_takes
    264 rows, 264 pages
  BitmapAnd
    Bitmap Index Scan on year_idx
        3,704 matches, 5 pages
    Bitmap Index Scan on course_idx
        7,143 matches, 8 pages
  • Each index gives the addresses of its matches as a bitmap, one bit per row.
  • AND the bitmaps, then visit only the pages of rows in both: 13 index pages, then 264 table pages, instead of all 736.
  • For OR, the same with a BitmapOr.
  • The textbook calls this intersection of identifiers (A9); one composite index on both columns would do it in one.

Sorting more than fits in memory

Sorting in PostgreSQL

-- big_student by name: 76 pages
Sort Method: quicksort  Memory: 736kB

-- the same, with work_mem = '64kB'
Sort Method: external merge  Disk: 448kB
Buffers: shared hit=76,
         temp read=108 written=117

-- big_takes by grade, year, LIMIT 5
Sort Method: top-N heapsort
  • Fits in work_mem (4 MB by default): quicksort in memory.
  • Doesn't fit: external merge, runs in temporary files. temp read and written count their pages.
  • With a LIMIT: top-N heapsort keeps only the best N rows as it reads.
  • An index in the right order: no sort at all (week 10).

Playground examples 2.1 and 2.2

Joins

The same result, three very different amounts of work.

Nested loop and block nested loop

for each row r in big_student:
    for each row s in big_takes:
        if r.student_no = s.student_no:
            output (r, s)
  • Works for any join condition, even < or LIKE.
  • Row at a time: big_takes is read once per student. nr × bs + br = 10,000 × 736 + 76 = 7,360,076 pages.
  • Block nested loop: read big_takes once per page of students instead. br × bs + br = 56,012 pages.
  • With M pages of memory, hold M − 2 student pages at a time: ⌈br / (M − 2)⌉ × bs + br. If all of big_student fits: 812.

Indexed nested loop: great for a few rows, terrible for many

For each outer row, look up its matches through an index on the inner table. Cost: br + nr × c, where c is one lookup.

Indexed nested loop, measured
Outer rowsLookupsPages
one student, 4321115
20 students named Sage Chen20316
all of big_takes, Music students inside100,000300,736
  • One student: 3 pages for the student, 12 for their enrollments. Nothing else is close.
  • 100,000 lookups of 3 pages each: nr × c grows with every outer row.
  • So "is there an index?" is the wrong question. "How many outer rows?" is the right one.

Merge join: sort both, then zip them together

Merge Join            10,000 rows
  Sort                 1,000 rows
    Seq Scan on big_student
  Sort                99,971 rows
    Seq Scan on big_takes
  • With both inputs sorted on the join key, one pass down each finds every match: br + bs = 812 pages.
  • Plus the sorts, unless an index or an earlier step already gives the order.
  • Only for equality joins (and a few range conditions).
  • It stops when either side runs out: here it never asked for the last 29 enrollments.

Playground examples 4.1 and 4.2

Materialize, or pipeline?

Materialization

  • Run each step to the end and write its whole result to a temporary table; the next step reads that.
  • Simple, but every intermediate result is written and read again.

Pipelining

  • Each step hands its rows straight to the next, as they are produced.
  • No temporary tables, and the first rows come out early.
  • PostgreSQL pipelines wherever it can. A Materialize node in a plan marks the exceptions.
→

Each plan node is an iterator with three operations: open(), next(), which returns one row, and close(). The top node calls next() on its children, and so on down.

Rows on demand, and the steps that block

Playground examples 5.1 and 5.2

Reading a plan: from the inside out

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT s.name, t.course_id
FROM big_student s
JOIN big_takes t ON t.student_no = s.student_no
WHERE s.dept_name = 'Music';

Hash Join (actual rows=10000 loops=1)
  Hash Cond: (t.student_no = s.student_no)
  Buffers: shared hit=812
  -> Seq Scan on big_takes t (rows=100000)
       Buffers: shared hit=736
  -> Hash (rows=1000)
       Buckets: 1024  Batches: 1  Memory Usage: 46kB
       -> Seq Scan on big_student s (rows=1000)
            Filter: (dept_name = 'Music')
            Rows Removed by Filter: 9000
            Buffers: shared hit=76
  1. Start at the deepest line: scan big_student, keep 1,000 Music students of 10,000 (76 pages).
  2. Build a hash table of them: one batch, 46 kB, fits in memory.
  3. Scan all of big_takes, probing with each row (736 pages).
  4. 10,000 matches come out of the top. Buffers at each line include the lines below it: 76 + 736 = 812.

Playground example 3.1

Worked example: one query, two plans

All Music students' enrollments

  • 1,000 outer rows: an index lookup for each would cost about 1,000 × 12 pages.
  • Hash join, 812 pages, with or without an index on big_takes (student_no).

Student 4321's enrollments

  • One outer row. Without an index on big_takes (student_no): nested loop, 739 pages (3 + 736).
  • With the index: nested loop, 15 pages (3 + 12).
→

The index on big_takes (student_no) helps the second query fifty times over and the first not at all. Whether an index pays depends on the queries your application runs.

Takeaways

  1. 1
    A plan is a tree of algorithms.

    Each node is one, with a cost in pages you can estimate.

  2. 2
    Memory decides how to sort.

    In memory, a quicksort; beyond it, runs on disk and merge passes.

  3. 3
    Three join families.

    Nested loop for few outer rows, hash for many, merge when sorted.

  4. 4
    Hashing and sorting do the rest.

    GROUP BY, DISTINCT and NOT EXISTS reuse the same two ideas.

  5. 5
    Rows flow up on demand.

    A LIMIT can stop a scan early; a sort or a hash build blocks it.
