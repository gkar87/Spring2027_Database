Reading a plan's page counts

Every EXPLAIN in this lab uses the same options, so your output and the grader's can be compared line by line:

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT …;
  • ANALYZE runs the query. BUFFERS adds a Buffers: line under each step.
  • A step's pages are its shared hit plus its read, if any. They include the pages of the steps indented under it, so the top step's count is the whole query's.
  • temp read and temp written count pages of temporary files, used when a sort or a hash does not fit in memory.
  • A line Buffers: under Planning: is the planner reading the catalog. Leave it out.

Questions that change a setting with SET end with RESET ALL;, so the next question starts from the defaults. Your PostgreSQL version may pick a slightly different inner step than the slides show; write down what your output says, and the written answers explain it.

Part B: predict, then measure

Predict first. Before you run anything, fill in P1 to P4 in the answers file with the formulas from slides 11 to 14, using br = 76, nr = 10,000 for big_student, bs = 736, ns = 100,000 for big_takes, and c = 3 pages for one primary key lookup. A wrong prediction loses nothing, as long as W1 explains it.

Then write each statement in lab7.sql under its comment, run the whole file, and copy the numbers into the answers file.

  1. Q1. One query on pg_class: relname, pages (pg_relation_size(oid) / 8192) and rows (reltuples) for big_student, big_takes, big_student_pkey and big_takes_pkey.

  2. Q2. EXPLAIN the join of every student with every enrollment, settings as they are: SELECT count(*) FROM big_student s JOIN big_takes t ON t.student_no = s.student_no. Record the join method and the pages at the top step.

  3. Q3. The same join as a merge join: SET enable_hashjoin = off; and SET enable_nestloop = off;, the EXPLAIN, then RESET ALL;. How did big_student arrive in student_no order: a Sort, or an index scan?

  4. Q4. The same join as an indexed nested loop: turn off enable_hashjoin, enable_mergejoin and enable_memoize, EXPLAIN, then RESET ALL;. Record how many times the inner step ran (loops).

  5. Q5. SET work_mem = '64kB';, then EXPLAIN SELECT * FROM big_takes ORDER BY course_id, year, then RESET ALL;. Record the sort method and the temp pages read and written.

  6. Q6. The same sort with the default work_mem, then the same with LIMIT 10. Two EXPLAINs.

  7. Q7. Three EXPLAINs of the enrollments with grade 'F', each with LIMIT 5: (a) in no order, (b) ORDER BY year, (c) ORDER BY reg_id.

  8. Q8. For each department, the number of F grades its students received: dept_name, f_grades, most first, then by dept_name. Run the query, then EXPLAIN it, and name the step that does the grouping.

  9. Q9. Student 4321's name with each course_id and year they took, as a join of the two big tables. EXPLAIN it; then CREATE INDEX big_takes_student_idx ON big_takes (student_no);; then EXPLAIN it again.

  10. Q10. How many Music students took no course in 2027? Use NOT EXISTS. Run it, then show its plan with EXPLAIN (COSTS OFF), and name the join step.

Part C: three short answers

In lab7_answers.txt, in your own words, a short paragraph each:

  1. W1. Compare P1 to P4 with what Q2 to Q4 measured. Which matched, which did not, and why? Then explain why PostgreSQL chose its plan for Q2 but a nested loop for Q9, in terms of the number of outer rows.

  2. W2. Compute the textbook's cost for Q5's sort, b × (2⌈logM−1(b / M)⌉ + 1), with b = 736 and M = 8 pages (64 kB). Compare it with Q5's temp read plus temp written, and give one reason they differ.

  3. W3. In Q7, which query read the most pages, though all three return five rows? Which step blocks the pipeline there, and what index would let it stop early?

Part D: CS 5200 only

  1. D1. A block nested loop with M pages of memory costs ⌈br / (M − 2)⌉ × bs + br. Compute it for M = 3, 10 and 78, with br = 76 and bs = 736, and show the arithmetic.

  2. D2. In lab7.sql: turn off enable_hashjoin, enable_mergejoin, enable_indexscan, enable_bitmapscan and enable_memoize, then EXPLAIN the join of the Music students with their enrollments (WHERE s.dept_name = 'Music'), then RESET ALL;. Record the join method, the pages and the execution time. The pages match a hash join's; the time does not. Explain why, using the line Rows Removed by Join Filter. If something goes wrong

  • "big_tables.sql: No such file or directory": the four files are not in the same folder. Move them together and run again.
  • "relation "department" does not exist" while loading: big_tables.sql ran before university.sql. Leave the first lines of lab7.sql as they were given.
  • "relation "big_takes_student_idx" already exists": you ran Q9 on its own, after a full run. Run the whole file; the reload removes the index.
  • A later question shows a merge join or a nested loop you did not ask for: an earlier question is missing its RESET ALL;.
  • Your page counts differ from a classmate's by a few: different PostgreSQL versions read the catalog a little differently. Use your own numbers; the written answers explain them.
  • Anything else: copy the exact message and bring it to office hours, Tuesday and Wednesday 12:00–3:00 p.m., MIC room D159, or email it to me.
