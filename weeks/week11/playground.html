Week 11 playground: how a query runs

A plan is a tree of small programs, each pulling rows from the ones below it. Here you watch PostgreSQL pick out rows, sort them when memory runs short, join two tables three different ways, and stop early when a LIMIT is reached, counting the pages each step reads.

How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.
  • A box runs as one transaction. SET LOCAL changes a setting until the end of that transaction, so a setting changed in one box is back to normal in the next.
  • Examples that create an index start with BEGIN; and end with ROLLBACK;, so nothing is kept. Reset database, at the top, puts the starting data back, whatever you changed.
  • Exercises have a Check answer button. It runs your statements inside a transaction and rolls them back, so checking never changes the data. Your solved exercises are remembered in this browser only.
  • Timings are your browser's and change from run to run. Count rows and pages, not milliseconds.

The big tables, and two ways to read a plan

This week uses last week's generated tables: big_student (10,000 rows on 76 pages) and big_takes (100,000 rows on 736 pages), each with only its primary key indexed. Every student has exactly 10 enrollments, and each department has 1,000 students.

Two functions turn a plan into rows. plan_steps(query) shows the plan without running the query. plan_actual(query) runs it, like EXPLAIN ANALYZE, and adds, for each step, the rows it produced over all its runs, how many times it ran (loops), the pages it and the steps below it touched, and how it sorted. To try them at home in psql, run university.sql and then big_tables.sql.

1. Selection: finding the rows

Slides 6 and 7. With no index on the condition, the only way is a linear scan: read every page and test every row. With an index on it, a few pages lead straight to the rows.

For two conditions joined by AND, with an index on each, PostgreSQL can read both indexes, keep only the row addresses found in both (BitmapAnd), and only then visit the table.

2. Sorting, in memory and on disk

Slides 8 and 9. A sort may use up to work_mem of memory, 4 MB unless you change it. If the rows fit, PostgreSQL sorts them in memory (quicksort). If not, it sorts memory-sized runs, writes each to a temporary file, and merges the runs (external merge). temp read and written count those file pages.

Sorting all 100,000 enrollments does not fit in 4 MB either. With a LIMIT, though, PostgreSQL keeps only the best few rows as it reads (top-N heapsort), and with an index in the right order it does not sort at all.

3. Three ways to join

Slides 11 to 15. Start with eight rows, where you can follow every comparison, then let PostgreSQL do the same on 100,000.

All 1,000 Music students and their 10,000 enrollments. Left to itself, PostgreSQL builds a hash table on the smaller input, the students, and probes it once for each enrollment: 76 + 736 = 812 pages.

The settings enable_hashjoin, enable_mergejoin and enable_nestloop tell the planner to avoid one method. They exist for experiments like this one, not for applications. Turning off the hash join and the nested loop leaves a merge join: both inputs are sorted on student_no, then read once, side by side.

Look at the rows the sort of big_takes handed up: fewer than 100,000. The merge stops as soon as the students run out, without reading the end of the other input.

Turning off the other two leaves a nested loop. Each of the 100,000 enrollments looks up its student through big_student_pkey, three pages a time: an indexed nested loop. (enable_memoize is turned off too; otherwise PostgreSQL remembers each student it has already looked up.)

A nested loop is not always the slow choice. For one student, the outer side has one row, so the inner side is read once, and PostgreSQL picks a nested loop by itself.

A hash join needs its hash table to fit in work_mem. When it does not, both inputs are first split into partitions (PostgreSQL calls them batches) written to temporary files, and each pair of partitions is joined in turn.

4. Grouping, duplicates and NOT EXISTS

Slide 17. GROUP BY and DISTINCT both need equal values brought together, by hashing (HashAggregate) or by sorting (GroupAggregate on sorted input), the same two ideas as the joins.

NOT EXISTS is planned as an anti join: a join that keeps the rows with no match, each once. Here, the students who never took MU-199.

5. Pipelining: rows on demand

Slides 19 to 21. Each step hands rows to the one above it as they are asked for, one at a time. A LIMIT stops asking after five rows, so a scan beneath it reads only a page or two. A sort can't hand up its first row until it has seen every row, so it reads the whole table, LIMIT or not.

The planner knows about LIMIT, too. For only five rows of the Music join it gives up the hash join, which can't return a row before it has read every student, and picks a nested loop that can stop early: a few enrollment pages, and three pages to look up each student, instead of 812.

Exercises

Several exercises use this join, the Music students and their enrollments:

SELECT s.name, t.course_id
FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
WHERE s.dept_name = 'Music'

Inside the quotes of plan_steps or plan_actual, write each quote of the query twice: ''Music''. A SET LOCAL in your answer lasts until the check is over.

Show the plan_steps of the Music join, with every setting as it is.

Hint

SELECT * FROM plan_steps('…'); with the whole query inside the quotes.

Show a solution
SELECT * FROM plan_steps('SELECT s.name, t.course_id
  FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
  WHERE s.dept_name = ''Music''');

A hash join, with the hash table built on the 1,000 Music students. Steps 3 and 4 are the build side; step 2 is the probe side.

Using SET LOCAL, make PostgreSQL run the Music join as a merge join, then show its plan_steps.

Hint

Turn off the two other methods. Example 3.2 shows how.

Show a solution
SET LOCAL enable_hashjoin = off;
SET LOCAL enable_nestloop = off;
SELECT * FROM plan_steps('SELECT s.name, t.course_id
  FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
  WHERE s.dept_name = ''Music''');

Neither input is stored in student_no order, so both are sorted first.

Turn off the hash join, the merge join and memoize, and run the Music join with plan_actual. Return only the columns step, node and loops. How many times did the inner step run, and why that number?

Hint

Three SET LOCAL lines, then SELECT step, node, loops FROM plan_actual('…');

Show a solution
SET LOCAL enable_hashjoin = off;
SET LOCAL enable_mergejoin = off;
SET LOCAL enable_memoize = off;
SELECT step, node, loops FROM plan_actual('SELECT s.name, t.course_id
  FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
  WHERE s.dept_name = ''Music''');

100,000 times: once for every row of the outer input, all of big_takes. That is nr in the cost formula br + nr × c.

Left to itself, PostgreSQL groups SELECT course_id, count(*) FROM big_takes GROUP BY course_id by hashing (Example 4.1). Turn hashing off for grouping, then show that query's plan_steps.

Hint

The setting is enable_hashagg.

Show a solution
SET LOCAL enable_hashagg = off;
SELECT * FROM plan_steps(
  'SELECT course_id, count(*) FROM big_takes GROUP BY course_id');

Without hashing, PostgreSQL sorts the 100,000 rows by course_id first, then counts each run of equal values as it reads them. Ten groups fit easily in memory, which is why hashing wins when it is allowed.

Set work_mem to '64kB' and run SELECT * FROM big_student ORDER BY name with plan_actual. Return the node, actual_rows and sort_method of the sort step only.

Hint

The sort step is the one whose sort_method is not null, or step 1.

Show a solution
SET LOCAL work_mem = '64kB';
SELECT node, actual_rows, sort_method
FROM plan_actual('SELECT * FROM big_student ORDER BY name')
WHERE step = 1;

76 pages of students don't fit in 8 pages of memory, so the sort writes runs to disk and merges them.

How many students in big_student have never taken MU-199? Use NOT EXISTS and return one number.

Hint

Example 4.2 has the query inside plan_steps. Run it directly.

Show a solution
SELECT count(*)
FROM big_student s
WHERE NOT EXISTS (SELECT 1 FROM big_takes t
                  WHERE t.student_no = s.student_no
                    AND t.course_id = 'MU-199');

The plan is a Hash Right Anti Join: the hash table is built on the students, and each MU-199 enrollment found crosses its student off.

Return one row with two columns: the rows the sequential scan of big_takes produced for SELECT * FROM big_takes LIMIT 5, and for SELECT * FROM big_takes ORDER BY year LIMIT 5.

Hint

The scan's node is indented, so pick it with WHERE node LIKE '%Seq Scan', inside (SELECT actual_rows FROM plan_actual('…') WHERE …).

Show a solution
SELECT (SELECT actual_rows FROM plan_actual(
          'SELECT * FROM big_takes LIMIT 5') WHERE node LIKE '%Seq Scan') AS no_sort,
       (SELECT actual_rows FROM plan_actual(
          'SELECT * FROM big_takes ORDER BY year LIMIT 5') WHERE node LIKE '%Seq Scan') AS sorted;

The scan is the same program both times. Only what asks it for rows differs: a LIMIT stops after five, a sort keeps asking until the table is done.

There are 20 students named Sage Chen. Create an index named big_takes_student_idx on big_takes (student_no), then show the plan_steps of the join for those students: the Music join with s.name = 'Sage Chen' in place of the department.

Hint

CREATE INDEX big_takes_student_idx ON big_takes (student_no);, then plan_steps with WHERE s.name = ''Sage Chen''.

Show a solution
CREATE INDEX big_takes_student_idx ON big_takes (student_no);
SELECT * FROM plan_steps('SELECT s.name, t.course_id
  FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
  WHERE s.name = ''Sage Chen''');

Twenty outer rows, so an indexed nested loop: each Sage Chen's ten enrollments are found through the new index. Compare its 316 pages, in plan_actual, with the 812 of a hash join.
