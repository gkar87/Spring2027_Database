Week 14 playground: recovery and administration

A committed transaction must survive a crash, and an unfinished one must leave no trace. The log is how a database keeps both promises. Here you read a log, replay recovery after a crash you place yourself, measure PostgreSQL's own log, clean up after old row versions, and give a program only the privileges it needs.

1. A log you can query

Slides 9 to 13. This week's database has one more table, wal_log: a recovery log in the book's notation, with five transactions on four items, A to D. The system crashed right after record 18.

  • <T0 start>, <T0 commit>, <T0 abort>: a transaction begins, commits or finishes rolling back. Column kind says which.
  • <T0, A, 1000, 950>: T0 changed A from 1000 (old_val) to 950 (new_val). Kind update.
  • <T4, C, 600>: written while T4 was being rolled back, setting C back to 600. Kind redo-only: it is never undone.
  • <checkpoint {T1}>: everything before it is safely on disk, and T1 was still running. Column active holds that list.

Recovery's first question is where each transaction stood at the crash. One that committed must keep all its changes; one that has neither a commit nor an abort record must lose all of them.

T4 rolled back before the crash, so it is finished: its <T4 abort> record says the rollback is complete. Only T2 is unfinished.

Without a checkpoint, recovery would have to read the whole log from the beginning. The last checkpoint tells it where to start, and which transactions were running at that moment.

2. Crash, then recover

Slides 15 to 17. The book's recovery algorithm makes two passes over the log. The redo pass goes forward from the last checkpoint and repeats every change, of every transaction, even the ones that will be undone; along the way it works out the undo list, the transactions with no commit or abort. The undo pass then goes backward and rolls those back, the same way a rollback does while the system is running: it sets each item back to its old value, logs that as a redo-only record, and logs <T abort> when it reaches the transaction's start.

Move the crash earlier and step through again. A crash right after record 7 leaves T1 unfinished, so the undo pass has to go back past the checkpoint to reach T1's start.

The redo pass starts from what the checkpoint guaranteed was on disk. A query can work that out: the last value written to each item before record 7.

DISTINCT ON (item) keeps the first row for each item in the ORDER BY order, here the latest. D is missing because nobody had written it yet: it still holds its starting value, 500. A, B and C hold T0's and T1's values. T1 had not committed at the checkpoint, but its change to C was on disk anyway: a checkpoint writes every changed page, committed or not. That is why recovery needs an undo pass at all.

3. PostgreSQL's own log

Slide 21. PostgreSQL calls its log the write-ahead log, or WAL. Every change goes into it before the changed page may be written to the table's file, and a transaction has committed when its commit record is on disk. A position in the WAL is an LSN (log sequence number): a byte offset, shown as two hexadecimal numbers. The WAL is stored as files of 16 MB.

Subtract two positions and you get the bytes written in between. A temporary table holds the starting position; temporary tables are not logged, so it adds nothing itself.

One row costs under a hundred bytes of log. Changing every row of big_student writes more log than the table holds: each new row version goes into the log, and so does a copy of each page the first time it changes after a checkpoint. That copy is how PostgreSQL repairs a page that was only half written when the power went (full_page_writes). The table grew too: section 4 explains why.

A few settings decide how safe a commit is. Ask the server:

  • fsync makes PostgreSQL wait until the disk confirms each write. In this page it is off: your browser's database lives in memory and vanishes when you close the tab, so there is nothing to protect. On a real server, turning it off risks a corrupted database after a power cut.
  • synchronous_commit on means COMMIT returns only after the commit record is on disk. Turned off, a crash can lose the last fraction of a second of commits, but never leaves the data inconsistent.
  • checkpoint_timeout (in seconds) and max_wal_size (in MB) say how often PostgreSQL takes a checkpoint: every 5 minutes, or sooner if that much log has piled up.

You can also ask for a checkpoint now. Afterwards, redo_lsn is where recovery would start redoing if the server crashed at this moment.

PostgreSQL's recovery is redo only. It never needs an undo pass, because it never overwrites a row: an unfinished transaction's new versions sit beside the old ones, and since it is not marked committed, nobody ever sees them (week 13). On a real server, CHECKPOINT needs a superuser or the pg_checkpoint role.

4. Cleaning up old versions

Slide 23. Every UPDATE leaves the old version of the row behind, and so does every rolled-back change. Once no transaction can still see an old version, it is dead: it takes up space, and every sequential scan still reads it. VACUUM marks that space free for new rows. At least 10,000 dead versions, more if you ran Example 3.2, whose rolled-back versions are dead too. The table has grown from 608 kB. (pg_stat_force_next_flush() makes the statistics up to date at once; a server updates them every few seconds.) Now vacuum it, in a box of its own: VACUUM can't run inside a transaction.

Run Example 4.2 again. No dead versions are left, but the size has not changed: VACUUM frees the space inside the pages for later rows, and doesn't give it back. VACUUM FULL writes a new, compact copy of the table. It locks the table while it works, so on a busy server it is a last resort.

Run Example 4.2 once more: 608 kB again. On a server you rarely type VACUUM yourself. The autovacuum daemon vacuums, and runs ANALYZE (week 12) on, each table once enough of it has changed. Nothing runs in the background in your browser, so here it never comes.

5. Roles and privileges

Slide 24. A role is a user, or a group of users, or both. A new role can do nothing until it is granted privileges: SELECT, INSERT, UPDATE or DELETE on a table, or only on some of its columns. SET ROLE lets the owner act as another role, to test what it can do. Milestone 3's program runs as a role like this.

Granting to each person one by one doesn't scale. Grant to a group role instead, and make people members of it: CREATE ROLE dana LOGIN IN ROLE staff;. Dana then has whatever staff has. REVOKE takes a privilege back.

6. Backups, at home

Slide 22. The log protects you from a crash, not from a lost disk or a mistaken DROP TABLE. For those you need a copy kept somewhere else. These commands run in a terminal, not in this page; try them on the university database from Lab 0:

pg_dump -Fc -f university.dump university     # a logical backup, one file
createdb university_copy
pg_restore -d university_copy university.dump  # load it into a new database
psql -d university_copy -c "SELECT count(*) FROM takes"

A dump is a snapshot of one moment. To recover to any moment, a server keeps a base backup, a copy of its files, and archives every WAL file after it. Replaying the archived WAL on the base backup brings the database forward to just before the mistake: point-in-time recovery.

Exercises

Exercises 1 to 5 are about wal_log, with the crash right after record 18 unless the exercise says otherwise. Exercises 6 to 8 create roles; the checker rolls them back, so leave out BEGIN, COMMIT and ROLLBACK. The last statement's result is the one checked.

List the transactions on the undo list: those with a start record but no commit or abort record. One column, tx.

Hint

Group by tx, as Example 1.2 does, and keep a group with HAVING: bool_or(kind = 'start') and not bool_or(kind IN ('commit', 'abort')).

Show a solution
SELECT tx FROM wal_log
GROUP BY tx
HAVING bool_or(kind = 'start')
   AND NOT bool_or(kind IN ('commit', 'abort'));

Only T2. T4 rolled back, but its abort record says the rollback finished, so recovery leaves it alone. The bool_or(kind = 'start') test keeps out the checkpoint, whose tx is NULL.

Suppose the crash had come right after record 9, so records 10 to 18 were never written. Which transactions would be on the undo list? One column, tx.

Hint

Exercise 1's query, looking only at records with lsn <= 9.

Show a solution
SELECT tx FROM wal_log
WHERE lsn <= 9
GROUP BY tx
HAVING bool_or(kind = 'start')
   AND NOT bool_or(kind IN ('commit', 'abort'));

T1 and T2. T1's commit is record 10, which never made it. Recovery learns about T1 from the checkpoint's list, since T1 started before it; set the crash to record 9 in section 2 and watch the undo pass go back past the checkpoint.

The undo pass sets items back, newest change first. List what it does: two columns, the item and the value it sets it back to, in the order the undo pass does them.

Hint

The update records of the transactions from Exercise 1 (use it as a subquery), with their old_val, ordered by lsn descending.

Show a solution
SELECT item, old_val FROM wal_log
WHERE kind = 'update'
  AND tx IN (SELECT tx FROM wal_log
             GROUP BY tx
             HAVING bool_or(kind = 'start')
                AND NOT bool_or(kind IN ('commit', 'abort')))
ORDER BY lsn DESC;

D back to 500, then A back to 950. The undo pass logs each one as a redo-only record, <T2, D, 500> and <T2, A, 950>, and then <T2 abort>. Going backward matters when a transaction wrote the same item twice: the oldest value must be the one that stays.

List every record the redo pass redoes, in order: three columns, lsn, item and the value it writes. The redo pass starts after the last checkpoint and redoes both update and redo-only records, whoever wrote them.

Hint

Compare lsn with a subquery that finds the last checkpoint's lsn, as in Example 1.3. Keep the two kinds of record that change an item.

Show a solution
SELECT lsn, item, new_val FROM wal_log
WHERE kind IN ('update', 'redo-only')
  AND lsn > (SELECT max(lsn) FROM wal_log WHERE kind = 'checkpoint')
ORDER BY lsn;

Five records: 9, 12, 14, 15 and 18. The redo pass repeats history, including T2's changes, which the undo pass will take back, and T4's change and its rollback, which leave C at 600.

A challenge. Show each item's value once recovery has finished: two columns, item and its value, ordered by item. Every item has been written at least once. Check your answer against the end of section 2's replay.

Hint

An item ends with the value of the last change that survives. Changes by transactions not on the undo list survive, with their new_val. For a transaction on the undo list, only its first change to each item matters, and it leaves that change's old_val. Put both kinds of row in one CTE, with their lsn, and keep the latest row for each item with DISTINCT ON, as in Example 2.1.

Show a solution
WITH undo AS (
  SELECT tx FROM wal_log
  GROUP BY tx
  HAVING bool_or(kind = 'start') AND NOT bool_or(kind IN ('commit', 'abort'))
), w AS (
  SELECT item, lsn, new_val AS v FROM wal_log
  WHERE kind IN ('update', 'redo-only') AND tx NOT IN (SELECT tx FROM undo)
  UNION ALL
  (SELECT DISTINCT ON (tx, item) item, lsn, old_val FROM wal_log
   WHERE kind = 'update' AND tx IN (SELECT tx FROM undo)
   ORDER BY tx, item, lsn)
)
SELECT DISTINCT ON (item) item, v AS value
FROM w ORDER BY item, lsn DESC;

A 950, B 2000, C 600, D 500. This works because the log follows strict two-phase locking: once an unfinished transaction has written an item, nobody else writes it, so its first old value is the last committed one.

Create a role named clerk that can read department but change only its budget column. Then act as clerk: raise Music's budget by 1,000, and show Music's dept_name and budget.

Hint

Example 5.3's GRANT, then SET ROLE clerk;. Without SELECT, the UPDATE is refused: its WHERE clause reads dept_name, and budget + 1000 reads the budget.

Show a solution
CREATE ROLE clerk;
GRANT SELECT, UPDATE (budget) ON department TO clerk;
SET ROLE clerk;
UPDATE department SET budget = budget + 1000 WHERE dept_name = 'Music';
SELECT dept_name, budget FROM department WHERE dept_name = 'Music';

Music at 61,000. As clerk, UPDATE department SET building = … would be refused with "permission denied". The checker's rollback also undoes the SET ROLE.

Create a group role staff that can read department, and a role dana that can log in and is a member of staff, with no privileges granted to dana directly. Then act as dana and show current_user and the number of departments.

Hint

Grant to staff, not to dana. CREATE ROLE dana LOGIN IN ROLE staff; makes dana a member at creation; GRANT staff TO dana; does the same for an existing role.

Show a solution
CREATE ROLE staff;
GRANT SELECT ON department TO staff;
CREATE ROLE dana LOGIN IN ROLE staff;
SET ROLE dana;
SELECT current_user, count(*) FROM department;

dana and 7. When the next clerk joins, one GRANT staff TO … gives them everything staff can do, and one REVOKE takes it away when they leave.
