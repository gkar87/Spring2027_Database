Recovery and Administration

A database that loses a committed sale, or keeps half of a transfer, is worse than no database. Recovery is what lets you trust COMMIT.

What can fail

Three kinds of failure, and what each one destroys
FailureExamplesWhat is lostWho fixes it
Transaction failureA constraint is broken, a deadlock, ROLLBACKNothing but that transaction's workRollback, while running
System crashPower cut, operating system or server bugEverything in memory; the disk survivesRecovery at restart (today)
Disk failureA head crash, a dead SSD, a deleted directorySome or all of the diskBackups and replicas
  • We assume fail-stop: a crash stops the system, it doesn't scribble nonsense on the disk first. Checksums catch the rare exception.

Storage

What survives a crash, and how data gets there.

Three kinds of storage

  • Stable storage doesn't exist; it is approximated. Write each block to two disks, one after the other, and a crash can damage at most one copy.
  • Only the log needs stable storage, and the log is small.

Data moves in blocks

  • A write changes only the buffer. The block reaches the disk at some later output, chosen by the buffer manager (week 10), not by the transaction.

The problem: half a transfer on disk

T0 moves 50 from A to B:

read(A); A := A - 50; write(A)
read(B); B := B + 50; write(B)
commit

A was 1000 and B 2000. The system crashes after output(A) and before output(B).

  • On disk: A = 950, B = 2000. Fifty has vanished.
  • Rerun T0? Then A = 900: wrong. Leave it? Still wrong.
  • With only the data on disk, nobody can tell which writes happened, or whether T0 committed.
  • So, before changing anything on disk, write down what you are about to change, somewhere that survives: a log.

The log

A record of every change, written before the change.

Log records

<T0 start>
<T0, A, 1000, 950>
<T0, B, 2000, 2050>
<T0 commit>
<T1 start>
<T1, C, 700, 600>
  • <T start>: T has begun.
  • <T, X, old, new>: T wrote X, which held old and now holds new.
  • <T commit>: T has committed. <T abort>: T finished rolling back.
  • The log is only ever appended to, so writing it is fast: one stream, no seeking.

Playground examples 1.1 and 1.2

Write-ahead logging

  • The WAL rule: log first, data later. Then the log can always explain what the disk holds.
  • Commit costs one write of the log, not one write per changed block.

Redo and undo

redo(T)

  • Sets every item T wrote to its new value, going forward through the log.
  • For T with a <T commit> or <T abort> record.

undo(T)

  • Sets every item T wrote back to its old value, going backward.
  • For T with <T start> and neither of those.
  • Logs each step as a redo-only record <T, X, old>, then <T abort>.
  • Both are idempotent: doing one twice gives the same result as once. A crash during recovery is harmless; recovery just runs again.
  • The redo-only records make a rollback look like ordinary changes, so a rolled-back transaction ends with <T abort> and is simply redone.
  • Rolling back a transaction while the system runs uses the same undo.

One log, three crashes

Checkpoints

A checkpoint

  1. Writes every log record in memory to stable storage.
  2. Writes every changed block in the buffer to disk.
  3. Logs <checkpoint L>, where L lists the transactions running.
  • Everything before the checkpoint is on disk, so recovery redoes only what comes after it.
  • Transactions in L may have changes on both sides. Their undo can reach back before the checkpoint.
  • Without checkpoints, recovery reads the whole log, and the log grows forever.
  • Updates pause while the book's checkpoint runs; a fuzzy checkpoint lets them continue (19.5.4).

Playground example 1.3

The recovery algorithm

Repeat history, then roll back the unfinished.

Pass 1: redo, going forward

  1. 1
    Start at the last checkpoint.

    Set the undo list to its L.

  2. 2
    Redo every change, of every transaction.

    <T, X, old, new> and <T, X, V> both set X, even when T will be undone. This is called repeating history.

  3. 3
    Keep the undo list.

    Add T at <T start>; remove it at <T commit> or <T abort>.

At the end of the log, the database is exactly as it was at the crash, and the undo list holds the transactions that never finished.

Pass 2: undo, going backward

  1. 1
    Scan back from the end of the log.

    Look only at records of transactions on the undo list.

  2. 2
    Undo each change.

    For <T, X, old, new>, set X to old and log <T, X, old>.

  3. 3
    Finish each transaction.

    At <T start>, log <T abort> and take T off the list. Stop when the list is empty.

Then the database opens for new transactions.

When may a changed block go to disk?

Two choices for the buffer manager, and what each forces recovery to do

  • Real systems choose steal and no-force for speed, and pay for it with both redo and undo. The log makes that cheap.

ARIES, in one slide

What it adds

  • Every log record has a log sequence number (LSN); every page stores the LSN of its last change, the PageLSN.
  • Redo skips a record whose LSN is at most the page's PageLSN: that change is already there.
  • Undo writes compensation log records, the book's redo-only records, each pointing to the next record to undo.
  • Fuzzy checkpoints record which pages are dirty.

Three passes

  1. Analysis: from the checkpoint, find the dirty pages and the unfinished transactions.
  2. Redo: repeat history from the oldest change that might be missing.
  3. Undo: roll back the unfinished, backward.

PostgreSQL in practice

Its log, backups, cleaning up and access control.

PostgreSQL's write-ahead log

  • The WAL is a series of 16 MB files in the server's pg_wal directory; a position in it is an LSN.
  • COMMIT returns once the commit record is flushed to disk (synchronous_commit).
  • A checkpoint runs every 5 minutes, or sooner after much WAL.
  • The first change to a page after a checkpoint logs the whole page, so a half-written page can be rebuilt (full_page_writes).
  • Redo only. Rows are never overwritten (week 13), so an unfinished transaction's versions just stay invisible: there is nothing to undo.
  • The commit log records which transactions committed; recovery replays the WAL forward from the checkpoint, and that is all.
  • The same WAL feeds replicas and backups.

Playground examples 3.1 to 3.4

Backups and point-in-time recovery

  • pg_dump makes a logical backup of one database at one moment; pg_restore loads it.
  • A replica replays the WAL as it is written, so it can take over within seconds (19.7). It copies mistakes too, so it doesn't replace backups.

Playground section 6

VACUUM: the cost of row versions

  • Every UPDATE and DELETE leaves a dead version behind, and so does every rollback.
  • VACUUM marks their space reusable; the file doesn't shrink.
  • VACUUM FULL rewrites the table compactly, but locks it while it works.
  • Autovacuum vacuums and analyzes each table once enough of it has changed. Leave it on.
  • A transaction left open for hours stops VACUUM from removing anything newer than its snapshot.
  • Watch pg_stat_user_tables: n_dead_tup, last_autovacuum.

Roles and least privilege

CREATE ROLE staff;
GRANT SELECT ON department, course TO staff;
CREATE ROLE dana LOGIN IN ROLE staff;

CREATE ROLE clerk LOGIN;
GRANT SELECT, UPDATE (budget)
  ON department TO clerk;
  • A role is a user, a group, or both. A new role can do nothing.
  • Grant to groups, and make people members; REVOKE takes a privilege back.
  • Give each program its own role with only what it uses: an injection then reaches only those tables.
  • Nobody's everyday work runs as a superuser.

Takeaways

  1. 1
    Log first, data later.

    The WAL rule lets the log explain whatever the disk holds after a crash.

  2. 2
    Committed means the commit record is on stable storage.

    Not that the data pages are.

  3. 3
    Redo forward, then undo backward.

    Repeat history from the last checkpoint, then roll back the undo list, logging as you go.

  4. 4
    The log protects against crashes, not disasters.

    Backups, archived WAL and replicas handle lost disks and mistakes.

  5. 5
    Keep the server healthy.

    Let autovacuum run, and give every program the least privilege it needs.
