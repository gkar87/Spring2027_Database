How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.
  • Examples that change data or create an index start with BEGIN; and end with ROLLBACK;, so nothing is kept. A box runs as one unit: if any statement in it fails, none of its changes are kept.
  • Reset database, at the top, puts the starting data back, whatever you changed. Loading takes a few seconds longer this week, because of the two big tables.
  • Exercises have a Check answer button. It runs your statements inside a transaction and rolls them back, so checking never changes the data. Your solved exercises are remembered in this browser only.
  • Timings in EXPLAIN ANALYZE are your browser's, and change from run to run. Count pages and rows, not milliseconds.

Each student has exactly 10 enrollments. The function plan_steps(query) lists the steps of a query's plan as rows, the way EXPLAIN does, so the exercises can check a plan. To try them at home in psql, run university.sql and then big_tables.sql.

1. Rows live on pages

Slides 5 to 7. PostgreSQL reads and writes 8 kB pages, never single rows. The hidden column ctid is a row's address: (page, item on that page).

A table's size divided by 8,192 bytes is its number of pages. An index is stored in pages too, as a separate file.

An UPDATE does not change a row where it stands. It writes a new version of the whole row, usually on the same page, and leaves the old version behind for transactions that might still need it (week 13). VACUUM reclaims dead versions later.

2. Counting the pages a query reads

Slides 10 and 11. EXPLAIN (ANALYZE, BUFFERS) runs the query and reports, for each step, the pages it found in the buffer pool (shared hit) and the pages it had to read in (read). Together they are the pages the step touched. A sequential scan touches every page of the table, however few rows it returns.

Through the primary key's index, one row costs a few pages: one per level of the tree, plus the table page that holds the row.

3. A B+-tree, one key at a time

Slides 14 to 17. A real index page holds hundreds of keys; this one holds 3, so that splits happen while you watch. The rules are the same.

Because the leaves are in key order, the primary key index also gives rows in order, and the first or last few rows cost only a few pages. No sort step appears in the plan.

4. Indexes in PostgreSQL

Slides 18 to 22. CREATE INDEX builds a B+-tree on the columns you name. Inside a transaction, the new index is used at once, and disappears with ROLLBACK.

A Bitmap Index Scan collects the addresses of the matching rows from the index, sorts them by page, and a Bitmap Heap Scan then reads each page once. When the index alone holds every column the query needs, an Index Only Scan can skip the table, but only for pages that VACUUM has marked as holding no old versions. These tables were just loaded, so you will mostly see bitmap scans here.

An index on two columns is sorted by the first, then by the second within it, like a phone book by last name, then first name. It serves a condition on the first column, or on both. A condition on the second column alone can only scan the whole index.

An index on name stores names as they are. A condition on lower(name) can't use it; an index on the expression lower(name) can.

The planner estimates how many rows a condition keeps. When it keeps most of the table, reading every page in order is cheaper than jumping between them, and the index is left unused.

Every index is kept up to date by every INSERT, UPDATE and DELETE on its table. Here, the same 20,000 inserts with no extra index and with three.

Exercises

Exercises 3 to 8 ask you to create an index and show a plan with plan_steps. Use the index name the exercise gives: it is part of the answer. Checking runs inside a transaction that is rolled back, so the index is never kept.

How many pages does big_student take? Return one number.

Hint

pg_relation_size('table') gives bytes, and a page is 8,192 bytes.

Show a solution
SELECT pg_relation_size('big_student') / 8192 AS pages;

How many rows of big_takes are on page 0? Return one number.

Hint

A ctid can be compared with another: page 0 is every ctid from '(0,0)' up to, but not including, '(1,0)'.

Show a solution
SELECT count(*) AS rows_on_page_0
FROM big_takes
WHERE ctid >= '(0,0)' AND ctid < '(1,0)';

Divide 100,000 by this number and compare with the page count from Example 1.2.

The registrar often lists one student's enrollments. Create an index named big_takes_student_idx that helps SELECT * FROM big_takes WHERE student_no = 777, then show that query's plan_steps.

Hint

Two statements: CREATE INDEX name ON table (column);, then SELECT * FROM plan_steps('…'); with the query inside quotes.

Show a solution
CREATE INDEX big_takes_student_idx ON big_takes (student_no);
SELECT * FROM plan_steps('SELECT * FROM big_takes WHERE student_no = 777');

A report counts enrollments in one course in one year: SELECT count(*) FROM big_takes WHERE course_id = 'MU-199' AND year = 2015. Create one index named big_takes_cy_idx that serves both conditions, then show its plan_steps.

Hint

One index on both columns. Inside the quotes of plan_steps, write each quote of the query twice: ''MU-199''.

Show a solution
CREATE INDEX big_takes_cy_idx ON big_takes (course_id, year);
SELECT * FROM plan_steps(
  'SELECT count(*) FROM big_takes WHERE course_id = ''MU-199'' AND year = 2015');

The columns in the other order work too, because both conditions are equalities.

A search box finds students by name, whatever the case: SELECT * FROM big_student WHERE lower(name) = 'sage chen'. Create an index named big_student_lower_idx that this query can use, then show its plan_steps.

Hint

Index the expression the query uses, in parentheses: (lower(name)).

Show a solution
CREATE INDEX big_student_lower_idx ON big_student (lower(name));
SELECT * FROM plan_steps(
  'SELECT * FROM big_student WHERE lower(name) = ''sage chen''');

Create an index named big_takes_year_idx on year. Then return one row with two columns: the first step of the plan for SELECT * FROM big_takes WHERE year > 2005, and the first step for … WHERE year > 2024. Example 4.4 shows how to pick out step 1.

Hint

SELECT (SELECT node FROM plan_steps('…') WHERE step = 1), (SELECT node FROM plan_steps('…') WHERE step = 1);

Show a solution
CREATE INDEX big_takes_year_idx ON big_takes (year);
SELECT (SELECT node FROM plan_steps(
          'SELECT * FROM big_takes WHERE year > 2005') WHERE step = 1) AS after_2005,
       (SELECT node FROM plan_steps(
          'SELECT * FROM big_takes WHERE year > 2024') WHERE step = 1) AS after_2024;

After 2005 keeps most of the table, so every page would be read anyway: the index is left unused.

No new index this time. Write the query for the 10 most recent enrollments, the ones with the highest reg_id (all columns), and show its plan_steps. Which index does it use?

Hint

ORDER BY reg_id DESC LIMIT 10, inside plan_steps('…').

Show a solution
SELECT * FROM plan_steps(
  'SELECT * FROM big_takes ORDER BY reg_id DESC LIMIT 10');

The primary key's index, read backward from its last leaf. No sort, and only a few pages.

Create a hash index named big_takes_hash_idx on student_no. Then, as in exercise 6, return one row with the first plan step for SELECT * FROM big_takes WHERE student_no = 4321 and for … WHERE student_no BETWEEN 1 AND 3.

Hint

CREATE INDEX name ON table USING hash (column);

Show a solution
CREATE INDEX big_takes_hash_idx ON big_takes USING hash (student_no);
SELECT (SELECT node FROM plan_steps(
          'SELECT * FROM big_takes WHERE student_no = 4321') WHERE step = 1) AS equal,
       (SELECT node FROM plan_steps(
          'SELECT * FROM big_takes WHERE student_no BETWEEN 1 AND 3') WHERE step = 1) AS range;

A hash index answers "equal to" only. Hashing scatters neighbouring keys, so it has no order to follow for a range.
