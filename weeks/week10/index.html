Where rows live

On disk, in pages, in the order they arrived.

Memory is fast and forgets; disk is slow and remembers

  • A database keeps everything on SSD or disk, and copies the parts it is using into memory.
  • So the cost of a query is mostly how many pages it has to bring in from storage.

The unit is the page, not the row

  • Storage is read and written in blocks. PostgreSQL's page is 8 kB (8,192 bytes).
  • Each table and each index is its own file of pages, numbered from 0.
  • Wanting one row costs its whole page. Wanting all 136 rows on that page costs the same.
  • So: how many pages a query touches is how we count its cost this week.

Inside a page

  • Rows vary in length (a varchar holds as much as it holds), so a fixed grid would not work.
  • Try SELECT ctid, * FROM student;. All 13 are on page 0, in the order they were inserted.

A table is a heap, and an UPDATE adds a row

  • A heap file keeps rows in no particular order. A new row goes wherever there is room.
  • An UPDATE does not change a row in place. It writes a whole new version and marks the old one as ended, so transactions still reading the old one can (week 13).
  • A DELETE only marks the row as ended.
  • VACUUM later frees the space of versions nobody can see. Autovacuum runs it for you.
BEGIN;
SELECT ctid, tot_cred FROM student
WHERE id = '12345';     -- (0,2)
UPDATE student SET tot_cred = tot_cred + 3
WHERE id = '12345';
SELECT ctid, tot_cred FROM student
WHERE id = '12345';     -- (0,14): a new version
ROLLBACK;

Two other ways to lay out data

Large values: TOAST

A row must fit in a page. A long text or jsonb value, past about 2 kB, is compressed or moved to a side table, and the row keeps a pointer to it. You never see it happen, but SELECT * pays to fetch it back.

Columns instead of rows

A row store keeps each row together: good for "everything about student 45678". A column store keeps each column together: good for "average of one column over a billion rows", reading only that column. Analytics systems use it (textbook 13.6).

The buffer pool

The pages that are in memory right now.

Every page goes through the buffer pool

  • A changed page is dirty. It is written back later, in the background, and only after its log record is safe (week 14).

Counting pages with EXPLAIN

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM big_takes
WHERE student_no = 4321;

Seq Scan on big_takes
    (actual rows=10 loops=1)
  Filter: (student_no = 4321)
  Rows Removed by Filter: 99990
  Buffers: shared hit=736
  • ANALYZE runs the query and reports what really happened, not only the estimate.
  • shared hit: pages found in the buffer pool. read: pages brought in from storage.
  • Ten rows wanted, all 736 pages touched, 99,990 rows read and thrown away. That is a sequential scan.

Indexes

A small, sorted structure that says where the rows are.

Ten rows among 100,000

Read everything

A sequential scan: 736 pages, every time. Fine for a small table or when most rows are wanted.

Keep the table sorted

Binary search finds a student in about 10 page reads. But only one sort order is possible, and every insert must make room in the middle.

Keep a sorted index

A separate structure, sorted on the search key, pointing at the rows. Many indexes per table, and an insert touches only a few pages of each.

The index has to stay sorted and shallow while rows come and go. That is what a B+-tree does.

The B+-tree

  • A search reads one page per level, from the root down. The B+-tree explorer

Why three or four reads are enough

Keys reachable at each height, about 300 entries per page
LevelsKeysLike
1300a course roster
290,000our big_takes

  • An 8 kB page holds hundreds of short keys with their pointers. That fanout is why the tree is so shallow.
  • big_takes_pkey has 2 levels. Finding reg_id = 4321 touches 3 pages: 2 in the index, 1 in the table.
  • The top levels are used by every search, so they stay in the buffer pool. Usually only the leaf and the row cost a read.

Ranges and order come free

-- down to reg_id 500, then along the leaves
SELECT reg_id, course_id FROM big_takes
WHERE reg_id BETWEEN 500 AND 520
ORDER BY reg_id;

-- start at the last leaf, walk backward
SELECT reg_id, course_id FROM big_takes
ORDER BY reg_id DESC LIMIT 5;  -- 3 pages
  • For BETWEEN, < or >: search for the low end, then follow the leaf links until past the high end.
  • The leaves are already in order, so ORDER BY on the indexed column needs no sort, and LIMIT stops early.
  • "Latest 5" or "page 3 of results" (week 9's keyset pagination) is cheap for this reason.

Playground example 3.1

Inserting: splits keep the tree balanced

  • Most inserts change one leaf. A split changes a few pages; a root split, rarely, adds a level.

Indexes in PostgreSQL

CREATE INDEX big_takes_student_idx
  ON big_takes (student_no);

DROP INDEX big_takes_student_idx;
  • A B-tree unless you say otherwise.
  • PRIMARY KEY and UNIQUE create one for you.
  • A foreign key does not. Index the referencing column when you join on it, or delete parent rows.
  • In a plan: Index Scan (index, then each row), Bitmap Index Scan plus Bitmap Heap Scan (collect addresses, then read each page once, in order), Index Only Scan (the index has every column needed).

Playground example 4.1

Indexes on several columns, and on expressions

CREATE INDEX big_takes_cy_idx
  ON big_takes (course_id, year);
-- helps: course_id = 'CS-347'
-- helps: course_id = 'CS-347' AND year = 2020
-- not much: year = 2020 alone

CREATE INDEX big_student_lower_idx
  ON big_student (lower(name));
-- helps: WHERE lower(name) = 'sage chen'
  • A two-column index is sorted like a phone book: by the first column, then by the second within it.
  • So it serves the first column alone, or both. For the second alone, the matches are scattered through it, and PostgreSQL can at best read the whole index.
  • An index stores values as they are. A condition on lower(name) needs an index on lower(name).

Other kinds of index

Index types in PostgreSQL
TypeAnswersTypical use
B-tree (default)=, <, BETWEEN, ORDER BYalmost everything
Hash= onlylong keys looked up exactly
GIN"contains"jsonb, arrays, full-text search
GiSToverlaps, nearestmaps and shapes, time ranges
BRINranges, roughlyhuge tables stored in time order, such as logs

A hash index scatters neighbouring keys, so it cannot answer a range. A BRIN index keeps only the smallest and largest value per block of pages: tiny, but useful only when the table's order follows the column.

Every index has a price

Writes

Every INSERT, UPDATE of an indexed column, and DELETE's later cleanup changes each index too. Five indexes, five more trees to keep sorted.

Space

An index on big_takes.student_no takes 117 pages, 16% of the table. It also competes for the buffer pool.

It may go unused

With an index on year, year > 2020 uses it; year > 2010 keeps 63% of the rows, and the planner reads the whole table instead.

Index what your queries search, join and sort by. Then check the plan, not your hopes. Playground examples 4.4 and 4.5

Worked example: one student's enrollments

SELECT * FROM big_takes
WHERE student_no = 4321;

-- before: Seq Scan
--   736 pages, 99,990 rows thrown away
CREATE INDEX big_takes_student_idx
  ON big_takes (student_no);
-- after: Bitmap Index Scan, Bitmap Heap Scan
--   2 index pages + 10 table pages = 12
  • From 736 pages to 12, for a 117-page index.
  • Why 10 table pages for 10 rows? This student's enrollments were inserted about 10,000 rows apart, so each sits on a different page.
  • If the table were stored in student_no order (a clustering index, textbook 14.2), all ten would share one page. PostgreSQL's CLUSTER sorts a table once; new rows do not keep the order.

Takeaways

  1. 1
    Count pages, not rows.

    A query costs the pages it touches; EXPLAIN (ANALYZE, BUFFERS) counts them.

  2. 2
    An UPDATE writes a new row.

    Old versions stay until VACUUM.

  3. 3
    A B+-tree is shallow and sorted.

    One read per level; ranges and order follow the leaves.

  4. 4
    Index what you search, join and sort by.

    Foreign keys included; the first column of a composite index matters most.

  5. 5
    Every index costs writes and space.

    Check the plan to see it used.
