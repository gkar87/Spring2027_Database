The relational model and algebra

Weeks 1 and 2: tables are sets of rows, keys identify them, and every query is a composition of a few operators.

Keys, and the operators that every query is made of

Keys

  • Superkey: determines the whole row.
  • Candidate key: a superkey with nothing to spare.
  • Primary key: the candidate key we chose; never NULL.
  • Foreign key: values that must appear as a key in another table.

After GROUP BY, every column in SELECT must be grouped or inside an aggregate: a group has one row. Practice question 2f.

NULL means unknown, and unknown spreads

Three-valued logic
ExpressionResult
NULL = NULL, NULL > 5unknown
unknown AND falsefalse
unknown OR truetrue
unknown AND true, NOT unknownunknown
x IS NULLtrue or false, never unknown
  • WHERE and HAVING keep only true. Unknown is dropped, like false.
  • count(*) counts rows; count(col), sum and avg skip NULLs.
  • x NOT IN (subquery) is never true if the subquery yields a NULL. Prefer NOT EXISTS.
  • A CHECK constraint passes on unknown: CHECK (grade IN (…)) accepts a NULL grade.

An outer join's condition belongs in ON

-- every department, with its instructors
-- earning over 90,000 (0 included)
SELECT d.dept_name, count(i.id)
FROM department d
LEFT JOIN instructor i
  ON i.dept_name = d.dept_name
 AND i.salary > 90000
GROUP BY d.dept_name;
  • As written: all 7 departments, most with 0.
  • Move i.salary > 90000 to WHERE, and the unmatched rows, whose salary is NULL, are dropped: only 2 departments remain. The LEFT JOIN has become an inner join.
  • Count a column from the right side, count(i.id), not count(*), or an empty department counts 1.

Review exercises 1 to 3

Subquery, CTE or window function?

Compare with one value

A scalar subquery: salary > (SELECT avg(salary) FROM instructor). Correlate it to compare within a group.

Test for existence

EXISTS or NOT EXISTS with a correlated subquery: "students who took a course", "courses nobody took".

Keep every row, add a group fact

A window function: rank() OVER (PARTITION BY dept_name ORDER BY salary DESC). To filter on it, wrap it in a subquery or CTE.

A CTE (WITH name AS (…)) names a step to make a long query readable; WITH RECURSIVE follows a chain, like prerequisites. Review exercises 4 to 7

Changing data safely

  • INSERT, UPDATE, DELETE: an UPDATE or DELETE without WHERE changes every row.
  • Constraints: NOT NULL, UNIQUE, PRIMARY KEY, CHECK, REFERENCES. A statement that breaks one is refused whole.
  • ON DELETE on a foreign key: NO ACTION (the default) refuses the delete, CASCADE deletes the referring rows, SET NULL keeps them with a NULL.
  • Transactions: BEGIN, then COMMIT to keep or ROLLBACK to undo everything since BEGIN.

The normalization toolkit

  1. 1
    Closure.

    Start with α; add the right side of any dependency whose left side is inside; repeat until nothing changes.

  2. 2
    Keys.

    Attributes on no right side are in every key. Grow from them; a key's closure is everything, and no smaller set's is.

  3. 3
    BCNF test.

    Every non-trivial α → β has α a superkey. 3NF also allows β inside some candidate key.

  4. 4
    Decompose.

    Split on a violating α → β into (α ∪ β) and the rest without β. Lossless, because α is a key of the first part.

  5. 5
    Check preservation.

    A rule whose attributes no longer sit in one table is lost. If it matters, choose 3NF.

Worked example: in 3NF, not in BCNF

R(A, B, C, D), F = { AB → C, C → D, D → A }

  1. B is on no right side, so every key contains B. B+ = {B}.
  2. {A, B}+ = {A, B, C, D}; {B, C}+ adds D, then A: all; {B, D}+ adds A, then C: all.
  3. Candidate keys: AB, BC and BD.
  • BCNF? No: in C → D, C is not a superkey (and in D → A, D is not).
  • 3NF? Yes: D is in the key BD, and A is in the key AB, so both violations are allowed.
  • The lesson: when every attribute is in some key, the table is in 3NF whatever its dependencies, and BCNF may cost a rule.
