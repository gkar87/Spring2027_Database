Why not just use files?

A spreadsheet or a folder of CSV files works, until several people and programs need the same data at once, and need it to stay right.

What goes wrong when a registrar runs on files

Six problems with file-based data and what a DBMS does about each
ProblemWith filesWhat a DBMS does
RedundancyA student's address is copied into the billing file and the advising file, and the copies drift apart.Store each fact once; every program reads the same copy.
Integrity"Credits must be positive" is checked in some programs and forgotten in others.Constraints declared once, enforced on every change.

Files copy the data; a DBMS keeps one copy and guards it

A database system is software that guards shared data

Database

A collection of related data about one enterprise: a university, a store, a hospital.

Database management system (DBMS)

The software that stores that data and lets many users and programs define, query and change it, safely and efficiently.

You have already used dozens

  • PostgreSQL, our engine this term, free and open source.
  • MySQL, SQL Server, Oracle, and SQLite, which runs inside every phone.
  • NoSQL systems such as MongoDB, for week 15.
§

The point of a DBMS is to let you say what data you want and what must stay true, and to leave how to the system.

PostgreSQL is the database developers use most

Three levels of abstraction

A DBMS hides how data is stored behind layers, so each layer can change without breaking the one above it.

  • View level: what one application or user sees. An advisor's view has no salaries in it.
  • Logical level: what data exists and how it relates. Tables, columns, keys.
  • Physical level: how it is stored. Files, pages, indexes.

Physical data independence

You can add an index or move files and no query has to change. Weeks 10–12 use this every day.

The relational model

One data structure, the relation, and a handful of rules about it. Fifty years on, it still underlies almost every database you will use.

“Future users of large data banks must be protected from having to know how the data is organized in the machine (the internal representation).”

E. F. Codd, “A Relational Model of Data for Large Shared Data Banks,” Communications of the ACM, 1970. The first sentence of the paper that started the relational model.

Schema and instance

Relation schema

The relation's name and its attributes, with their domains. It changes rarely, by design.

Relation instance

The set of tuples at one moment. It changes every time someone is hired, enrolls or gets a grade.

≈

The same split you know from programming: the schema is a variable's type, the instance is its current value. A database schema is the set of all relation schemas: five of them in our university. Playground example 1.2

A relation is a set, and that has consequences

Order does not matter

Neither the order of tuples nor, formally, of attributes carries meaning. Ask for an order with ORDER BY.

No duplicates

A set cannot hold the same tuple twice. Every relation therefore has at least one key.

Atomic values

Each attribute value is indivisible: one phone number per cell, not a list. This is first normal form, week 7.

!

SQL bends the second rule. A SQL table or query result is a bag (a multiset) and may contain duplicate rows unless you declare a key or write DISTINCT. We will meet this difference all term.

Count the duplicates, playground section 3

Keys: what makes a tuple unique

  • Superkey: a set of attributes whose values identify a tuple. In student, {id} and {id, name} both are.
  • Candidate key: a minimal superkey. {id} is one; {id, name} is not, because name adds nothing.
  • Primary key: the candidate key the designer chooses. We underline it.
Worked example: is {name} a key of student?

Today, no two students share a name. But a key is a promise about every legal instance, not a fact about today's data. A second Morgan Lee could enroll tomorrow, so {name} is not a key.

A key may need several attributes

takes(id, course_id, semester, year, grade)

A student may retake a course in a later term, so id and course_id alone are not enough.

Try to insert a duplicate key, playground section 4

Foreign keys connect relations: our university

Foreign key

An attribute whose every value must appear as a key value in another relation. takes.id must be the id of a real student.

This is the whole of this week's database, and the one the playground and Lab 0 load.

See it with its types in the playground

What a foreign key forbids

Rejected: a reference to nothing 
INSERT INTO student
VALUES ('00777', 'Lee Grant', 'Astrology', 0);

There is no Astrology department, so PostgreSQL reports a foreign-key violation and stores nothing.

Rejected: leaving others dangling 
DELETE FROM department
WHERE dept_name = 'Music';

A student, an instructor and a course still point at Music. By default the delete is refused; in week 5 you will choose ON DELETE CASCADE or SET NULL instead.

§

Referential integrity: every foreign-key value matches an existing key, or is NULL. The DBMS checks it on every insert, update and delete, in every program, forever. That is the integrity row of slide 7, solved.

Run both in the playground, section 5

How the DBMS checks a foreign key

NULL: a value that is missing

Three Spring 2027 enrollments in takes have no grade yet. Their grade is NULL: unknown, or not applicable. NULL is not zero and not the empty string.

  • Any comparison with NULL, even NULL = NULL, is unknown, not true.
  • WHERE keeps a row only when its condition is true.
  • So test for it with IS NULL and IS NOT NULL.
-- finds nothing: grade = NULL is unknown
SELECT * FROM takes WHERE grade = NULL;

-- finds the 3 enrollments without a grade
SELECT * FROM takes WHERE grade IS NULL;

Declarative

The query names the answer. It does not say which file to open, whether to use an index, or in what order to look. The optimizer decides, and it can decide differently tomorrow if the data grows.

The result is a relation too

So it can be the input to another query. That closure is what lets small queries compose into large ones, and it is the heart of next week's relational algebra.

What to take away

  1. 1
    A DBMS exists to keep shared data correct.

    Redundancy, integrity, atomicity, concurrency, access and security are each a job it does once for every program.

  2. 2
    Layers buy independence.

    Views over a logical schema over a physical layout; change one, keep the others.

  3. 3
    A relation is a set of tuples over named attributes.

    Schema is the type; instance is the current value. SQL results are bags.

  4. 4
    Keys and foreign keys are promises about every instance.

    The DBMS enforces them on every change.

  5. 5
    NULL means missing, and comparisons with it are unknown.

    Use IS NULL.
