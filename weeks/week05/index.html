Today: the statements that change things

INSERT, UPDATE and DELETE change rows. CREATE, ALTER and DROP change tables. Constraints, views, triggers and privileges decide what may change, and who may see it.

Changing the data

Transactions first, so every experiment can be undone; then INSERT, UPDATE and DELETE.

Try changes safely: BEGIN, then COMMIT or ROLLBACK

  • Atomic: all of a transaction's changes happen, or none do. A failed statement means none.
  • In psql, a statement outside BEGIN is its own transaction and is committed at once. There is no undo.
!

Before you run an UPDATE or DELETE on real data, type BEGIN; first. Check the result, then decide.

INSERT adds rows: listed values, or a query's result

-- every column, in table order
INSERT INTO department
VALUES ('Art', 'Morrow', 40000);

-- named columns; the rest: DEFAULT or NULL
INSERT INTO student (id, name)
VALUES ('77777', 'Pat Moreno');

-- many rows from a query
INSERT INTO takes (id, course_id, semester, year)
SELECT id, 'CS-101', 'Fall', 2027
FROM student
WHERE dept_name IS NULL;
  • Name the columns. The statement then survives a new column, and a reader knows which value goes where.
  • Pat Moreno gets dept_name NULL and tot_cred 0, because student says tot_cred integer DEFAULT 0.
  • INSERT … SELECT adds one row per row of the query: here Emery Walsh and the new Pat Moreno, the two students with no department.
DEFAULT

The value a column gets when an INSERT leaves it out. Without one, the default is NULL.

Run all three in a transaction, playground example 1.2

UPDATE changes values in the rows WHERE picks

-- 3% at 90,000 or more, else 5%
UPDATE instructor
SET salary = CASE
  WHEN salary >= 90000 THEN salary * 1.03
  ELSE salary * 1.05
END;

11 rows updated: no WHERE means every row. Noor Haddad's NULL salary stays NULL, because NULL × 1.05 is NULL.

Why one statement, not two

Run "5% where salary < 90,000" first and Maria Lopez goes from 87,000 to 91,350. Then "3% where salary ≥ 90,000" raises that salary again. One UPDATE with CASE decides every row from its old value.

!

An UPDATE or DELETE with no WHERE changes every row. Run the WHERE as a SELECT first to see which rows it picks.

Run it, playground example 1.3

A subquery in UPDATE or DELETE sees the data from before

DELETE removes rows, unless another table still needs them

-- the three enrollments with no grade yet
DELETE FROM takes WHERE year = 2027;

-- every row: the table stays, empty
DELETE FROM takes;

-- refused: teaches still points at this row
DELETE FROM instructor WHERE name = 'Priya Raman';
-- ERROR: update or delete on table "instructor"
-- violates foreign key constraint
-- "teaches_id_fkey" on table "teaches"
Three ways to remove data
StatementWhat goes
DELETE FROM t WHERE …The rows WHERE picks. Constraints are checked row by row.
TRUNCATE tEvery row, fast. The table stays.
DROP TABLE tThe rows and the table itself.

The refusal is a feature

Priya Raman teaches two sections. Deleting that row would leave rows in teaches pointing at nobody, so PostgreSQL refuses. Slide 15 shows the other choices.

Defining tables

CREATE TABLE, the types a column can have, and ALTER and DROP for tables that already hold data.

CREATE TABLE: columns, types and the rules they keep

CREATE TABLE prereq (
  course_id  varchar(8) REFERENCES course,
  prereq_id  varchar(8) REFERENCES course,
  PRIMARY KEY (course_id, prereq_id),
  CHECK (course_id <> prereq_id)
);

INSERT INTO prereq VALUES
  ('CS-190', 'CS-101'),
  ('CS-315', 'CS-190'),
  ('CS-319', 'CS-315');   -- and 3 more
  1. 1
    Each column has a name and a type.

    Both are course ids, so both use course's type, varchar(8).

  2. 2
    REFERENCES makes each a foreign key.

    A prereq row can only name courses that exist.

  3. 3
    The key is both columns together.

    A key of two columns is written as a table constraint, after the columns.

  4. 4
    CHECK states a rule about the row.

    A course cannot be its own prerequisite.

Common PostgreSQL column types and when to use them

Integer division truncates: 7 / 2 is 3, and 7 / 2.0 is 3.5. Week 4's averages were numeric because avg returns numeric for integer input.

ALTER TABLE changes a table that already holds rows

-- new column: existing rows get NULL
ALTER TABLE department
  ADD COLUMN phone varchar(12);
-- ... or the DEFAULT, if you give one
ALTER TABLE course
  ADD COLUMN active boolean DEFAULT true;
-- rename, and remove
ALTER TABLE department
  RENAME COLUMN phone TO office;
ALTER TABLE department DROP COLUMN office;
-- a table, and the views built on it
DROP TABLE IF EXISTS club CASCADE;
  • Each ALTER is checked against the rows already there. Adding NOT NULL to a column that holds a NULL fails.
  • IF EXISTS turns "no such table" from an error into a notice, so a script can run twice.
  • CASCADE also drops what depends on the table, such as views and other tables' foreign keys. Read what it says it dropped.

DDL is transactional in PostgreSQL

CREATE, ALTER and DROP inside BEGIN … ROLLBACK are undone too. Not every database can do this.

Integrity constraints

Rules written once, in the table, and enforced on every change from every program.

Four constraints on a single table

Single-table constraints, an example of each, and the error PostgreSQL gives
ConstraintSaysBreaking it on our database
NOT NULLA value is requirednull value in column "name" of relation "instructor" violates not-null constraint
UNIQUENo two rows share the value; NULLs do not countduplicate key value violates unique constraint …
PRIMARY KEYUNIQUE and NOT NULL; one per tableInserting id 10101 again: … unique constraint "instructor_pkey"
CHECK (…)The condition must not be falseA salary of 20,000: violates check constraint "instructor_salary_check"
!

CHECK rejects only false. For a NULL salary, salary > 29000 is unknown, so the row is accepted. That is how Noor Haddad got in. If a value is required, say NOT NULL as well.

Break each one, playground examples 3.1 and 3.2

A foreign key decides what happens when its row is deleted

dept_name varchar(20) REFERENCES department ON DELETE SET NULL ON UPDATE CASCADE

Name your constraints, and add them later if you must

ALTER TABLE course
  ADD CONSTRAINT credits_range
  CHECK (credits BETWEEN 1 AND 6);

INSERT INTO course
VALUES ('CS-999', 'Marathon', 'Comp. Sci.', 8);
-- ERROR: new row for relation "course"
-- violates check constraint "credits_range"

ALTER TABLE course DROP CONSTRAINT credits_range;
  • A name you chose tells the reader which rule failed. PostgreSQL's own names, such as course_credits_check, are guessable but not chosen.
  • Adding a constraint checks every existing row. If one breaks it, the ALTER fails and nothing changes.
  • Drop or replace a rule by its name.

Why in the database, not the app?

The registrar's web form, a Python script and a tired person in psql all go through the same table. A rule in the table holds for all three.

Views

A query with a name, used like a table: to hide columns, to save typing, and to give each reader the slice they need.

A view is a stored query, not stored rows

Name a question once, then ask it like a table

CREATE VIEW dept_summary AS
SELECT d.dept_name,
       count(i.id)         AS instructors,
       round(avg(i.salary)) AS avg_salary
FROM department d
LEFT JOIN instructor i ON i.dept_name = d.dept_name
GROUP BY d.dept_name;

SELECT * FROM dept_summary WHERE instructors = 0;
Result: 1 row

Economics0NULL
  • The hard part, the outer join and count(i.id) from week 4, is written once.
  • A view can use other views. DROP VIEW removes the query, never the data.

Materialized views store the rows

CREATE MATERIALIZED VIEW runs the query once and keeps the result, which is fast to read but goes stale. REFRESH MATERIALIZED VIEW dept_summary_m; runs it again. Use one for slow reports that may be a little out of date.

Run it, playground example 4.2

Some views can be changed, and WITH CHECK OPTION guards them

CREATE VIEW cs_faculty AS
SELECT id, name, dept_name FROM instructor
WHERE dept_name = 'Comp. Sci.'
WITH CHECK OPTION;

-- ok: salary is NULL
INSERT INTO cs_faculty
VALUES ('99998', 'Ben Ortiz', 'Comp. Sci.');

INSERT INTO cs_faculty
VALUES ('99997', 'Ana Silva', 'Music');
-- ERROR: new row violates check option
-- for view "cs_faculty"
  • A view over one table, with no GROUP BY, DISTINCT, aggregate or set operation, is updatable: PostgreSQL turns an INSERT, UPDATE or DELETE on it into one on the table.
  • Columns the view leaves out get their DEFAULT or NULL.
  • dept_summary is not updatable: which instructor would "set instructors = 5" change?

WITH CHECK OPTION

Without it, the Ana Silva row would go into instructor and then be invisible through the very view that inserted it.

Run it, playground example 4.3

Recursion over prerequisites

A query that refers to itself, to follow a chain of any length.

What must a student take before CS-319?

WITH RECURSIVE: a base query, UNION, and a step

WITH RECURSIVE needs(prereq_id, depth) AS (
  -- base: the direct prerequisites
  SELECT prereq_id, 1
  FROM prereq WHERE course_id = 'CS-319'
  UNION
  -- step: prerequisites of what we have
  SELECT p.prereq_id, n.depth + 1
  FROM prereq p
  JOIN needs n ON p.course_id = n.prereq_id
)
SELECT prereq_id, min(depth) AS depth
FROM needs
GROUP BY prereq_id
ORDER BY depth, prereq_id;
Result: 4 rows

  • In the step, needs means only the rows the last round added.
  • It stops when a round adds nothing. A cycle in the data would never stop while depth keeps growing, so real code adds a guard such as WHERE n.depth < 20.

Triggers and privileges

Code that runs when rows change, and rules about who may read or change what.

A trigger runs your function when a row changes

CREATE OR REPLACE FUNCTION credits_earned()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE student
  SET tot_cred = tot_cred +
      (SELECT credits FROM course
       WHERE course_id = NEW.course_id)
  WHERE id = NEW.id;
  RETURN NEW;
END $$;

CREATE TRIGGER credits_earned
AFTER UPDATE OF grade ON takes
FOR EACH ROW
WHEN ((OLD.grade IS NULL OR OLD.grade = 'F')
      AND NEW.grade IS NOT NULL AND NEW.grade <> 'F')
EXECUTE FUNCTION credits_earned();
  1. 1
    When:

    AFTER an UPDATE of the grade column on takes.

  2. 2
    For which rows:

    Each changed row whose grade went from nothing or F to a pass.

  3. 3
    What:

    The function adds the course's credits to that student. OLD and NEW are the row before and after.

PostgreSQL writes trigger functions in PL/pgSQL. The $$ … $$ quotes the function body.

Run it, playground example 6.1

One UPDATE becomes two, and the second is invisible

!

Use a constraint when one can say it; a trigger only for what constraints cannot, such as keeping a total or a log. Hidden work surprises the next programmer, and triggers that fire triggers are hard to debug.

GRANT gives a role a privilege; REVOKE takes it back

CREATE ROLE ta;
GRANT SELECT ON faculty TO ta;           -- a view
GRANT SELECT, UPDATE (grade) ON takes TO ta;

SET ROLE ta;                -- act as ta
SELECT * FROM faculty;      -- allowed
SELECT salary FROM instructor;
-- ERROR: permission denied for table instructor
RESET ROLE;                 -- back to the owner

REVOKE UPDATE (grade) ON takes FROM ta;
  • Privileges: SELECT, INSERT, UPDATE, DELETE, REFERENCES, and more. UPDATE can be limited to columns.
  • A role is a user or a group. Grant to a group role, then GRANT ta TO kim;
  • The owner of a table has every privilege on it; everyone else has none until granted.

A view plus a grant

ta can read faculty but not instructor: the view shows the columns, the missing grant hides the salaries.

What to take away

  1. 1
    BEGIN first; COMMIT or ROLLBACK after you look.

    A transaction is all or nothing.

  2. 2
    Run an UPDATE's or DELETE's WHERE as a SELECT first.

    No WHERE means every row. Subqueries see the data from before.

  3. 3
    Write the rules into the table, and name them.

    CHECK rejects only false, so NULL passes: add NOT NULL when a value is required.

  4. 4
    Choose each foreign key's ON DELETE.

    NO ACTION refuses, CASCADE deletes, SET NULL keeps the row.

  5. 5
    Views name queries; WITH RECURSIVE follows chains.

    Triggers and grants decide what else happens, and who may do it.
