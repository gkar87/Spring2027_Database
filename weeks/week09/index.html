Programs that talk to a database

A driver carries SQL from your code to the server and rows back.

What happens when a program runs a query

  • The server is a separate program, often on another machine. Each statement is a message there and a message back.
  • That wait is small on one machine and large across a network, and it is paid once per statement. Section 4 is about paying it less often.

The names differ; the shape does not. Connect, send SQL with placeholders and values, read rows, commit or roll back, close. Learn it once in Python and it carries over.

From a web page to the database

The three tiers of a web application, and what each one does with the data
TierWhat runs thereWhat it does with the data
BrowserHTML, a form, JavaScriptSends a request over HTTP with the user's input; never talks to the database.
Application serverA Python program (Flask, Django), Java, NodeChecks who the user is, runs the business rules, sends parameterized SQL through a pooled connection, turns rows into a page or JSON.

  • HTTP forgets each request, so who is signed in travels as a session cookie, and the application checks it on every request before any SQL runs.
  • A large web application keeps the same shape and splits the middle tier: pages, business logic and data access in separate layers, many application servers sharing pooled connections, and a cache in front of the slow queries.

A first program

import psycopg

with psycopg.connect("dbname=university") as conn:
    cur = conn.execute(
        "SELECT name, tot_cred FROM student "
        "WHERE dept_name = %s ORDER BY name",
        ("Physics",))
    for name, credits in cur:
        print(name, credits)
  • connect takes the same settings as psql. A password never goes in the code: the driver reads PGPASSWORD or a password file.
  • %s marks where a value goes; the values follow as a tuple. ("Physics",) needs its comma.
  • A cursor hands back rows as tuples. Loop over it, or call fetchone(), fetchmany(n) or fetchall().
  • Leaving the with block commits, or rolls back if an exception escaped, and closes the connection.

  • Money stays Decimal. Turning a salary into a float brings rounding errors back.

  • NULL becomes None, and in Python None == None is true. Three-valued logic stays in the database.
  • Going in, the same table works backwards: pass a Decimal or a date, not a string you formatted.

Parameters and SQL injection

A user's text is data. The moment it becomes part of the SQL, the user is writing your queries.

The bug: building SQL out of strings

def find_students(conn, text):
    # WRONG: the text becomes part of the SQL
    sql = ("SELECT id, name FROM student "
           f"WHERE name ILIKE '%{text}%'")
    return conn.execute(sql).fetchall()
  • For ri it works, and every test passes.
  • For O'Brien it fails with a syntax error: the apostrophe ends the string.
  • For ' OR 1=1 -- it returns every student.
  • With a driver or server that runs several statements per call, x'; DELETE FROM takes; -- deletes every enrollment.
!

The same bug comes from +, %, .format() and f-strings. Injection is consistently among the most common serious flaws found in web applications, on OWASP's lists of the top ten.

The fix: always send values as parameters

cur = conn.execute(
    "SELECT id, name FROM student "
    "WHERE name ILIKE %s ORDER BY name",
    ("%" + text + "%",))

# a table name chosen at run time
from psycopg import sql
q = sql.SQL("SELECT count(*) FROM {}").format(
        sql.Identifier(table_name))
  • The %s is a placeholder, not Python's % operator: never write "..." % value.
  • Wildcards belong to the value: "%" + text + "%" builds a value, not SQL.
  • Placeholders hold values only. A table or column name chosen at run time goes through psycopg.sql.Identifier, which quotes it as a name, or better, through a fixed list of allowed names.
  • Same idea in SQL: PREPARE … $1 and format('%I', …). Playground examples 1.1 and 1.2

Assume one mistake gets through

Least privilege

The program logs in as its own role, granted only what it needs. A role that can SELECT and INSERT cannot DELETE, even if injected. Lab 6, Q3.

Secrets out of code

Passwords and keys live in environment variables or a password file, never in the source or the repository. Code gets shared; secrets should not.

Store hashes, not passwords

If your application has user accounts, store a slow, salted hash (bcrypt, scrypt or Argon2), never the password. A stolen table then reveals no passwords.

Textbook section 9.8 covers application security, including cross-site scripting and audit trails.

Transactions from a program

psycopg opens a transaction for you. Ending it is your job.

When a transaction starts and ends

  • Forget to commit, and the program's changes vanish when it closes, while its open transaction holds locks the whole time.
  • conn.autocommit = True makes each statement its own transaction, like psql. Use it for scripts that only read.

Errors arrive as exceptions

try:
    conn.execute(
        "INSERT INTO takes "
        "VALUES (%s, %s, %s, %s, NULL)",
        (sid, cid, sem, year))
    conn.commit()
except psycopg.errors.UniqueViolation:
    conn.rollback()
    print("already enrolled")
except psycopg.Error as e:
    conn.rollback()
    raise
  • Each SQLSTATE code has its exception class: 23505 is UniqueViolation, 23503 ForeignKeyViolation, 23514 CheckViolation.
  • All of them are subclasses of psycopg.Error, so one except can catch the rest.
  • After any error, roll back before the next statement, or it fails with "current transaction is aborted".
  • Catch what you can handle; let the rest rise, so that a bug is not hidden.

Check, then act: in one transaction

Enrolling is a conversation: does the student exist, does the course, are the prerequisites passed, then insert. Run it as one transaction, so that it ends in one commit or not at all.

One transaction is not the whole story. Two copies of the program can both check at the same moment, both see "not enrolled", and both insert.

Let the database have the last word

  • A rule a constraint can state belongs in a constraint: the primary key of takes refuses the second insert, however the checks raced.
  • The program checks to give a helpful message; the constraint guarantees the rule.
  • Rules no constraint can state need locking or a stricter isolation level: week 13.

Worked example: one enrollment request

def can_enroll(conn, sid, cid):
    cur = conn.execute("""
        SELECT p.prereq_id FROM prereq p
        WHERE p.course_id = %s
          AND NOT EXISTS (
            SELECT 1 FROM takes t
            WHERE t.id = %s
              AND t.course_id = p.prereq_id
              AND t.grade IS NOT NULL
              AND t.grade <> 'F')""",
        (cid, sid))
    missing = [r[0] for r in cur]
    conn.rollback()      # read-only: end it
    return missing
  • Student 54321 asks for CS-347. It needs CS-101 and MA-201.
  • 54321 passed CS-101 with an A-, and takes MA-201 this term, with no grade yet.
  • So the query returns ['MA-201'], and the program refuses with a reason the student can act on.
  • The order of the parameters follows the order of the %s marks, not the order of the function's arguments.

Efficient round trips

A correct program can still be slow by asking too often, or for too much.

The N+1 problem

If you are writing a for loop around conn.execute, ask whether one query with a join could answer all the iterations at once. Playground examples 3.1 and 3.2

Moving many rows

Many rows in: executemany

cur.executemany(sql, rows) runs one statement for a list of parameter tuples, and psycopg sends them in a pipeline instead of waiting for each one.

Very many rows in: COPY

cur.copy("COPY t FROM STDIN") streams rows in PostgreSQL's bulk format: much faster than INSERTs for loading thousands of rows.

Very many rows out: a server-side cursor

conn.cursor(name="big") keeps the result on the server and fetches it in batches, so a million rows never sit in your program's memory at once. Lab 6, P8 (CS 5200).

And the simplest saving of all: select only the columns and rows you need. SELECT * then filtering in Python moves every row across the network for nothing.

One page at a time

Keep the last key of each page and ask for WHERE id > %s ORDER BY id LIMIT %s. Lab 6, P6. Playground examples 3.3 and 3.4

Connections are expensive; share them

  • Each PostgreSQL connection is a separate server process, with its own memory. Opening one takes a handshake and a login.
  • The server accepts only so many: max_connections is 100 by default.
  • A web application that opened a connection per request would spend its time connecting, and run out under load.

A connection pool

A pool opens a few connections once and lends them out: a request borrows one, uses it, and gives it back. In Python, psycopg_pool.ConnectionPool; between many programs and one server, a separate pooler such as PgBouncer.

Give it back with no open transaction, or the next borrower inherits it.

ORMs write the SQL for you

An object-relational mapper, such as SQLAlchemy or Django's, maps a table to a class and a row to an object: Student.objects.filter(dept_name="Physics") becomes a parameterized SELECT.

  • Values are always parameters, so the usual injection bug goes away, until someone writes raw SQL inside the ORM.
  • Reaching a related object in a loop (each student's advisor) quietly sends one query per object: N+1 again. Both ORMs have a way to load the related rows in one query.

Why this course writes the SQL itself

An ORM saves typing, not understanding. To know why a page is slow, or whether a rule is enforced, you read the SQL it sends, and everything in weeks 1 to 8 applies to it.

Takeaways

  1. 1
    Values are parameters, always.

    Never build SQL from a value with +, %, format() or an f-string.

  2. 2
    End every transaction.

    Commit what should stay, roll back after any error, and don't leave one open.

  3. 3
    Let constraints guarantee rules.

    The program checks to explain; the database enforces.

  4. 4
    Count round trips.

    One join beats a query per row; a page beats the whole table.

  5. 5
    Give the program only what it needs.

    Its own role, and secrets outside the code.
