Week 13 playground: transactions and concurrency

A transaction is a group of statements that happen completely or not at all, and that behave as if nobody else were using the database. Here you make transactions succeed and fail, reason about interleaved schedules with SQL, watch two real sessions collide at each isolation level, and look at the locks and row versions PostgreSQL uses to keep them apart.

How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.
  • The database in your browser has one session: one user, one connection. Everything you run here happens one statement at a time, so nothing can collide. Section 3 replays two real sessions recorded on a PostgreSQL server; Lab 8 has you open two yourself.
  • A box without BEGIN runs as one unit: if any statement fails, the ones before it are undone too. A box that starts with BEGIN; should end with COMMIT; or ROLLBACK;. The examples end with ROLLBACK;, so nothing is kept. Reset database, at the top, puts the starting data back, whatever you changed.
  • Exercises have a Check answer button. It runs your statements inside a transaction and rolls them back, so your answer must not contain BEGIN, COMMIT or ROLLBACK of its own. Savepoints are fine. Your solved exercises are remembered in this browser only.

1. All or nothing

Slides 3 to 7. Moving 5,000 of budget from Music to Physics takes two UPDATEs. If only the first one happened, 5,000 would vanish. Inside BEGIN … COMMIT, the two happen together or not at all: that is atomicity. ROLLBACK undoes everything since BEGIN.

Inside the transaction, the first SELECT sees its own changes: 55,000 and 90,000. After ROLLBACK, the second sees the budgets as they were.

When a statement fails, PostgreSQL does not keep the statements before it either. Department budgets must be above 0, so the second UPDATE here is refused, and the first is undone with it. Run it, then run Example 1.3 to see that Music still has 60,000.

A savepoint marks a point inside a transaction that you can go back to without losing everything. ROLLBACK TO SAVEPOINT undoes only what came after the mark; the transaction stays open. A program uses it to try one step, and recover if that step fails, without starting over.

The Physics raises are still there; Diego Torres in Music is back at 72,000. The last ROLLBACK then undoes the Physics raises too.

2. Schedules, as data

Slides 9 to 13. A schedule lists the operations of several transactions in the order they ran. This week's database has five, in a table you can query:

  • sched(sched, step, tx, op, item): in schedule sched, at step, transaction tx does op: R reads item, W writes it, C commits, A aborts. The items are A and B; commits and aborts have no item.
  • S1 runs T1 and then T2. S2 interleaves the same operations. S3 is the lost update. S4 has three transactions. In S5, T2 reads what T1 wrote and commits, and then T1 aborts.

A query can lay a schedule out the way the book draws it, one column for each transaction:

Two operations conflict when they belong to different transactions, touch the same item, and at least one of them writes. Their order matters: swap them and someone reads a different value, or a different write survives. Every other pair can be swapped freely. This self-join finds the conflicting pairs in S3, earlier step first:

Each conflicting pair says one transaction must come before the other in any equivalent serial order. Those are the edges of the precedence graph: Ti → Tj when an operation of Ti conflicts with a later one of Tj.

S3 has an edge each way, T1 → T2 and T2 → T1: no serial order can put each before the other. A schedule is conflict serializable exactly when its precedence graph has no cycle. Week 4's WITH RECURSIVE finds every transaction reachable from each one; a transaction that can reach itself is on a cycle.

UNION, not UNION ALL, is what makes this stop: once no new (start, at) pair turns up, the recursion ends, even around a cycle.

Serializable is not the whole story. In S5, T2 reads the A that T1 wrote and commits; then T1 aborts. T2 has committed work based on a value that never officially existed, and committed work can't be undone. A schedule is recoverable if every transaction commits only after the ones it read from have committed, and cascadeless if no transaction reads a value whose writer has not yet committed. S2 and S4 are conflict serializable, yet not cascadeless: had T1 aborted in S2, T2 would have had to abort too. PostgreSQL never lets this happen, because a session never sees another session's uncommitted writes. Section 3 shows it.

4. Locks

Slides 21 and 22. Writers in PostgreSQL take locks: an UPDATE locks each row it changes until its transaction ends, so a second writer of the same row waits, as in the deadlock and lost update scenarios above. Holding every lock until commit is strict two-phase locking. Readers take no row locks, and never wait for writers. The view pg_locks lists the locks each session holds; pg_backend_pid() picks out yours.

On the table and its index, RowExclusiveLock: "I am changing some rows here." It does not block other writers of other rows; it only blocks things like DROP TABLE. The locks on single rows are not listed: PostgreSQL marks them in the row itself, the xmax of section 5. The transactionid lock is what a waiting session waits on: when this transaction ends, the waiter wakes. The line for pg_locks is the SELECT reading the view.

SELECT … FOR UPDATE locks the rows it reads as if it were about to change them. It is how read-then-write code avoids the lost update in Read Committed: the second session's FOR UPDATE waits until the first commits, and then reads the new value.

5. Versions, not overwrites

Slides 23 and 24. PostgreSQL never changes a row in place. An UPDATE writes a new version of the row and marks the old one as replaced. Every row has hidden columns that say which version it is: xmin, the transaction that created it; xmax, the transaction that deleted or replaced it (0 if none); and ctid, its place on disk, (page, slot), as in week 10.

After the UPDATE, the row you see has a new ctid and your transaction's number as its xmin. The old version is still on the page. Another session, which can't see your uncommitted version, keeps reading that one: that is why readers never wait for writers.

The old version is back, at its old ctid, and its xmax now holds the number of the transaction that rolled back. Rolling back wrote nothing: PostgreSQL keeps a record of which transactions committed and which aborted, and a version whose xmax aborted still counts as alive. The dead new version stays on the page until VACUUM clears it (week 14).

Which versions a statement sees is decided by its snapshot: the list of transactions that had committed when it was taken. Read Committed takes a new snapshot for each statement; Repeatable Read and Serializable take one at the first statement and keep it to the end. pg_current_snapshot() shows it as xmin:xmax:running: every transaction below the first number is finished, every one from the second on is in the future, and the list names those still running in between.

Exercises

The checker wraps your answer in its own transaction and rolls it back, so leave out BEGIN, COMMIT and ROLLBACK. SAVEPOINT and ROLLBACK TO SAVEPOINT are fine. The last statement's result is the one checked.

History lends Biology 10,000 of its budget. Make the two changes, then show dept_name and budget of both departments, ordered by dept_name.

Hint

Example 1.1, without its BEGIN and ROLLBACK, with the departments and the amount changed.

Show a solution
UPDATE department SET budget = budget - 10000 WHERE dept_name = 'History';
UPDATE department SET budget = budget + 10000 WHERE dept_name = 'Biology';
SELECT dept_name, budget FROM department
WHERE dept_name IN ('History', 'Biology') ORDER BY dept_name;

Biology 105,000 and History 40,000. In a program, both UPDATEs go in one transaction, so a failure between them can't lose the 10,000.

Give every Comp. Sci. instructor a raise of 5,000. Then set a savepoint named before_math, give every Mathematics instructor a raise of 5,000, and change your mind about Mathematics only. Show name and salary of the instructors in both departments, ordered by name.

Hint

Example 1.4 shows the pattern: SAVEPOINT, the change, ROLLBACK TO SAVEPOINT.

Show a solution
UPDATE instructor SET salary = salary + 5000 WHERE dept_name = 'Comp. Sci.';
SAVEPOINT before_math;
UPDATE instructor SET salary = salary + 5000 WHERE dept_name = 'Mathematics';
ROLLBACK TO SAVEPOINT before_math;
SELECT name, salary FROM instructor
WHERE dept_name IN ('Comp. Sci.', 'Mathematics') ORDER BY name;

The Comp. Sci. raises stay; Maria Lopez is back at 87,000.

List the conflicting pairs of operations in schedule S4: two columns, the earlier step and the later step, ordered by both. Before you run it, find them by hand in Example 2.1's layout (change S2 to S4 and add a t3 column).

Hint

Example 2.2, for S4, keeping only the two step columns.

Show a solution
SELECT a.step AS first, b.step AS second
FROM sched a JOIN sched b
  ON a.sched = b.sched AND a.item = b.item
 AND a.tx <> b.tx AND a.step < b.step
 AND 'W' IN (a.op, b.op)
WHERE a.sched = 'S4'
ORDER BY first, second;

Four pairs: (1, 7) and (3, 7) on A, T1 before T2's write; (3, 4), T2 reading what T1 wrote; and (5, 6), T2 reading what T3 wrote. Steps 1 and 4 both read A, which is no conflict.

For each schedule, show its name and true or false: is it conflict serializable? Include every schedule, even one with no edges at all.

Hint

Keep Example 2.4's two CTEs. In the final query, go through the distinct schedule names and use NOT EXISTS to look for a row of reach with start = at.

Show a solution
WITH RECURSIVE edge AS (
  SELECT DISTINCT a.sched, a.tx AS from_tx, b.tx AS to_tx
  FROM sched a JOIN sched b
    ON a.sched = b.sched AND a.item = b.item
   AND a.tx <> b.tx AND a.step < b.step
   AND 'W' IN (a.op, b.op)
), reach(sched, start, at) AS (
  SELECT sched, from_tx, to_tx FROM edge
  UNION
  SELECT r.sched, r.start, e.to_tx
  FROM reach r JOIN edge e ON e.sched = r.sched AND e.from_tx = r.at
)
SELECT s.sched,
       NOT EXISTS (SELECT 1 FROM reach r
                   WHERE r.sched = s.sched AND r.start = r.at) AS serializable
FROM (SELECT DISTINCT sched FROM sched) s
ORDER BY s.sched;

Only S3 is not. Starting from the list of schedules, not from edge, keeps a schedule with no conflicts at all in the answer.

Which schedules are not recoverable? A schedule is not recoverable when some transaction reads an item written by another transaction that has not committed yet, and then commits before that writer commits (or the writer never commits). Show only the schedule names.

Hint

Start from Example 2.5's reads of uncommitted data, as a CTE of (sched, writer, reader). Join each to the reader's commit, and keep it when no commit by the writer comes before that step.

Show a solution
WITH rf AS (
  SELECT DISTINCT r.sched, w.tx AS writer, r.tx AS reader
  FROM sched w JOIN sched r
    ON r.sched = w.sched AND r.item = w.item
   AND w.op = 'W' AND r.op = 'R'
   AND r.tx <> w.tx AND w.step < r.step
  WHERE NOT EXISTS (SELECT 1 FROM sched e
                    WHERE e.sched = w.sched AND e.tx = w.tx
                      AND e.op IN ('C', 'A') AND e.step < r.step)
)
SELECT DISTINCT rf.sched
FROM rf JOIN sched rc
  ON rc.sched = rf.sched AND rc.tx = rf.reader AND rc.op = 'C'
WHERE NOT EXISTS (SELECT 1 FROM sched wc
                  WHERE wc.sched = rf.sched AND wc.tx = rf.writer
                    AND wc.op = 'C' AND wc.step < rc.step);

Only S5. S2 and S4 also read uncommitted data, but each reader commits after its writers, so they are recoverable, though not cascadeless.

Lock History's row with SELECT … FOR UPDATE, then list the mode of every lock your session holds on the department table itself (not its index), from pg_locks.

Hint

In pg_locks, relation is the table's internal number. 'department'::regclass turns the name into that number.

Show a solution
SELECT * FROM department WHERE dept_name = 'History' FOR UPDATE;
SELECT mode FROM pg_locks
WHERE pid = pg_backend_pid() AND relation = 'department'::regclass;

RowShareLock. Like RowExclusiveLock, it is a table lock that lets other sessions read and write the table's other rows; the lock on History's row itself is marked in the row.

Change Biology's building to Hale. Then show one row with one column: true if the Biology row you now see was created by your own transaction. Compare its xmin with pg_current_xact_id().

Hint

xmin has type xid and pg_current_xact_id() has type xid8, a wider number. Cast the second: pg_current_xact_id()::xid.

Show a solution
UPDATE department SET building = 'Hale' WHERE dept_name = 'Biology';
SELECT xmin = pg_current_xact_id()::xid AS mine
FROM department WHERE dept_name = 'Biology';

True: the UPDATE wrote a new version, and its xmin is this transaction. Run the SELECT alone and you get false, because the version you see then was made by the transaction that loaded the data.

Section 3's write skew scenario broke the rule that the two Hale departments keep at least 200,000 between them. Write the check a careful transaction would make after its own cut: lower Mathematics's budget by 10,000, then return one row, one column: true if the Hale departments still have at least 200,000 together.

Hint

An UPDATE, then a SELECT of sum(budget) >= 200000 over the departments in Hale.

Show a solution
UPDATE department SET budget = budget - 10000 WHERE dept_name = 'Mathematics';
SELECT sum(budget) >= 200000 AS rule_kept
FROM department WHERE building = 'Hale';

True: 200,000, so this transaction may commit. The trouble in the scenario was that each session made the same check and saw only its own cut. Under Serializable, PostgreSQL notices that the two checks together depended on each other's writes and cancels one; under Repeatable Read nothing stops them.
