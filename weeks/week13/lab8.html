Registration opens at 8:00 a.m., and a thousand students click Enroll in the same second. The registrar's program passed every test with one user. Here you play two users at once, in two terminal windows, and find out which ways of writing an enrollment survive.

Files and setup

  • university.sql: the university database, the same as since week 5. If your university database already has it, you don't need it again.
  • lab8_setup.sql: makes this lab's three small tables in the university database: lab8_section (three sections, one with a single seat left), lab8_enroll (who is in each), and lab8_duty (two teaching assistants, both on duty). Running it again puts them back as they were. It never changes the university's own tables.
  • lab8_answers.txt: the starter file for your results and written answers.

This lab needs two sessions on the same server at the same time: two terminal windows, each running psql. A Colab notebook runs one statement at a time and can't do this, so use PostgreSQL installed on your own computer (Lab 0, path 1). If you have used Colab so far, install it now, before you start; the university database loads the same way. pgAdmin works too: each Query Tool tab is its own session.

  1. Put the files in one folder and open two terminal windows there. Put them side by side.
  2. In both, start psql: psql -d university (on Windows, psql -U postgres -d university). Call the left one A and the right one B.
  3. In each, run SELECT pg_backend_pid();. Two different numbers: two sessions. Write them in the answers file.
  4. In A, run \i lab8_setup.sql.

How to run a task

  • Each task is a numbered list of steps. Type each step in the session it names, A or B, in exactly that order, and press Enter after each one.
  • Sometimes a statement doesn't answer: the cursor just sits there. That session is waiting for a lock. That is part of the lab: go on with the next step in the other session, and watch the waiting one finish when it is released.
  • Start every task with \i lab8_setup.sql in A, so each one starts from the same data. If a task goes wrong, run ROLLBACK; in both sessions, then the setup, and start the task again.
  • Keep everything each window shows: you hand in both, as lab8_A.txt and lab8_B.txt. On macOS or Linux, start each window with script lab8_A.txt (or lab8_B.txt) before psql, and type exit after quitting psql at the end. On Windows, select all the text in each window and paste it into the file. pgAdmin users copy each tab's statements and messages.
  • After each task, fill in its row in the answers file while the results are on screen.

Before you start, step through the scenarios in the week 13 playground's replay. They are the same kinds of collisions, on the department budgets, so you'll know what to look for.

Part A: the tasks, T1 to T10

Every task but T8 gives you the statements. T1 to T5 are on the section with one seat left, CS-347-1: 30 seats, 29 taken.

  1. T1. Can B see A's uncommitted change? Run \i lab8_setup.sql in A first.

    1. A: BEGIN;
    2. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-347-1';
    3. B: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';
    4. A: ROLLBACK;
    5. B: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';

    Record what B saw both times.

  2. T2. The last seat, sold twice. Run the setup again. Each session plays a program that reads how many seats are taken, sees one is left, and writes back the new total, 30, with its student's enrollment. Read Committed, the default.

    1. A: BEGIN;
    2. B: BEGIN;
    3. A: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';
    4. B: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';
    5. A: UPDATE lab8_section SET taken = 30 WHERE sec = 'CS-347-1';
    6. A: INSERT INTO lab8_enroll VALUES ('90001', 'CS-347-1');
    7. A: COMMIT;
    8. B: UPDATE lab8_section SET taken = 30 WHERE sec = 'CS-347-1';
    9. B: INSERT INTO lab8_enroll VALUES ('90002', 'CS-347-1');
    10. B: COMMIT;
    11. A: SELECT taken, (SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1') AS enrolled FROM lab8_section WHERE sec = 'CS-347-1';

    Record taken and enrolled at the end. They should agree.

  3. T3. Fix 1: one statement that checks and adds. Setup again. Now each session adds 1 and checks the capacity in the same UPDATE. A program enrolls the student only if the UPDATE changed a row.

    1. A: BEGIN;
    2. B: BEGIN;
    3. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-347-1' AND taken < capacity;
    4. B: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-347-1' AND taken < capacity;
    5. A: INSERT INTO lab8_enroll VALUES ('90001', 'CS-347-1');
    6. A: COMMIT;
    7. B: ROLLBACK;
    8. A: SELECT taken, (SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1') AS enrolled FROM lab8_section WHERE sec = 'CS-347-1';

    Step 4 waits. Which step lets it go on? What does it report then, and why is that right? B rolls back because its UPDATE changed nothing: the section is full.

  4. T4. Fix 2: lock the row when you read it. Setup again. The read-then-write program from T2, with FOR UPDATE on the read.

    1. A: BEGIN;
    2. B: BEGIN;
    3. A: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1' FOR UPDATE;
    4. B: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1' FOR UPDATE;
    5. A: UPDATE lab8_section SET taken = 30 WHERE sec = 'CS-347-1';
    6. A: INSERT INTO lab8_enroll VALUES ('90001', 'CS-347-1');
    7. A: COMMIT;
    8. B: ROLLBACK;
    9. A: SELECT taken, (SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1') AS enrolled FROM lab8_section WHERE sec = 'CS-347-1';

    Record what B's SELECT returned, and when. B sees the section is full, so it rolls back.

  5. T5. Fix 3: Repeatable Read. Setup again. The program from T2, unchanged, in Repeatable Read transactions.

    1. A: BEGIN ISOLATION LEVEL REPEATABLE READ;
    2. B: BEGIN ISOLATION LEVEL REPEATABLE READ;
    3. A: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';
    4. B: SELECT capacity, taken FROM lab8_section WHERE sec = 'CS-347-1';
    5. A: UPDATE lab8_section SET taken = 30 WHERE sec = 'CS-347-1';
    6. A: INSERT INTO lab8_enroll VALUES ('90001', 'CS-347-1');
    7. A: COMMIT;
    8. B: UPDATE lab8_section SET taken = 30 WHERE sec = 'CS-347-1';
    9. B: ROLLBACK;
    10. A: SELECT taken, (SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1') AS enrolled FROM lab8_section WHERE sec = 'CS-347-1';

    Record B's error message exactly. A program would retry B's whole transaction, read 30, and stop.

  6. T6. Watch a session wait. Setup again. B's UPDATE (step 4) waits; while it does, A looks at the server's lock table and its list of sessions.

    1. A: BEGIN;
    2. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-319-1';
    3. B: BEGIN;
    4. B: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-319-1';
    5. A: SELECT pid, locktype, relation::regclass AS relation, mode, granted FROM pg_locks WHERE NOT granted;
    6. A: SELECT pid, state, wait_event_type, wait_event, left(query, 40) AS query FROM pg_stat_activity WHERE datname = current_database() AND pid <> pg_backend_pid();
    7. A: COMMIT;
    8. B: COMMIT;
    9. A: SELECT taken FROM lab8_section WHERE sec = 'CS-319-1';

    Record the locktype and mode of the lock B waits for, and B's wait_event. Your pid numbers will differ.

  7. T7. Deadlock. Setup again. Each session adds a student to two sections, in opposite orders.

    1. A: BEGIN;
    2. B: BEGIN;
    3. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-319-1';
    4. B: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'BIO-101-1';
    5. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'BIO-101-1';
    6. B: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-319-1';
    7. A: COMMIT;
    8. B: ROLLBACK;

    Step 6 ends in an error after about a second. Record which session got it, the first line of the message, and what happened to A's waiting UPDATE. Leave out the DETAIL lines' process numbers.

  8. T8. Fix the deadlock. Setup again. Write T7 again so that both sessions update the two sections in the same order, BIO-101-1 first, and run it, keeping the same turns: A, B, A, B and so on. Write your steps in the answers file, then run them.

    One session will wait, but no deadlock can happen. Record which step waited and the final taken of both sections.

  9. T9. Write skew. Setup again. The rule: at least one teaching assistant is on duty. Ari and Bea each check that the other is still on duty, then go off duty. Repeatable Read.

    1. A: BEGIN ISOLATION LEVEL SERIALIZABLE;
    2. B: BEGIN ISOLATION LEVEL SERIALIZABLE;
    3. A: SELECT count(*) FROM lab8_duty WHERE on_duty;
    4. B: SELECT count(*) FROM lab8_duty WHERE on_duty;
    5. A: SELECT locktype, relation::regclass AS relation, page, tuple, mode FROM pg_locks WHERE mode = 'SIReadLock';
    6. A: UPDATE lab8_duty SET on_duty = false WHERE ta = 'Ari';
    7. B: UPDATE lab8_duty SET on_duty = false WHERE ta = 'Bea';
    8. A: COMMIT;
    9. B: COMMIT;
    10. A: SELECT ta, on_duty FROM lab8_duty ORDER BY ta;

    Record the last count. Did either transaction fail?

  10. T10. Write skew, caught. Setup again. T9 again, in Serializable transactions.

    1. A: BEGIN ISOLATION LEVEL SERIALIZABLE;
    2. B: BEGIN ISOLATION LEVEL SERIALIZABLE;
    3. A: SELECT count(*) FROM lab8_duty WHERE on_duty;
    4. B: SELECT count(*) FROM lab8_duty WHERE on_duty;
    5. A: UPDATE lab8_duty SET on_duty = false WHERE ta = 'Ari';
    6. B: UPDATE lab8_duty SET on_duty = false WHERE ta = 'Bea';
    7. A: COMMIT;
    8. B: COMMIT;
    9. A: SELECT ta, on_duty FROM lab8_duty ORDER BY ta;

    Record which COMMIT failed, its message, and who is on duty at the end. What should the program that ran B do next?

Part B: savepoints, T11

  1. T11. Savepoints, in one session. Setup again; this task needs only session A. Student 00035 enrolls in three sections in one transaction, with a savepoint before each enrollment. The student is already in BIO-101-1, so that INSERT fails.

    1. A: BEGIN;
    2. A: SAVEPOINT s1;
    3. A: INSERT INTO lab8_enroll VALUES ('00035', 'CS-319-1');
    4. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-319-1';
    5. A: SAVEPOINT s2;
    6. A: INSERT INTO lab8_enroll VALUES ('00035', 'BIO-101-1');
    7. A: -- your statement here
    8. A: SAVEPOINT s3;
    9. A: INSERT INTO lab8_enroll VALUES ('00035', 'CS-347-1');
    10. A: UPDATE lab8_section SET taken = taken + 1 WHERE sec = 'CS-347-1';
    11. A: COMMIT;

    Replace the comment with the one statement that undoes only the failed enrollment and lets the transaction go on. Then show 00035's sections and, for every section, taken next to the number of enrollments. What does COMMIT print if you leave that statement out, and why?

Part C: three short answers

In lab8_answers.txt, in your own words, a short paragraph each, using what your sessions showed:

  1. W1. Explain what went wrong in T2, and how each of T3, T4 and T5 prevented it. Which of the three would you use for the enrollment feature of a real program, and why?

  2. W2. In T6, what exactly was B waiting for, according to pg_locks? Why does a session wait on another transaction rather than on the row itself, and when does the wait end?

Part D: CS 5200 only

  1. D1. Run T10 again, and right after step 4, run this in A:

    SELECT locktype, relation::regclass AS relation, page, tuple, mode
FROM pg_locks WHERE mode = 'SIReadLock';

    Then finish the task. These are predicate locks: they block nothing, but record what each Serializable transaction read. Record the rows. What does each lock cover, and why the whole table rather than single rows? (Hint: how did the SELECT read lab8_duty?) Then explain how these locks let PostgreSQL see that A and B depend on each other.

  2. D2. A different enrollment program never updates taken: it counts the enrollments and inserts one if there are fewer than 30. Run it in Repeatable Read, as below, then again with SERIALIZABLE in steps 1 and 2 (setup before each).

    1. A: BEGIN ISOLATION LEVEL REPEATABLE READ;
    2. B: BEGIN ISOLATION LEVEL REPEATABLE READ;
    3. A: SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1';
    4. B: SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1';
    5. A: INSERT INTO lab8_enroll VALUES ('90001', 'CS-347-1');
    6. B: INSERT INTO lab8_enroll VALUES ('90002', 'CS-347-1');
    7. A: COMMIT;
    8. B: COMMIT;
    9. A: SELECT count(*) FROM lab8_enroll WHERE sec = 'CS-347-1';

    Record the final count each time. In Repeatable Read, the two transactions inserted different rows and changed nothing in common: explain why the section still ended up overbooked, which anomaly this is, and why Serializable caught it.

If something goes wrong

  • A step you expected to wait answered at once, or the other way round: a step was skipped or done in the wrong session. Run ROLLBACK; in both, then the setup, and start the task again.
  • "current transaction is aborted, commands ignored until end of transaction block": an earlier statement in that session failed. Run ROLLBACK; there. That is what B does after the errors in T5 and T7.
  • "WARNING: there is already a transaction in progress" after BEGIN: the previous task was never finished in that session. Run ROLLBACK; and start the task again.
  • The setup itself waits: the other session still has a transaction open on the lab tables. Run ROLLBACK; in B.
  • "relation "lab8_section" does not exist": run \i lab8_setup.sql in A, from the folder where the file is, and check both sessions are connected to university.
  • Anything else: copy the exact message and bring it to office hours, Tuesday and Wednesday 12:00–3:00 p.m., MIC room D159, or post it in the week 13 discussion in Brightspace.
