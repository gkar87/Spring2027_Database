Concurrency bugs pass every test you run alone. They show up on the busy day, as money that vanished or a rule that quietly broke.

Two statements that must happen together

BEGIN;
UPDATE department SET budget = budget - 5000
WHERE dept_name = 'Music';
UPDATE department SET budget = budget + 5000
WHERE dept_name = 'Physics';
COMMIT;
  • Moving 5,000 of budget from Music to Physics takes two UPDATEs.
  • If the server crashes between them, 5,000 has vanished.
  • If another session sums the budgets between them, it sees 5,000 too little.
  • A transaction makes the two one unit: nobody sees half of it, and a crash keeps all of it or none.

Transactions

What a transaction promises.

ACID: four promises

The four properties of a transaction, and what provides each in PostgreSQL
PropertyThe promiseWho keeps it
AtomicityAll of the transaction's changes happen, or none.Row versions and the commit record (this week and next)
ConsistencyA transaction that starts from a correct database leaves a correct one.You, with constraints and transactions that keep your rules
IsolationEach transaction behaves as if it ran alone.Snapshots and locks, as strong as the isolation level asks
DurabilityOnce COMMIT returns, the changes survive a crash.The write-ahead log (week 14)
  • Consistency is the odd one: the database checks your constraints, but only you know that the budgets in Hale must add to 200,000.

The life of a transaction

  • An aborted transaction can be restarted as a new transaction, if it failed for a reason like a deadlock; a program does that, not the database.

Transactions in SQL

BEGIN;
UPDATE instructor SET salary = salary * 1.1
WHERE dept_name = 'Physics';
SAVEPOINT after_physics;
UPDATE instructor SET salary = salary * 1.1
WHERE dept_name = 'Music';
ROLLBACK TO SAVEPOINT after_physics;
COMMIT;   -- keeps only the Physics raises
  • Without BEGIN, each statement is its own transaction (autocommit).
  • COMMIT keeps; ROLLBACK undoes everything since BEGIN.
  • After an error, the transaction can only roll back: PostgreSQL ignores every statement until it ends.
  • A savepoint lets you undo part of a transaction and carry on.
  • psycopg starts a transaction for you; with conn.transaction(): commits at the end of the block, or rolls back if an exception leaves it.

Schedules

Which interleavings are safe, and how to tell.

Interleaving is the point

  • Running one transaction at a time is safe but slow: while one waits for a disk or a user, the others wait too.
  • A schedule is serializable if it leaves the same result as some serial order. That is the goal.

Conflicting operations

Two operations of different transactions on the same item
FirstThenConflict?Why
Ri(Q)Rj(Q)NoBoth read the same value in either order.
Ri(Q)Wj(Q)YesSwapped, Ti would read Tj's value.
Wi(Q)Rj(Q)YesSwapped, Tj would read the older value.
Wi(Q)Wj(Q)YesSwapped, a different write survives.
  • Operations on different items never conflict, and can be swapped freely.
  • If swapping non-conflicting neighbours can turn a schedule into a serial one, it is conflict serializable.

Playground example 2.2

The precedence graph

  • With no cycle, any topological order of the graph is an equivalent serial order: S4 can be T1, T3, T2 or T3, T1, T2.

Finding a cycle with SQL

WITH RECURSIVE edge AS (
  SELECT DISTINCT a.sched, a.tx AS from_tx,
                  b.tx AS to_tx
  FROM sched a JOIN sched b
    ON a.sched = b.sched AND a.item = b.item
   AND a.tx <> b.tx AND a.step < b.step
   AND 'W' IN (a.op, b.op)
), reach(sched, start, at) AS (
  SELECT sched, from_tx, to_tx FROM edge
  UNION
  SELECT r.sched, r.start, e.to_tx
  FROM reach r JOIN edge e
    ON e.sched = r.sched AND e.from_tx = r.at
)
SELECT * FROM reach WHERE start = at;
  • edge: the precedence graph, from the conflicting pairs.
  • reach: every transaction reachable from each one.
  • A transaction that reaches itself is on a cycle.
  • UNION drops repeated rows, so the recursion stops even around a cycle. UNION ALL would run forever.
  • Here it finds S3: T1 reaches T1, and T2 reaches T2.

Serializable is not enough: aborts

S5

  1. T1 reads A
  2. T1 writes A
  3. T2 reads A, T1's uncommitted value
  4. T2 commits
  5. T1 reads B
  6. T1 aborts
  • T2 committed work built on a value that never officially existed, and committed work can't be undone. S5 is not recoverable.
  • Recoverable: a transaction commits only after every transaction it read from has committed.
  • Cascadeless: nobody reads uncommitted values at all, so one abort never forces others to abort.
  • PostgreSQL's schedules are always cascadeless: a session never sees another's uncommitted writes.

What can go wrong

Five anomalies, each in one of the recorded scenarios
AnomalyWhat happens
Dirty readB reads a value A has written but not committed. A rolls back; B used a value that never existed.
Non-repeatable readA reads Physics's budget twice and gets two values, because B committed a change in between.
PhantomA counts Physics instructors twice and gets 2, then 3: B inserted a row that matches A's condition.
Lost updateA and B both read 60,000 and each write back their own total. One raise disappears.
Write skewA and B each check a rule, see it holds, and change different rows. Together they break it.

Three ways to avoid the lost update

-- 1. Let the database do the arithmetic
UPDATE department SET budget = budget + 5000
WHERE dept_name = 'Music';

-- 2. Lock the row when you read it
SELECT budget FROM department
WHERE dept_name = 'Music' FOR UPDATE;
-- ... compute in the program, then UPDATE

-- 3. Repeatable Read, and retry on error
BEGIN ISOLATION LEVEL REPEATABLE READ;
  • The bug is read, compute, write back: the value read can be out of date by the time it is written.
  • 1: the second UPDATE waits for the first, then rereads the row. Both raises kept: 75,000.
  • 2: FOR UPDATE makes the second reader wait, so it reads 65,000.
  • 3: the second writer gets "could not serialize access due to concurrent update" and runs again.

Scenarios: lost update, no lost update, lost update caught

Write skew, and what Serializable adds

  • The rule: the two Hale departments, Comp. Sci. and Mathematics, keep at least 200,000 between them. They start with 210,000.
  • A cuts Comp. Sci. by 10,000 and B cuts Mathematics by 10,000. Each first checks the total: 210,000, fine.
  • In Repeatable Read both commit, and the total is 190,000. They changed different rows, so nothing conflicted on a row.
  • In Serializable, PostgreSQL also tracks what each transaction read. A read what B wrote and B read what A wrote: no serial order explains that, so B's COMMIT fails. Retried, B sees 200,000 and refuses.
→

If a transaction checks a rule that involves other rows than the ones it changes, use Serializable, or lock what you check with FOR UPDATE.

Scenarios: write skew, write skew caught

Retrying in a program

RETRY = (errors.SerializationFailure,
         errors.DeadlockDetected)

def cut_budget(conn, dept, amount):
    for attempt in range(5):
        try:
            with conn.transaction():
                cur = conn.execute(HALE_SUM)
                total = cur.fetchone()[0]
                if total - amount < 200000:
                    raise ValueError("below 200,000")
                conn.execute(CUT, (amount, dept))
            return
        except RETRY:
            continue  # rolled back: run it again
    raise RuntimeError("gave up after 5 tries")
  • The connection's isolation level is set once, to Serializable. HALE_SUM and CUT hold the SELECT and the UPDATE.
  • A serialization failure or a deadlock is not a bug: it is the database asking you to try again.
  • Retry the whole transaction, reads included, so the checks see the new data.
  • Give up after a few tries, and tell the user.
  • A rule failure (ValueError here) is not retried: retrying would fail the same way.

Locks and versions

How PostgreSQL keeps sessions apart.

Locks and two-phase locking

  • A shared lock lets others read too; an exclusive lock lets nobody else lock the item. Only two shared locks are compatible.
  • PostgreSQL locks every row it writes until the transaction ends, strict two-phase locking for writes, but readers take no row locks: they read an older version instead.

Playground examples 4.1 and 4.2

Deadlock

  • Detection, PostgreSQL's way: wait deadlock_timeout (1 second), look for a cycle, cancel one transaction.
  • Prevention, your way: change rows in the same order everywhere, for example by key. Then no cycle can form.

Scenario: deadlock

Versions, not overwrites

  • This is multiversion concurrency control (MVCC): readers never wait for writers, and writers never wait for readers.

Playground examples 5.1 and 5.2

Snapshots decide what you see

A snapshot

  • The set of transactions that had committed when it was taken.
  • A version is visible if its xmin is in the snapshot and its xmax is not.
  • Plus your own changes.

When it is taken

  • Read Committed: at each statement. Each statement sees the latest commits, so two reads can differ.
  • Repeatable Read and Serializable: once, at the first statement, kept to the end.
  • Old versions pile up until VACUUM removes those no snapshot can see any more. Next week.

Takeaways

  1. 1
    A transaction is all or nothing.

    Group changes that belong together; consistency is your rules, kept inside one transaction.

  2. 2
    Serializable means a serial order explains it.

    No cycle in the precedence graph; recoverable and cascadeless handle aborts.

  3. 3
    Know your level.

    Read Committed allows lost updates and write skew; Repeatable Read stops lost updates; Serializable stops both.

  4. 4
    Errors under concurrency are normal.

    Retry the whole transaction on a serialization failure or deadlock.

  5. 5
    Locks for writers, versions for readers.

    Strict two-phase locking on rows, and snapshots of row versions.
