Query Optimization

Last week, the algorithms a plan is made of. This week, how PostgreSQL picks one plan out of thousands without running any of them: by rewriting the query, guessing how many rows each step will produce, and searching join orders cleverly. And what happens when a guess is wrong.

Rules that never change the answer

Some equivalence rules from the textbook, and what each one lets the optimizer do
RuleIn algebraWhat it buys
Split a selectionσθ1 ∧ θ2(E) ≡ σθ1(σθ2(E))Each condition can move on its own.
Joins commuteE1 ⋈ E2 ≡ E2 ⋈ E1Either input can be the hash table or the outer loop.
Joins associate(E1 ⋈ E2) ⋈ E3 ≡ E1 ⋈ (E2 ⋈ E3)Any join order.
Selection through a joinσθ(E1 ⋈ E2) ≡ σθ(E1) ⋈ E2, if θ uses only E1Filter before joining.
Projection through a joinkeep only the columns used aboveNarrower rows, fewer pages to hash or sort.
  • The optimizer applies rules like these to generate alternatives, then costs them. It never changes what the query means.

Filter early: push selections down

  • A heuristic the textbook gives: perform selections as early as possible, then projections.
  • PostgreSQL always does this. You never have to write the filter in a subquery yourself.

Playground example 1.4

Two conditions: assume they are independent

The rules

  • AND: s1 × s2
  • OR: s1 + s2 − s1 × s2
  • NOT: 1 − s

On big_takes

  • course_id = 'CS-101' AND semester = 'Summer': 0.21428 × 0.2 → 4,286 expected.
  • course_id = 'CS-101' OR semester = 'Summer': 0.21428 + 0.2 − 0.04286 → 37,142 expected, 37,141 found.
→

Multiplying is right only when knowing one condition tells you nothing about the other. Course and semester are unrelated here, so the guesses land.

Playground example 2.1

When columns are related

SELECT * FROM big_takes
WHERE year = 2027 AND grade IS NULL;
-- expected 137, found 3,704

CREATE STATISTICS takes_year_grade (mcv)
  ON year, grade FROM big_takes;
ANALYZE big_takes;
-- expected 3,704, found 3,704
  • 1/27 of rows are from 2027, 3.7% have no grade: 100,000 × 1/27 × 0.037 = 137.
  • But the two are the same rows: 2027 courses are still in progress.
  • An estimate 27 times too low can turn a hash join into a nested loop that runs thousands of times.
  • CREATE STATISTICS collects the most common pairs. Also: dependencies and ndistinct.

Playground examples 2.2 and 2.3

Estimating a join

  • Joining on a key of s, a foreign key of r: at most nr rows. big_takes ⋈ big_student: 100,000.
  • Otherwise: nr × ns / max(V(A, r), V(A, s)).
  • Department in Kirk ⋈ big_student: 1 × 10,000 / 7 = 1,429 expected, 1,000 found. Departments are not all the same size.

  • A left-deep tree joins the result so far with one stored table at a time, so each join can pipeline into the next.
  • The key idea: the best way to join {department, big_student, big_takes} doesn't depend on what is joined after it. Work it out once, reuse it.

Dynamic programming, one set size at a time

Try the join order explorer

What PostgreSQL does

  • Dynamic programming over sets, with bushy trees allowed, for up to join_collapse_limit tables in one FROM: 8 by default.
  • Beyond 8, it plans the query in pieces, keeping the order you wrote between them.
  • At 12 or more tables (geqo_threshold), it switches to a genetic search: good plans, not guaranteed best.
  • Cross products are left until no join condition remains.
  • SET join_collapse_limit = 1 makes it follow your written order: useful for experiments, rarely in production.

Rewrites and stored results

What the optimizer changes before it plans, and what it can't.

Subqueries become joins

Students who took MU-199, and who never did, written four ways
Written asPlanned as
student_no IN (SELECT …)Hash Right Semi Join
EXISTS (SELECT … WHERE t.student_no = s.student_no)Hash Right Semi Join, the same plan
NOT EXISTS (…)Hash Right Anti Join
student_no NOT IN (SELECT …)a scan with a subplan in its filter
  • Turning a correlated subquery into a join is decorrelation: it can then use any join algorithm and any order.
  • NOT IN is never true if the subquery returns a NULL (week 3), so it isn't an anti join. Prefer NOT EXISTS.

Playground examples 5.1 and 5.2

Views and materialized views

A view

  • Replaced by its definition, then optimized with the rest of the query.
  • WHERE student_no = 42 on a GROUP BY view is pushed below the grouping: 10 rows counted, not 100,000.
  • WHERE n_courses > 10 can't be: every group must be counted first.

A materialized view

CREATE MATERIALIZED VIEW course_counts AS
  SELECT course_id, count(*) AS n
  FROM big_takes GROUP BY course_id;

REFRESH MATERIALIZED VIEW course_counts;
  • Stores the result: reading it is 1 page, not 736.
  • PostgreSQL does not keep it current; you refresh it.

Playground examples 5.3 and 5.4

When a plan is slow

  1. 1
    Run EXPLAIN ANALYZE.

    Find the lowest step where expected and actual rows differ ten times or more.

  2. 2
    Stale or missing statistics?

    Run ANALYZE on the tables under it.

  3. 3
    Related columns?

    CREATE STATISTICS on them, then ANALYZE.

  4. 4
    A value the sample missed?

    Raise the column's statistics target: ALTER TABLE … ALTER COLUMN … SET STATISTICS 500.

  5. 5
    Still wrong?

    Rewrite the query (NOT EXISTS for NOT IN), or add the index the plan needs. Turning enable_ settings off is for experiments only.

Takeaways

  1. 1
    Same answer, many expressions.

    Equivalence rules let the optimizer filter early and reorder joins.

  2. 2
    Plans are chosen by estimates.

    Rows are guessed from statistics: common values, histograms, distinct counts.

  3. 3
    Two assumptions can fail.

    Uniformity and independence. Common-value lists and CREATE STATISTICS fix them.

  4. 4
    Join order by dynamic programming.

    Best plan per set of tables, smallest sets first.

  5. 5
    Write what you mean.

    IN and EXISTS plan the same; NOT EXISTS beats NOT IN; materialized views need refreshing.
