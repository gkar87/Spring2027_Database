Week 12 playground: how PostgreSQL chooses a plan

The planner never runs a plan to see how good it is. It guesses how many rows each step will produce, from statistics it keeps about every table, and picks the plan whose guesses cost least. Here you read those statistics, check the guesses against the truth, catch them going wrong, and fix them.

How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.
  • A box runs as one transaction. SET LOCAL changes a setting until the end of that transaction, so a setting changed in one box is back to normal in the next.
  • Examples that create something start with BEGIN; and end with ROLLBACK;, so nothing is kept. ANALYZE is the exception: the table sizes it measures stay even after a rollback. Reset database, at the top, puts the starting data back, whatever you changed.
  • Exercises have a Check answer button. It runs your statements inside a transaction and rolls them back, so checking never changes the data. Your solved exercises are remembered in this browser only.
  • Timings are your browser's and change from run to run. Count rows and pages, not milliseconds.

The guess next to the truth

This week uses the generated tables again: big_student (10,000 rows) and big_takes (100,000 rows), with only their primary keys indexed. Every student has exactly 10 enrollments.

A new function, plan_rows(query), runs a query and shows, for each step, est_rows, the rows the planner expected before it ran, next to actual_rows, the rows it really produced. When a step runs more than once (loops), both are for one run. EXPLAIN ANALYZE shows the same two numbers as rows= twice on each line. To try it at home in psql, run university.sql and then big_tables.sql.

1. What the planner knows about a table

Slides 8 to 10. ANALYZE reads a table and stores what it found. Two places hold it: pg_class keeps each table's size (the book's nr and br), and the view pg_stats keeps, for each column, the number of distinct values (V(A, r)), the share of NULLs, the most common values with the share of rows each has, and a histogram of the rest.

reltuples of −1 means the table has never been analyzed. The seed's small tables never were, and PostgreSQL's automatic ANALYZE waits until at least 50 rows have changed, so on a real server these 7 departments and 10 courses could stay unanalyzed for good. Section 3 shows what that costs.

For course_id = 'CS-101', the planner looks CS-101 up in the most common values and multiplies its share, 0.21428, by 100,000 rows: 21,428. To read the two lists side by side, turn them into rows with unnest. They are stored as a type that has to be cast to text and back to an array first.

A column with too many distinct values for that list gets a histogram instead: boundaries that split the rows into buckets of equal size. reg_id has 400 buckets of 250 rows. For reg_id < 12345 the planner counts the whole buckets below 12,345 and the part of the one it falls in.

2. Two conditions at once

Slides 11 and 12. For A AND B the planner multiplies the two shares, as if knowing one told you nothing about the other: the independence assumption. For A OR B it adds them and takes away the overlap. In big_takes, the course and the semester really are unrelated, so the guesses are right.

Year and grade are not unrelated. Every 2027 enrollment is still in progress, so its grade is NULL, and only those are. The planner multiplies 1/27 of the rows by 3.7% and expects 137 rows; there are 3,704.

CREATE STATISTICS tells PostgreSQL to collect statistics on columns together. The mcv kind keeps the most common pairs of values, so the next ANALYZE sees that 2027 and NULL go together. Raising default_statistics_target to 400 for this one ANALYZE makes it read every row instead of a sample, so you get the same numbers every time.

3. How big is a join?

Slide 13. This query finds the courses taken by students in the department housed in Kirk, which is Physics. It joins four tables, and it comes back several times this week.

SELECT s.name, c.title
FROM department d
  JOIN big_student s ON s.dept_name = d.dept_name
  JOIN big_takes t   ON t.student_no = s.student_no
  JOIN course c      ON c.course_id = t.course_id
WHERE d.building = 'Kirk'

Before department and course are analyzed, the planner knows nothing about them and assumes a few pages' worth of rows. Read the steps from the bottom up: it expects 3 departments in Kirk, where there is 1, but also far fewer matching students than there are, so it ends up expecting 560 result rows instead of 10,000. Each estimate is built from the ones below it, errors included.

Now analyze them and look again. This example keeps its ANALYZE, so the estimates in Example 3.1 change too; Reset database puts the never-analyzed state back. The estimates come much closer. The one left is the uniformity assumption: with 7 departments, the planner expects each to have 10,000 / 7 = 1,429 students, but Physics has 1,000 and Computer Science 3,000.

4. Choosing the join order

Slides 14 to 17. The Kirk query can join its four tables in many orders. All give the same 10,000 rows, but some make huge results along the way. Try a few orders, then watch how the optimizer finds the best one without trying them all.

PostgreSQL searches orders itself for up to join_collapse_limit tables, 8 unless changed. Setting it to 1 makes it join in the order the query is written, which lets you try a bad order for real. Compare actual_rows on the join steps.

The planner's order joins the one Kirk department to its 1,000 students first, so every later join works on small inputs. The written order joins all 100,000 enrollments to their courses and their students before it finally keeps only Physics: 210,000 rows made by joins instead of 21,000, for the same answer.

5. Rewrites the optimizer makes for you

Slides 19 and 20. Before choosing an order, PostgreSQL rewrites the query into an equivalent one it can plan better. IN (subquery) and EXISTS both become a semi join, a join that keeps each left row at most once, so the two ways of writing it get the same plan.

Their negations are not equivalent. If the subquery of NOT IN returns a NULL, NOT IN is never true (week 3), so PostgreSQL cannot turn it into an anti join and keeps it as a subplan, a small plan run inside the filter. Here student_no can't be NULL and the answers are the same, but the planner does not use that fact. Write NOT EXISTS.

A view is replaced by its definition, and a condition on the view's grouping column is pushed down below the GROUP BY, so only student 42's rows are counted. A condition on the count itself can't be pushed: every group has to be counted first.

A materialized view stores its result, so reading it is one small scan instead of grouping 100,000 rows. The price: PostgreSQL does not keep it up to date. It shows the old count until you run REFRESH MATERIALIZED VIEW.

From pg_stats, work out the planner's estimate for grade = 'B' in big_takes. Return one row: the value B and the estimate, rounded to a whole number of rows.

Hint

Show a solution
SELECT m.val, round(m.freq * 100000) AS estimate
FROM pg_stats,

Hint

FROM plan_rows('SELECT * FROM big_takes WHERE year = 2027 AND grade = ''A''');

The planner expects 420: 1/27 of the rows, times the 11% of grades that are A. There are none, because no 2027 enrollment has a grade yet.

With join_collapse_limit set to 1, write the Kirk query in an order that makes its joins produce as few rows as possible. Return one number: the sum of actual_rows over its join steps, from plan_actual.

Hint

Pick the join steps with WHERE node ~ 'Join|Nested Loop'. The join order explorer shows which order is best.

Show a solution
SET LOCAL join_collapse_limit = 1;
SELECT sum(actual_rows)
FROM plan_actual('SELECT s.name, c.title FROM department d
  JOIN big_student s ON s.dept_name = d.dept_name
  JOIN big_takes t ON t.student_no = s.student_no
  JOIN course c ON c.course_id = t.course_id
  WHERE d.building = ''Kirk''')
WHERE node ~ 'Join|Nested Loop';

21,000: 1,000 after the first join, then 10,000 twice. Starting with big_student and then department gives the same.

This query lists the students who have never taken CS-347, but its plan uses a subplan:

SELECT name FROM big_student
WHERE student_no NOT IN (SELECT student_no FROM big_takes WHERE course_id = 'CS-347')

Rewrite it with NOT EXISTS and show the new query's plan_steps.

Hint

Example 5.2 does this for MU-199.

Show a solution
SELECT * FROM plan_steps('SELECT name FROM big_student s
  WHERE NOT EXISTS (SELECT 1 FROM big_takes t
                    WHERE t.student_no = s.student_no
                      AND t.course_id = ''CS-347'')');

An anti join, which PostgreSQL can plan like any other join: here a hash join that builds its table on the students.

Create a materialized view named course_counts with each course_id in big_takes and its number of enrollments, n. Then add the enrollment (100001, 1, 'MU-199', 'Fall', 2027, NULL) to big_takes, and return the n for MU-199 from the view, up to date.

Hint

Example 5.4 shows every statement. Without the REFRESH, the view still shows the old count.

Show a solution
CREATE MATERIALIZED VIEW course_counts AS
  SELECT course_id, count(*) AS n FROM big_takes GROUP BY course_id;
INSERT INTO big_takes VALUES (100001, 1, 'MU-199', 'Fall', 2027, NULL);
