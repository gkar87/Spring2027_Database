What goes wrong in a wide table

One table that holds two kinds of fact stores some of them many times, and then the copies drift apart.

inst_dept stores each department once per instructor

Repeating a fact is not just wasted space. Every copy is a chance for the copies to disagree.

Three anomalies, one cause

Update

UPDATE inst_dept
SET building = 'Watson'
WHERE id = '10101';

One row says Watson, two say Hale. Which is right? The table cannot say.

Insert

INSERT INTO inst_dept
  (dept_name, building)
VALUES ('Art', 'Morrow');

Refused: id is the key and cannot be NULL. A department with no instructors cannot exist.

Delete

DELETE FROM inst_dept
WHERE name = 'Diego Torres';

Music's building and budget go with the only Music instructor.

→

The cause is the same each time: department facts depend on dept_name, which is not the table's key. Run all three, examples 1.2 to 1.4

Splitting a table: lossless or lossy

Lossless: split on dept_name, a key of the department part. Joining the parts gives back exactly the 11 rows.

Lossy: split on building, a key of neither part. The join returns 19 rows; 8 of them are false.

Functional dependencies

The rules that say which facts belong together.

A functional dependency says one value fixes another

Functional dependency

α → β holds on a schema when any two rows that agree on the attributes in α also agree on the attributes in β. Read it as "α determines β".

Data can disprove a dependency, never prove one

-- groups that break dept_name → building
SELECT dept_name,
       count(DISTINCT building) AS buildings
FROM inst_dept
GROUP BY dept_name
HAVING count(DISTINCT building) > 1;
-- no rows: this data obeys it
  • Group by the left side, count the distinct values of the right side. Any group above 1 is a counterexample.
  • name → salary passes today only because no two instructors share a name. The next hire could break it.
  • So the rules come from the people who use the data, like cardinality last week. The query checks that the data obeys them.
→

Keys are dependencies too

Superkey and candidate key

K is a superkey of R when K → R: it determines every attribute.

A candidate key is a superkey with no smaller superkey inside it. In inst_dept, id is the only one.

Trivial dependencies

α → β is trivial when β ⊆ α, like id, name → name. It holds in every table and never causes trouble.

The dependencies that matter are the non-trivial ones whose left side is not a superkey, like dept_name → building.

We write F for the dependencies we are given, and F+ for every dependency they imply.

Armstrong's axioms derive every implied dependency

The three axioms

  • Reflexivity: if β ⊆ α, then α → β.
  • Augmentation: if α → β, then γα → γβ.
  • Transitivity: if α → β and β → γ, then α → γ.

Rules that follow from them

  • Union: α → β and α → γ give α → βγ.
  • Decomposition: α → βγ gives α → β.
  • Pseudotransitivity: α → β and γβ → δ give αγ → δ.

Example: R(A, B, C, G, H, I)

F = { A → B, A → C, CG → H, CG → I, B → H }

  1. A → B and B → H give A → H (transitivity).
  2. CG → H and CG → I give CG → HI (union).
  3. A → C and CG → I give AG → I (pseudotransitivity).

The axioms are sound (they derive only true dependencies) and complete (they derive all of them).

Attribute closure: everything a set of attributes determines

result := α
repeat
  for each β → γ in F:
    if β ⊆ result:
      result := result ∪ γ
until result does not change
return result        -- this is α+
  • α+ is the set of attributes that α determines under F.
  • Each pass adds what some dependency's left side already covers. It stops when a pass adds nothing.
  • It never needs F+: it runs in time about quadratic in the size of F.

Closure answers three questions

Is α a superkey? Yes, if α+ holds every attribute.

Does α → β hold? Yes, if β ⊆ α+.

Is it a candidate key? Yes, if no smaller subset is a superkey. A and G alone are not.

A canonical cover is F with nothing extra

  • An attribute is extraneous if removing it from a dependency leaves F+ unchanged.
  • A canonical cover Fc implies the same dependencies as F, has no extraneous attributes, and has each left side once.
  • To find one: merge dependencies with the same left side, remove an extraneous attribute, and repeat until nothing changes.
  • 3NF synthesis, on slide 22, starts from Fc.

Example from the textbook

F = { A → BC, B → C, A → B, AB → C }

  1. Merge A → BC and A → B into A → BC.
  2. In AB → C, A is extraneous: B → C already holds. Drop it; B → C is now listed twice.
  3. In A → BC, C is extraneous: A → B and B → C imply it.

Fc = { A → B, B → C }

Normal forms

Tests a schema passes when it stores each fact once, and algorithms that make it pass.

First normal form: one value per cell

A schema is in 1NF when every attribute's domain is atomic: the database never has to take a value apart to answer a query.

Two columns that break 1NF
idphonescourse_code
10101816-555-0101, 816-555-0199CS-347-F25
  • phones holds a list. Finding who has a given number means parsing every cell. Fix: a table inst_phone(id, phone), as last week's multivalued attributes.
  • course_code packs a department, a number and a semester. A query for "every CS course" has to cut strings. Fix: one column per part.
  • Atomic depends on use: a date is atomic until you need its month.

Boyce-Codd normal form

BCNF

R is in BCNF when, for every dependency α → β in F+ on R, either it is trivial or α is a superkey of R.

inst_dept is not in BCNF

dept_name → building, budget is non-trivial, and dept_name+ = {dept_name, building, budget}, not every attribute. That one dependency is behind all three anomalies.

instructor and department are

In instructor(id, name, salary, dept_name) the only left side is id, a key. In department(dept_name, building, budget) it is dept_name, its key.

In practice: check the dependencies in F. If each one's left side is a superkey of the table, the table is in BCNF.

Decomposing into BCNF

While some table Ri breaks BCNF on α → β: replace it with (α ∪ β) and (Ri − (β − α)). Do it in SQL, exercise 8

A split is lossless when the shared columns are a key of one side

Splitting R into R1 and R2 is lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2.

  • dept_name → (dept_name, building, budget): lossless.
  • building determines neither part: lossy, as on slide 6.
-- check it on the data: both counts 0
SELECT count(*) AS missing FROM (
  SELECT * FROM inst_dept
  EXCEPT
  SELECT id, name, salary, dept_name,
         building, budget
  FROM inst_part NATURAL JOIN dept_part) m;
-- and the same with EXCEPT the other way

Dependency preservation: can each rule be checked in one table?

  • After a split, a dependency is preserved if the dependencies that fit inside single tables still imply it.
  • A preserved dependency is enforced by a key or a UNIQUE constraint on one table: cheap, on every insert.
  • A lost one can only be checked by joining the tables, on every change: in practice, a trigger, or nothing.

takes_flat: everything preserved

id → name, dept_name lives in the student part, course_id → title, credits in the course part, and the grade's dependency in the enrollment part.

BCNF does not always manage this. The next slide is the classic case where it cannot.

When BCNF loses a rule: dept_advisor

Third normal form, and how to reach it

3NF

For every α → β in F+: it is trivial, or α is a superkey, or each attribute of β − α is part of some candidate key. The third case is the only difference from BCNF.

  1. Find a canonical cover Fc.
  2. Make one table α ∪ β for each α → β in Fc.
  3. If no table holds a candidate key of R, add one that does.
  4. Drop any table contained in another.

This 3NF synthesis is always lossless and always preserves every dependency. The price: a little repetition can remain, like an instructor's department in dept_advisor.

BCNF or 3NF?

Lossless joinAlwaysAlways
Every dependency checkable in one tableNot alwaysAlways
Repetition left overNone from dependenciesPossible, as in dept_advisor

Aim for BCNF. When BCNF would lose a rule you care about, choose 3NF for that table and say why. Milestone 2 asks for exactly that argument.

The normal forms nest

2NF is mostly history: 3NF implies it, so we skip it.

4NF handles independent lists in one table, like an instructor's children and phone numbers: every child is paired with every phone. Split them into two tables.

Repeating a fact on purpose

  • Denormalization stores a joined or computed result to make some read faster, accepting the copies.
  • Prefer a view when the join is cheap enough: nothing is copied.
  • A materialized view stores the result and is refreshed on demand: REFRESH MATERIALIZED VIEW.
  • Whatever repeats needs a plan to stay in step: a trigger, a refresh schedule, or a rule that the copy is read-only.

Normalize first, then measure

Denormalize only for a query you have measured as too slow, and write down which copy is the master. Weeks 10 to 12 show how to measure.

What to take away

  1. 1
    A repeated fact is a dependency on a non-key.

    It causes update, insert and delete anomalies.

  2. 2
    Dependencies are rules; data only tests them.

    GROUP BY the left side and count the right side.

  3. 3
    Closure is the working tool.

    It finds keys and tests whether a dependency holds.

  4. 4
    Split on a key of one side, and nothing is lost.

    BCNF decomposition always splits that way.

  5. 5
    Choose 3NF when BCNF would lose a rule.
