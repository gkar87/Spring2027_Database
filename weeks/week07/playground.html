How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.

1. What goes wrong in a wide table

Slide 4. Comp. Sci.'s building and budget appear once per Comp. Sci. instructor: three times.

Slide 5, the update anomaly. Change the building in one row only, and Comp. Sci. is now in two buildings at once. Which one is right? The table can't say.

The insert anomaly. A new Art department, with a building and budget but no instructors yet, has nowhere to go: every row needs an instructor id, the primary key.

The delete anomaly. Diego Torres is Music's only instructor. Delete that one row and Music's building and budget go with it.

2. Functional dependencies, tested in SQL

Slides 8 and 9. α → β holds when rows that agree on α always agree on β. Group by α and count the different values of β: any group with more than one breaks the dependency. No rows back means this data obeys dept_name → building.

The other direction fails: Hale houses two departments, so building → dept_name does not hold.

Data can disprove a dependency but never prove one. Here name → salary holds, only because no two instructors share a name today. It is not a rule: the next hire could be a second Avery Chen. Which dependencies are rules is a question for the people who use the data.

Closures, keys and normal forms

Slides 12 to 21. Choose a schema, or type your own dependencies, and press Compute. Try the textbook's R first and follow the closure of {A, G} one step at a time; then try dept_advisor and see which dependency a BCNF split loses.

3. Splitting a table, and joining it back

Slides 6 and 18. Split inst_dept on dept_name, the left side of dept_name → building, budget. DISTINCT keeps each department once. Joining the two parts gives back exactly the 11 rows: nothing is missing, and nothing extra appears.

Split on building instead, which is not a key of either part. The join pairs every Hale instructor with both Hale departments: Avery Chen comes back in Mathematics as well as Comp. Sci. The extra rows are wrong facts, so this split loses information even though it adds rows.

4. When BCNF loses a rule

Slide 21. Say a student may have one advisor in each department, and each instructor advises for one department: i_id → dept_name and s_id, dept_name → i_id. The BCNF split puts those in two tables, and then no key can stop Riley Adams getting two Comp. Sci. advisors. Both inserts are accepted; only a join shows the broken rule.

The 3NF design keeps one table, dept_advisor(s_id, i_id, dept_name), with primary key (s_id, dept_name). The second insert is then refused by the key, at the price of repeating each instructor's department.

5. More examples to try

More tests of dependencies and keys, on takes_flat, which repeats each student's and each course's facts on every enrollment.

A dependency fails if some group of rows agrees on the left side and disagrees on the right.

A set of columns is a superkey of this data if no two rows share its values.

Change one copy of a course's title and the table holds two titles for one course.

Split by the two dependencies; the join gives back exactly the original rows, so the split is lossless.

Does course_id → title hold in takes_flat? Show each course_id with how many times its title is stored (one per enrollment), most copies first. The bigger the number, the more copies an update must change.

Hint

One group per course, and count(*) counts its rows. Every row of a group holds a copy of the title.

Show a solution
SELECT course_id, count(*) AS copies
FROM takes_flat
GROUP BY course_id
ORDER BY copies DESC;

Split takes_flat on the course: course_part(course_id, title, credits), one row per course, and rest_part with every other column plus course_id. Join them back with NATURAL JOIN and show how many rows the join returns.

Hint

Two CREATE TABLE … AS SELECT, as in example 3.1. A lossless split gives back exactly as many rows as takes_flat has.

Show a solution
CREATE TABLE course_part AS
SELECT DISTINCT course_id, title, credits FROM takes_flat;

CREATE TABLE rest_part AS
SELECT id, name, dept_name, course_id, semester, year, grade
FROM takes_flat;

SELECT count(*) FROM rest_part NATURAL JOIN course_part;

A lossy split. Make ib(id, name, salary, building) and bd(building, dept_name, budget), one row per building and department, from inst_dept. Show how many rows their natural join returns. Compare it with the 11 rows of inst_dept.

Hint

Example 3.2 showed the Hale rows only; count them all.

Show a solution
CREATE TABLE ib AS SELECT id, name, salary, building FROM inst_dept;
CREATE TABLE bd AS SELECT DISTINCT building, dept_name, budget FROM inst_dept;

SELECT count(*) FROM ib NATURAL JOIN bd;

Which students' facts does takes_flat copy most? Show each student's name and how many rows repeat their name and dept_name, for students with more than one row.

Hint

Group by the student (id, and name so you can show it), and keep groups with count(*) > 1.

Show a solution
SELECT name, count(*) AS rows
FROM takes_flat
GROUP BY id, name
HAVING count(*) > 1;

Decompose takes_flat into BCNF with three tables (a student part, a course part and an enrollment part), join all three back, and show three numbers: the rows the join returns, rows of takes_flat missing from it, and rows in it that takes_flat lacks.

Hint

The keys are id, course_id, and (id, course_id, semester, year). Put the join in a view whose columns follow takes_flat's order, then use EXCEPT both ways as in example 3.1.

Show a solution
CREATE TABLE s_part AS SELECT DISTINCT id, name, dept_name FROM takes_flat;
CREATE TABLE c_part AS SELECT DISTINCT course_id, title, credits FROM takes_flat;
CREATE TABLE e_part AS SELECT id, course_id, semester, year, grade FROM takes_flat;

CREATE VIEW back AS
SELECT s.id, s.name, s.dept_name, c.course_id, c.title, c.credits,
       e.semester, e.year, e.grade
FROM e_part e
JOIN s_part s ON s.id = e.id
JOIN c_part c ON c.course_id = e.course_id;

SELECT (SELECT count(*) FROM back) AS rows,
       (SELECT count(*) FROM (SELECT * FROM takes_flat EXCEPT SELECT * FROM back) a) AS missing,
       (SELECT count(*) FROM (SELECT * FROM back EXCEPT SELECT * FROM takes_flat) b) AS extra;
