Lab 5: Normalizing a sign-in sheet

The campus tutoring center has kept one spreadsheet of every session since January. It has started to disagree with itself. In this lab you test the rules its data should follow, fix the rows that break them, and split the sheet into tables that store each fact once, without losing a single session.

The sign-in sheet and its rules

Each row of tutoring is one session: a student met a tutor on a day for some minutes. There are 24 rows.

The columns of tutoring
ColumnTypeMeaning
student_idchar(3)The student, like S01
student_name, student_emailvarchar(30), varchar(40)The student's name and email
tutor_idchar(2)The tutor, like T1
tutor_namevarchar(30)The tutor's name
subjectvarchar(20)What the tutor tutors
center, center_roomvarchar(20), varchar(20)Where that subject is tutored, and the room
session_datedateThe day of the session
minutesintegerHow long it lasted

The center's director confirmed these five rules. Your job is to check whether the data obeys them, and then to design tables in which it has to.

  • F1: student_id → student_name, student_email. A student has one name and one email.
  • F2: tutor_id → tutor_name, subject. A tutor has one name and tutors one subject.
  • F3: subject → center. Each subject is tutored in one center.
  • F4: center → center_room. Each center is in one room.
  • F5: student_id, tutor_id, session_date → minutes. A student meets a tutor at most once a day.

Part B: ten questions in SQL

The tutoring table is also in the playground's scratch pad. Try each statement there first, then copy it into lab5.sql under its comment. Write the results each question asks for in lab5_answers.txt. Show exactly the columns asked for, in the order asked, and name a column the way the question does.

  1. Q1. Show, in one row, the number of sessions as sessions, the number of different students as students, and the number of different tutors as tutors.

  2. Q2. Test the email part of F1: show each student_id that has more than one different email in the sheet, with the number of different emails as emails. Use GROUP BY and HAVING, as on slide 9.

  3. Q3. Test the name part of F2 the same way: each tutor_id with more than one different name, and the number as names.

  4. Q4. Q2 and Q3 each find one typo. Look at the rows involved (in the scratch pad, not in your file), decide which spelling is right, and fix each typo with one UPDATE that sets the right value on every row of that student or tutor. psql prints how many rows each UPDATE changed; write both numbers in the answers file.

  5. Q5. Now test all five rules in one query that returns five rows: fd (the text F1 to F5) and violations, the number of left-side values that break that rule. For F1 and F2, a value breaks the rule if either attribute on the right has more than one different value. Join the five counts with UNION ALL. After Q4, every count should be 0.

  6. Q6. Is the left side of F5 a key of the sheet? Show, in one row: the number of rows as rows, the number of different (student_id, tutor_id, session_date) values as key_values, and the number of different (student_id, session_date) values as student_date_values. Hint: count(DISTINCT (a, b)) counts different pairs.

  7. Q7. Decompose the sheet into BCNF. Create these five tables, with the names, columns and types given, a primary key on each, NOT NULL on every column that a rule says must have a value, and a foreign key wherever a column refers to another of these tables:

    • center(center, center_room), from F4.
    • subject_center(subject, center), from F3.
    • tutor(tutor_id, tutor_name, subject), from F2.
    • tutee(student_id, student_name, student_email), from F1. (The university already has a student table.)
    • tutor_session(student_id, tutor_id, session_date, minutes), from F5.

    Use the same types as tutoring. Create them in an order in which each foreign key refers to a table that already exists.

  8. Q8. Fill the five tables from tutoring with INSERT INTO … SELECT, one statement per table. Then show, in one query, each table's name as table_name and its number of rows as rows, in the order listed in Q7.

  9. Q9. Create a view rejoined that joins the five tables back together, with the same ten columns as tutoring, in the same order. Then show, in one row, the number of rows of tutoring missing from the view as missing, and the number of rows in the view that tutoring does not have as extra. Use EXCEPT both ways, as in playground example 3.1.

  10. Q10. Using only the new tables, not tutoring, show each center's center, center_room, the total minutes of its sessions as total_minutes, and the number of sessions as sessions, most minutes first.

§

Check yourself: Q1 shows 24 sessions. The two UPDATEs in Q4 change 3 rows and 5 rows. In Q8, tutor_session has 24 rows; if it has fewer, an INSERT used DISTINCT where it should not, and if Q8 fails with a duplicate key, Q4's fixes did not happen. In Q9, both numbers are 0. If Q9 fails with "each EXCEPT query must have the same number of columns", count the view's columns.

Part C: three short answers

Answer in lab5_answers.txt.

  1. W1. Give one update, one insert and one delete anomaly that the original tutoring table allows, each with a concrete example from its rows: a name, a center or a session. Q2 and Q3 have already shown you what one of them looks like in practice.

  2. W2. Compute these three closures under F1 to F5, showing which rule adds what at each step, as on slide 13. Say whether each set is a superkey of tutoring.

    • {tutor_id}+
    • {student_id, tutor_id}+
    • {student_id, tutor_id, session_date}+

  3. W3. Q6 shows that (student_id, session_date) is also unique in this data. Should it be the key of tutor_session instead? Say why or why not, and what you would ask the tutoring center before deciding. Two to four sentences.

Part D: CS 5200 only

CS 4600 students may skip this part. Put these at the end of lab5.sql, after Q10.

The director adds a sixth rule, in two parts: a student who is tutored in a subject always sees the same tutor for it, and, by F2, each tutor tutors one subject. That is student_id, subject → tutor_id together with tutor_id → subject: the same shape as dept_advisor on slide 21.

  1. Q11. Test the new rule on tutoring: show the number of (student_id, subject) values with more than one different tutor, as violations.

  2. Q12. Create a table advises(student_id, subject, tutor_id) that records each student's tutor for each subject, with types as in tutoring, foreign keys to tutee, subject_center and tutor, tutor_id NOT NULL, a primary key that enforces the new rule, and a UNIQUE constraint on (student_id, tutor_id). Fill it from tutoring with one INSERT … SELECT DISTINCT, and show its number of rows as rows. Then run this INSERT, which should be refused:

    INSERT INTO advises VALUES ('S01', 'Calculus', 'T4');

    In the answers file, give the count and the name of the constraint that refused the INSERT.

  3. D1. In the answers file: what are the candidate keys of advises? Is it in BCNF? Is it in 3NF? Would you keep it as one table or split it, and what would each choice cost? Three to five sentences.

If something goes wrong

  • "tutoring.sql: No such file or directory": lab5.sql and tutoring.sql are not in the same folder. Move them together and run again.
  • "relation … already exists": you ran part of the file on its own, outside the reload. Run the whole file; the reload drops every table the lab creates.
  • "relation "tutor" does not exist" in Q7: a foreign key refers to a table created further down. Create the tables in the order listed.
  • "duplicate key value violates unique constraint" in Q8: a table got two rows for one key. Either Q4 missed a typo, or the INSERT is missing DISTINCT.
  • "insert or update on table … violates foreign key constraint" in Q8: fill the tables in the same order you created them.
  • Q9 shows numbers other than 0: compare the view's column order with tutoring's, using \d tutoring and \d rejoined.
  • Anything else: copy the exact message and bring it to office hours, Tuesday and Wednesday 12:00–3:00 p.m., MIC room D159, or post it in the week 7 discussion in Brightspace.
