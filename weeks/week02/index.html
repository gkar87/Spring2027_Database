Relational Algebra: The Math Under SQL

A handful of operators, each taking relations in and giving one relation back. They give every SQL query an exact meaning, and they are what the optimizer rewrites when it decides how to run your query.

Dr. Gorkem Kar University of Central Missouri School of Computer Science and Cybersecurity

Today builds on line 4

If every result is a relation, we can name a small set of operations on relations and build every query from them. That set is the relational algebra.

Why an algebra? Relations in, one relation out

Closure

Every operator takes one or two relations and returns a relation. So the output of one operator can be the input of the next.

  • Exact meaning. Each SQL query means one algebra expression.
  • Procedural. An expression says which operations, in what order.
  • Rewritable. The optimizer swaps an expression for a cheaper equivalent one (slide 21).

σ, π, ∪, −, × and ρ are the six basic operators. The others can be written with them, but they are worth having.

One relation in, one relation out

Selection picks rows, projection picks columns, rename changes names. Together they already express every single-table query from last week.

Selection σ keeps the tuples that pass a test

σdept_name = 'Physics'(instructor)

What can go in a selection's condition

Comparisons

An attribute compared with a constant or another attribute of the same tuple: =, ≠, <, ≤, >, ≥.

Connectives

∧ (and), ∨ (or), ¬ (not).

σdept_name = 'Physics' ∧ salary > 90000(instructor)
σdept_name = building(department)   -- two attributes

The first gives Sam Okafor alone. The second compares two attributes of the same tuple; here it is empty.

A condition looks at one tuple

"Instructors who earn more than Maria Lopez" compares two tuples, so σ alone cannot say it. We need two relations side by side: the product, slide 15, and rename, slide 10.

§

NULL works as in week 1: a comparison with NULL is unknown, and σ keeps only tuples whose condition is true.

Projection π keeps attributes, and a set keeps each tuple once

πdept_name(instructor)

In the algebra

π removes duplicates. Always.

In SQL

SELECT dept_name FROM instructor returns all 10 rows. You need SELECT DISTINCT to get the algebra's answer.

Compose operators: the order can matter

Works

πname(σdept_name = 'Physics'(instructor))

Select the Physics tuples, then keep their names: Sam Okafor, Kofi Mensah.

Fails

σdept_name = 'Physics'(πname(instructor))

π has already thrown dept_name away, so σ has nothing to test. The playground stops with There is no attribute dept_name and lists the one attribute left, name.

When σ and π can swap

πL(σc(R)) = σc(πL(R)) only if every attribute that the condition c uses is in the list L.

→

Equivalences like this one are the optimizer's rules. Slide 21 shows one that saves real work.

Rename ρ gives a relation a second name

ρi2(instructor)
ρs(sid, sname, dept, cred)(student)

The first is the same relation, now called i2. The second also renames each attribute, in order.

Why you need it

To compare a relation with itself. Who earns more than Maria Lopez?

πinstructor.name(
  σinstructor.salary > i2.salary ∧ i2.name = 'Maria Lopez'(
    instructor × ρi2(instructor)))
Result

Avery Chen, Jordan Patel and Sam Okafor. Maria Lopez earns 87,000; Kofi Mensah also earns 87,000, so Kofi Mensah is not more.

Without ρ

instructor × instructor has two attributes called instructor.salary, and the condition could not say which is which.

Set operations need compatible relations

Union-compatible

Both relations have the same number of attributes, and the i-th attribute of each has a compatible domain.

Fine

πname(student) ∪ πname(instructor)

22 names: no student shares a name with an instructor.

Not compatible

πname(student) ∪ πname, id(instructor) -- 1 vs 2
πname(student) ∪ πtot_cred(student)     -- text vs int

PostgreSQL reports the second as UNION types character varying and integer cannot be matched.

§

Attribute names do not have to match; positions and types do. The result takes the left side's names.

The Cartesian product × pairs every tuple with every tuple

A join is a product followed by a selection

σstudent.dept_name = department.dept_name(student × department)

72 pairs in, 12 out: each student with their own department. This pattern is so common it has its own symbol.

Theta join

R ⋈θ S = σθ(R × S), for any condition θ.

Equijoin

A theta join whose condition uses only = .

Same idea, in SQL

SELECT *
FROM student JOIN department
  ON student.dept_name = department.dept_name;
→

A DBMS never builds the 72 pairs first. Week 11 shows the join algorithms that skip them. The meaning is still "product, then select".

Run it, playground examples 3.1 and 3.2

Natural join ⋈ matches every attribute the two relations share

student ⋈ department

Natural join matches on names, even names you did not mean

Who took which course?

πname, title(student ⋈ takes ⋈ course)

Returns 14 pairs. But takes has 22 enrollments.

student and course both have dept_name, so the join also demands that the course be in the student's own department. Drew Kim, a Physics major, took CS-101 and CS-315; both vanish.

Fix: project away the accidental match

πname, title(student ⋈ takes ⋈ πcourse_id, title(course))

Returns 21 pairs: every enrollment except Drew Kim's second attempt at CS-101, which repeats a (name, title) pair.

!

The same trap exists in SQL's NATURAL JOIN. Most style guides prefer JOIN … ON or USING, which name the join attributes.

Division ÷ answers "for all" questions

R(A, B) ÷ S(B)

The A-values that appear in R with every B-value of S.

Here R = πid, course_id(takes) and S = πcourse_id(σdept_name = 'Comp. Sci.'(course)).

With the six basic operators:

πA(R) − πA((πA(R) × S) − R)

"All A's, minus those missing some B."

Same answer, different work

Many expressions mean the same relation. The optimizer's job is to find a cheap one.

Push selections down: filter before you combine

The rule: σc(R × S) = R × σc(S) when c uses only attributes of S. On 12 students it saves 60 tuples; on 30,000 students it saves millions.

From SQL to algebra, clause by clause

SELECT DISTINCT s.name, c.title      -- π
FROM   student s                     -- ρ
JOIN   takes t  ON s.id = t.id       -- ⋈θ
JOIN   course c ON t.course_id = c.course_id
WHERE  s.dept_name = 'Physics';     -- σ

πname, title(σdept_name = 'Physics'(student ⋈ takes ⋈ πcourse_id, title(course)))

What to take away

  1. 1
    Every operator returns a relation.

    So expressions nest, and a query is a tree of operators.

  2. 2
    σ picks tuples, π picks attributes, ρ renames.

    π removes duplicates; SQL needs DISTINCT for that.

  3. 3
    ∪ ∩ − need union-compatible inputs.

    Same number of attributes, compatible types, position by position.

  4. 4
    A join is a product followed by a selection.

    Natural join matches every shared name, wanted or not.

  5. 5
    Equivalent expressions can cost very different amounts.

    Pushing σ down is the optimizer's first trick.
