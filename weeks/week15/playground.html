1. Documents in a column

Slides 5 to 8. This week's database has a table review with 3,000 course reviews. Each one is a single jsonb value, a document: a JSON object that PostgreSQL stores in a parsed, binary form, so it can look inside it quickly. A review site might collect data this way, because different forms ask different questions and the questions change every term.

The four documents don't have the same keys. Review 4 has tags, a workload and a comment; review 2 has none of them. No ALTER TABLE was needed for any of it: the table's schema says only "a document", and each document carries its own structure. That is what schema on read means. The program that reads a review must cope with whatever keys it finds.

Two arrows take a document apart. -> returns a piece that is still JSON; ->> returns it as text. #>> follows a path. A key that is missing gives NULL, not an error.

In the result, as_json keeps the quotes of a JSON string and as_text doesn't. Compare a JSON value with JSON, as @> does in section 2, and a text value with text.

Once a value is text, a cast turns it into a number, and the rest of SQL works as usual: here, the average rating of each course.

Since nothing fixes the keys, it is worth asking which keys the documents actually have. jsonb_object_keys returns one row per key, so a join with it turns each document into several rows.

Four keys are in every document; the other five come and go. In a relational table those five would be columns full of NULLs, or tables of their own.

2. Looking inside documents

Slides 9 and 10. @> asks whether a document contains another: every key and value on the right must be in the document on the left. For an array, every element on the right must be somewhere in the array on the left.

? asks whether a key exists. About one review in ten names a teaching assistant:

An array inside a document can be opened into rows with jsonb_array_elements_text, one row per element, and then grouped like any column.

A JSON path is a small query language of its own, from the SQL standard. @? asks whether the path finds anything; jsonb_path_query returns what it finds. In the path, $ is the whole document and @ is the item being tested.

3. Indexing documents

Slide 11. Without an index, every one of these questions reads all 3,000 documents. A B+-tree (week 10) indexes one value per row, so it can't help with "contains this anywhere". A GIN index, a generalized inverted index, works like the index at the back of a book: for every key and value that occurs, it lists the rows that hold it.

The first plan uses the index: four rows, read from four pages, instead of 2,996 rows thrown away. The second question asks the same thing in other words, yet the plan goes back to a sequential scan. A GIN index on doc serves the operators @>, ? and @?, not an equality on an extracted value. For that you need an index on the expression itself, a B+-tree like week 10's:

The jsonb_path_ops kind of GIN index is smaller and faster for @> and @?, but can't answer ?. Whichever you choose, every index costs space and slows every write, as in week 10.

4. Embed or reference

Slides 12 and 13. A document database asks a design question that normalization (week 7) never did: should related data sit inside the document, or in a document of its own, referenced by its key? PostgreSQL can build documents from the university tables, so you can try both. jsonb_build_object makes an object; jsonb_agg gathers rows into an array.

A student's page shows the student and the whole transcript. As one document, that page is one read by one key, with no joins:

If the title changes, every one of those documents must change too: the update anomaly of week 7, back again. Embedding pays off when the data is read together, belongs to one parent and stays small, like a transcript. Reference instead, by key, when the data is shared, large, or changes on its own, like a course's title.

5. A key-value store

Slide 14. The simplest store of all keeps a value under a key and offers three operations: get, put and delete. The database does not look inside the value. Table kv plays one here: login sessions, preferences, a counter and a feature flag, each under a key whose prefix says what it is.

Put means "insert, or replace if the key is there". In SQL that is INSERT … ON CONFLICT … DO UPDATE, an upsert. It runs as one statement, so two people logging in at once can't both read 318 and both write 319, the lost update of week 13.

The first counter existed and went up to 319; the second didn't exist, so it started at 1. A true key-value store, such as Redis or DynamoDB, answers gets and puts very fast and spreads keys over many machines easily. The price shows when you ask a question that isn't "give me this key": which sessions belong to S0042? With only get and put, the answer is to read every value.

PostgreSQL can answer it, because it can look inside values. A pure key-value store can't, so a program that needs this keeps a second key, such as sessions-of:S0042, and must update both every time.

6. Sharding by hash

Slides 16 and 17. When one machine can't hold the data, or can't keep up with the writes, the rows are split among machines, called shards. A common rule hashes a shard key and takes the remainder: with three shards, a row goes to shard hash(key) mod 3. PostgreSQL's hash partitioning uses the same rule to split one table into parts on one machine, so you can watch it work.

The hash spreads the rows about evenly, and all of one student's reviews land in the same shard. (tableoid::regclass names the part each row is stored in.) The shard key decides which questions are cheap. Ask by student, and the planner reads one shard; ask by course, and it must ask all three and combine the answers:

Skipping the other parts is called partition pruning. On a cluster the second plan's Append would be a message to every machine, and a wait for the slowest. Extensions such as Citus spread PostgreSQL's partitions over several servers in just this way, and MongoDB and Cassandra shard by a hashed key too.

7. Replicas and quorums

Slides 18 to 21. Each shard is usually kept on several machines, called replicas, so that losing one machine loses no data. Keeping the copies the same costs time. A system like Dynamo or Cassandra lets you choose, for each request, how many replicas must answer: W for a write and R for a read, out of N copies. If R + W > N, every read asks at least one replica the latest write reached.

With W = 1 and R = 1, writes and reads are as fast as one machine, but a read can return the old version. Try W = 2 and R = 2, or W = 3 and R = 1: the read is never stale. The price is waiting for more machines, and a request fails if too few of them can be reached.

That price is the CAP trade-off. When the network splits the replicas into groups that can't reach each other (a partition), a system must choose: refuse some requests until the network heals, keeping the replicas consistent, or answer from whatever replicas it can reach, staying available but possibly stale. Many NoSQL systems choose availability and promise eventual consistency: once the writes stop, the replicas come to agree. PostgreSQL's own replication sends the WAL of week 14 to standby servers; with synchronous_commit set to wait for a standby, a commit waits for a second machine.

How many reviews of CS-347 carry the tag labs? One column, the count. Use containment.

Hint

Example 2.1, with one tag in the array and count(*) in the select list.

Show a solution
SELECT count(*) FROM review
WHERE doc @> '{"course_id": "CS-347", "tags": ["labs"]}';

114. A review tagged both labs and exams still contains ["labs"]: containment asks only that every element on the right be there.

For each teaching assistant named in a review, show three columns: the TA's name, the number of reviews that name them, and how many of those say the TA was helpful. Give the three columns different names. Order by name.

Hint

Keep the documents that have a ta key, group by doc #>> '{ta,name}', and count the helpful ones with count(*) FILTER (WHERE …). helpful is a JSON boolean, so cast its text with ::boolean.

Show a solution
SELECT doc #>> '{ta,name}' AS ta,
       count(*) AS reviews,
       count(*) FILTER (WHERE (doc #>> '{ta,helpful}')::boolean) AS helpful
FROM review
WHERE doc ? 'ta'
GROUP BY 1
ORDER BY 1;

Emery 98 and 71, Jules 101 and 75, Rowan 102 and 72. doc @> '{"ta": {"helpful": true}}' inside the FILTER works as well.

Which tags do CS-347's reviews carry? Two columns, the tag and the number of CS-347 reviews that carry it, most common first, ties broken by tag.

Hint

Example 2.3, keeping only the reviews whose course_id is CS-347.

Show a solution
SELECT t AS tag, count(*) AS reviews
FROM review, jsonb_array_elements_text(doc -> 'tags') AS t
WHERE doc ->> 'course_id' = 'CS-347'
GROUP BY t
ORDER BY reviews DESC, tag;

All six tags, between about 110 and 125 each. Reviews with no tags key give no rows at all: jsonb_array_elements_text of NULL is empty, so the join drops them.

How many reviews report a workload of more than 10 hours a week and at least 2 exams? One column, the count.

Hint

Either cast two extracted values, (doc -> 'workload' ->> 'hours')::int > 10 and the same for exams, or write one JSON path, as in Example 2.4, joining the two tests with &&.

Show a solution
SELECT count(*) FROM review
WHERE doc @? '$.workload ? (@.hours > 10 && @.exams >= 2)';

The same count comes from WHERE (doc -> 'workload' ->> 'hours')::int > 10 AND (doc -> 'workload' ->> 'exams')::int >= 2. Only the path version can use a GIN index.

Create a GIN index named review_doc_path on review that serves @> and @? but not ?. Then run exactly this check:

SELECT indexdef FROM pg_indexes WHERE indexname = 'review_doc_path';
Hint

Example 3.3 creates it. The operator class goes after the column: (doc jsonb_path_ops).

Show a solution
CREATE INDEX review_doc_path ON review USING gin (doc jsonb_path_ops);
SELECT indexdef FROM pg_indexes WHERE indexname = 'review_doc_path';

It indexes a hash of each path from the top of the document to a value, not each key on its own, so it can find a whole "ta": {"helpful": true} but can't tell whether a key exists. Add EXPLAIN to Exercise 4's query, in the same box, to see it used.

Build one document per department that offers a course, of the form {"dept": "Physics", "courses": ["PHY-101"]}, with the course ids in order. One column, the document, ordered by department name.

Hint

Group course by dept_name. In each group, jsonb_agg(course_id ORDER BY course_id) makes the array, and jsonb_build_object puts it beside the name.

Show a solution
SELECT jsonb_build_object('dept', dept_name,
                          'courses', jsonb_agg(course_id ORDER BY course_id)) AS doc
FROM course
GROUP BY dept_name
ORDER BY dept_name;

These documents hold only the ids, so a course's title is kept in one place: referencing, not embedding. In the output, "dept" comes before "courses" whichever order you wrote them in: jsonb keeps keys sorted, shorter keys first.

Count two more logins on April 27 and one on April 29, using the upsert from Example 5.2. Then show every key that starts with counter: and its value, ordered by key.

Hint

The same upsert three times: twice with the April 27 key and once with 'counter:logins:2027-04-29'. Leave out the RETURNING clauses, so the last result is the one checked.

Show a solution
INSERT INTO kv VALUES ('counter:logins:2027-04-27', '1')
ON CONFLICT (key) DO UPDATE SET value = to_jsonb(kv.value::int + 1);
INSERT INTO kv VALUES ('counter:logins:2027-04-27', '1')
ON CONFLICT (key) DO UPDATE SET value = to_jsonb(kv.value::int + 1);
INSERT INTO kv VALUES ('counter:logins:2027-04-29', '1')
ON CONFLICT (key) DO UPDATE SET value = to_jsonb(kv.value::int + 1);
SELECT key, value FROM kv WHERE key LIKE 'counter:%' ORDER BY key;

April 27 at 320 and April 29 at 1. The same statement both creates a key and increments it, so the program never has to ask first whether the key exists.

Split the reviews into four shards by student, as in Example 6.1: a table rs with columns id, student and doc, and parts named rs0 to rs3 for remainders 0 to 3. Load every review, then show each part's name and number of rows, ordered by name.

Hint

Example 6.1 with MODULUS 4, four PARTITION OF tables, and the same INSERT … SELECT. Group by tableoid::regclass.

Show a solution
CREATE TABLE rs (id int, student text, doc jsonb) PARTITION BY HASH (student);
CREATE TABLE rs0 PARTITION OF rs FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE rs1 PARTITION OF rs FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE rs2 PARTITION OF rs FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE rs3 PARTITION OF rs FOR VALUES WITH (MODULUS 4, REMAINDER 3);
INSERT INTO rs SELECT id, doc ->> 'student', doc FROM review;
SELECT tableoid::regclass AS part, count(*) AS reviews
FROM rs GROUP BY 1 ORDER BY 1;

739, 679, 760 and 822. Going from three shards to four moved most students to a different shard: with hash mod n, changing n moves most keys. Systems that add machines often, such as Dynamo and Cassandra, use consistent hashing instead, which moves only about a quarter of them.
