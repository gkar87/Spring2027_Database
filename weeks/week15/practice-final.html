Part A: the relational model, SQL and design (25 points)

  1. A1 (6 points). For every department, show its name, the number of courses it offers and the total credits of those courses. Include departments that offer no course, with 0 for both.

    Answer
    SELECT d.dept_name, count(c.course_id) AS courses,
       coalesce(sum(c.credits), 0) AS credits
FROM department d
LEFT JOIN course c ON c.dept_name = d.dept_name
GROUP BY d.dept_name;

    Seven rows; Comp. Sci. has 5 courses and 17 credits, Economics 0 and 0. Counting c.course_id rather than * gives Economics 0, and coalesce turns its NULL sum into 0. Marking: 2 for the LEFT JOIN, 2 for the two aggregates, 2 for the zeros.

  2. A2 (5 points). In relational algebra: the names of the instructors who have never taught a course.

    Answer

    πname(instructor ⋈ (πid(instructor) − πid(teaches))). The difference finds the ids; the join brings back the names. Three instructors: Kofi Mensah, Noor Haddad and Tomas Novak. Subtracting names instead of ids is wrong: two instructors could share a name.

  3. A3 (8 points). Booking(guest_id, guest_name, check_in, room_no, room_type, rate) has the dependencies { guest_id → guest_name, guest_id check_in → room_no, room_no → room_type, room_type → rate }.
    (a, 2 points) Give the candidate key. (b, 2 points) Is Booking in 3NF? Name a dependency that decides it. (c, 4 points) Decompose it into 3NF.

    Answer

    (a) {guest_id, check_in}: its closure adds guest_name, room_no, room_type and rate, and neither attribute alone reaches the other.

    (b) No. room_type → rate has a left side that is not a superkey and a right side that is not prime; guest_id → guest_name and room_no → room_type break it too.

    (c) (guest_id, guest_name), (guest_id, check_in, room_no), (room_no, room_type), (room_type, rate). Lossless, every dependency kept, each table in BCNF.

  4. A4 (6 points). An E-R diagram has entity sets team (team_id, name), coach (coach_id, name) and player (player_id, name). head_coach is one-to-one between team and coach, total on team. plays_for is many-to-many between player and team, with an attribute season. A player may play for the same team in several seasons. Map the diagram to tables, with primary and foreign keys.

    Answer
    • team(team_id, name, coach_id NOT NULL UNIQUE), coach_id references coach
    • coach(coach_id, name)
    • player(player_id, name)
    • plays_for(player_id, team_id, season), each id a foreign key to its table

    NOT NULL makes head_coach total on team; UNIQUE makes it one-to-one. season is in the key because the same player and team can appear in several seasons. Marking: 2 for the coach column with both constraints, 3 for plays_for and its key, 1 for the rest.

Part B: programs and databases (8 points)

  1. B1 (5 points). A Python program moves 5,000 of an instructor's salary into their department's budget:

    cur.execute("UPDATE instructor SET salary = salary - 5000 WHERE id = %s", (iid,))
cur.execute("UPDATE department SET budget = budget + 5000 WHERE dept_name = %s", (dept,))
conn.commit()

    (a, 2 points) The second statement fails. With psycopg's default settings, is the first change saved? (b, 2 points) Rewrite the code so that both changes are saved or neither is, and the program says which. (c, 1 point) Why can the first statement fail on this database even with a valid id?

    Answer

    (a) No. psycopg starts a transaction at the first statement and nothing is saved until commit; the error aborts the transaction, and the program never reaches commit. But the connection is now in a failed transaction, so every later statement fails until the program rolls back.

    try:
    with conn.transaction():
        cur.execute("UPDATE instructor SET salary = salary - 5000 WHERE id = %s", (iid,))
        cur.execute("UPDATE department SET budget = budget + 5000 WHERE dept_name = %s", (dept,))
    print("moved")
except psycopg.Error as e:
    print("not moved:", e.sqlstate)

    (c) The CHECK constraint: salary must stay above 29,000. An explicit commit after both statements and rollback in the except clause also earns full credit.

  2. B2 (3 points). A page of a web application lists big_takes 50 rows at a time with ORDER BY reg_id LIMIT 50 OFFSET 40000. Why does it get slower the further the user pages, and what query keeps every page fast?

    Answer

    OFFSET still produces and throws away the 40,000 rows before the page. Remember the last reg_id shown and ask for the next ones instead: WHERE reg_id > 40000 ORDER BY reg_id LIMIT 50, which starts in the primary key's index exactly where the last page ended.

Part C: storage and indexes (12 points)

  1. C1 (4 points). A table has 2 million rows and a B+-tree index on its key with about 100 entries per page. (a, 2 points) How many levels does the tree have? (b, 1 point) How many pages does finding one row by key read? (c, 1 point) How many levels would it need with 400 entries per page?

    Answer

    (a) Four: 1003 = 1 million is too few, 1004 = 100 million is enough. (b) Five: one per level plus the row's page. (c) Three: 4002 = 160,000 is too few, 4003 = 64 million is enough.

  2. C2 (4 points). instructor has a B-tree index on (dept_name, salary). For each WHERE clause, can the index find the rows? Say why.
    (i) WHERE dept_name = 'Physics'
    (ii) WHERE salary > 90000
    (iii) WHERE dept_name = 'Physics' AND salary > 90000
    (iv) WHERE lower(dept_name) = 'physics'

    Answer

    (i) Yes: the leading column. (ii) No: salary is sorted only within each department, so high salaries are spread through the index. (iii) Yes, best of all: equality on the first column, then a range in the second, one contiguous stretch. (iv) No: the index holds dept_name, not lower(dept_name); an index on the expression would.

  3. C3 (4 points). (a, 2 points) A query keeps 40% of a table's rows, and there is an index on the condition's column. Why may a sequential scan still be faster? (b, 2 points) What does the buffer pool do, and why does it make the second run of a query faster?

    Answer

    (a) Rows that match are on almost every page, so the index would visit nearly every page anyway, in random order and with the index's own pages on top; a sequential scan reads each page once, in order. (b) It keeps recently used pages in memory; the second run finds them there and reads few or none from disk.

Part D: query processing (12 points)

  1. D1 (6 points). r has 5,000 rows on 100 pages; s has 50,000 rows on 1,000 pages. They are joined on an equality condition. Give the cost in pages of: (a, 2 points) block nested loop, r outer; (b, 2 points) indexed nested loop, r outer, with c = 3; (c, 1 point) hash join, the hash table on r fitting in memory. (d, 1 point) Both inputs arrive already sorted on the join column. What is the cost of a merge join?

    Answer

    (a) 100 × 1,000 + 100 = 100,100. (b) 100 + 5,000 × 3 = 15,100. (c) 100 + 1,000 = 1,100. (d) 100 + 1,000 = 1,100, and its output is sorted too.

  2. D2 (6 points). With an index on big_takes (student_no), PostgreSQL printed this plan:

    SELECT t.course_id, t.grade
FROM big_student s JOIN big_takes t ON t.student_no = s.student_no
WHERE s.student_no = 77;

Nested Loop
  ->  Index Only Scan using big_student_pkey on big_student s
        Index Cond: (student_no = 77)
  ->  Bitmap Heap Scan on big_takes t
        Recheck Cond: (student_no = 77)
        ->  Bitmap Index Scan on big_takes_student_no_idx
              Index Cond: (student_no = 77)

    (a, 2 points) Why a nested loop and not a hash join? (b, 2 points) What does the bitmap scan do differently from a plain index scan, and why does it help here? (c, 2 points) Why can big_student be read with an index-only scan?

    Answer

    (a) One outer row: the inner side runs once, through the index, and touches a dozen pages. A hash join would read all of big_takes to build or probe its table. (b) It first collects the addresses of all matching rows from the index, then reads each table page once, in page order, instead of jumping back and forth row by row. Student 77's 10 enrollments are on 10 different pages. (c) The query needs only student_no from big_student, and that column is in the primary key's index.

Part E: query optimization (10 points)

big_takes has 100,000 rows; year runs from 2001 to 2027; the common-values list gives CS-101 a frequency of 0.21428 and a NULL grade a frequency of 0.03704.

  1. E1 (5 points). Estimate the rows each condition keeps, showing the selectivity: (a, 1 point) grade IS NULL; (b, 2 points) year >= 2020, assuming the years are spread evenly; (c, 2 points) course_id = 'CS-101' AND year >= 2020, and the assumption you used.

    Answer

    (a) 0.03704 × 100,000 = 3,704. (b) The rows not below 2020: 1 − (2020 − 2001) / (2027 − 2001) = 7/26 ≈ 0.27, so about 27,000. (c) 0.21428 × 7/26 × 100,000 ≈ 5,800, assuming the course and the year are independent. The real counts are 29,630 and 6,351: recent years are a little busier than the even spread assumes.

  2. E2 (5 points). (a, 2 points) Estimate the rows of big_student ⋈ department on dept_name, and say why. (b, 3 points) A query joins big_takes, big_student and department and keeps only departments in one building. Which join would you do first, and why?

    Answer

    (a) 10,000: dept_name is the key of department and a foreign key in big_student, so each student matches exactly one department. (b) Select the building's departments first, then join them with big_student, then with big_takes: each step keeps the intermediate result as small as possible. Joining big_takes and big_student first builds 100,000 rows only to throw most of them away.

Part F: transactions and concurrency (15 points)

  1. F1 (6 points). Schedule S: r1(X), r2(Y), w1(X), r2(X), w2(Y), r1(Z), w1(Z), c1, c2.
    (a, 3 points) List the conflicting pairs and draw the precedence graph. (b, 2 points) Is S conflict serializable? If so, give the equivalent serial order. (c, 1 point) Is S recoverable?

    Answer

    (a) Only X is used by both: w1(X) before r2(X) gives T1 → T2. (r1(X) before r2(X) is two reads, no conflict.) The graph is the one edge T1 → T2. (b) Yes, no cycle: T1 then T2. (c) Yes: T2 reads X from T1, and T1 commits first.

  2. F2 (5 points). At READ COMMITTED, session A runs SELECT count(*) FROM takes WHERE course_id = 'CS-101'; twice in one transaction. Between the two, session B inserts a CS-101 enrollment and commits. (a, 2 points) What does A see, and what is the anomaly called? (b, 3 points) What changes if A runs at REPEATABLE READ in PostgreSQL, and why?

    Answer

    (a) The second count is one higher: a phantom, a row that appears between two reads with the same condition. (b) Both counts are the same. At REPEATABLE READ, PostgreSQL takes one snapshot at the transaction's first statement and every statement reads from it, so B's later commit is invisible to A.

  3. F3 (4 points). T1 locks A, T2 locks B, then T1 asks for B and T2 asks for A, all exclusive. (a, 2 points) Draw the wait-for graph and say what has happened. (b, 2 points) What does PostgreSQL do about it, and what should the program do?

    Answer

    (a) T1 → T2 (T1 waits for T2's lock on B) and T2 → T1: a cycle, a deadlock. (b) After a short wait it checks for a cycle and aborts one of the two with a deadlock error; the other goes on. The program rolls back and retries the aborted transaction. Taking locks in the same order everywhere prevents it.

Part G: recovery (10 points)

The system crashes right after record 10. Before the crash, every change before the checkpoint had reached disk.

 1  <T1 start>
 2  <T1, X, 10, 20>
 3  <T2 start>
 4  <T2, Y, 5, 15>
 5  <T1 commit>
 6  <checkpoint {T2}>
 7  <T3 start>
 8  <T3, Z, 7, 9>
 9  <T2, X, 20, 25>
10  <T3 commit>

  1. Ga (4 points). Run the redo pass. What are X, Y and Z at its end, and what is the undo list?

    Answer

    Redo starts at the checkpoint with the undo list {T2}. Record 7 adds T3; record 8 sets Z = 9; record 9 sets X = 25; record 10 removes T3. Y = 15 was already on disk. End: X = 25, Y = 15, Z = 9, undo list {T2}.

  2. Gb (6 points). Run the undo pass. List the log records it writes, in order, and give the final values.

    Answer

    <T2, X, 20> (X = 20), then <T2, Y, 5> (Y = 5), then <T2 abort> at record 3. Final: X = 20, Y = 5, Z = 9. X goes back to T1's committed 20, not to 10; T3 committed, so Z stays 9.

Part H: NoSQL and distributed data (8 points)

  1. H1 (4 points). An item has N = 3 replicas. (a, 2 points) Does R = 1, W = 3 guarantee that every read sees the latest write? What does it cost? (b, 2 points) With R = 2 and W = 2, how many replicas can be down while reads and writes both still succeed?

    Answer

    (a) Yes, 1 + 3 > 3; reads are fast, but a write fails if any one replica is down. (b) One.

  2. H2 (4 points). As in Lab 9, event(id, doc) stores events as jsonb with a numeric capacity. (a, 2 points) Write a query for the titles of the events with capacity over 100. (b, 2 points) Would a GIN index on doc make it fast? If not, what index would?

    Answer
    SELECT doc->>'title'
FROM event
WHERE (doc->>'capacity')::int > 100;

CREATE INDEX ON event (((doc->>'capacity')::int));

    (b) No: a GIN index on doc answers containment (@>) and key questions, not ranges. A B-tree on the expression does, if the query uses the same expression.

CS 5200: the extra question

On the final, CS 5200 students answer one more question, worth 10 points. Their score is out of 110 and scaled to 100.

  1. G1 (10 points). (a, 6 points) PostgreSQL's REPEATABLE READ is snapshot isolation. Explain why readers never wait for writers under it, and describe write skew, with an example in which two transactions each keep a rule and together break it. (b, 4 points) During a network partition, what must a replicated store choose between, and what does each choice look like to a user?

    Answer

    (a) Each transaction reads from a snapshot of committed versions taken when it starts, and a write creates a new version instead of overwriting, so a reader just reads the older version. Write skew: the rule is that at least one doctor is on call. Alice and Bob are both on call; each transaction checks that the other is on call and takes itself off. Neither writes what the other read, so snapshot isolation lets both commit, and no one is on call. SERIALIZABLE detects this and aborts one.

    (b) Consistency or availability. Choosing consistency, the side that cannot reach a quorum refuses requests (an error or a wait). Choosing availability, both sides answer, so a user may read stale data and conflicting writes must be merged later.
