Semi-structured data

  • Schema on read: the database stores whatever shape it is given; the program that reads it must cope with missing keys.
  • JSON is the common format today; XML came before it (textbook 8.1).

Documents in PostgreSQL: jsonb

CREATE TABLE review (
  id  integer PRIMARY KEY,
  doc jsonb NOT NULL
);

SELECT doc ->> 'course_id' AS course,
       avg((doc ->> 'rating')::int)
FROM review
WHERE doc @> '{"tags": ["labs"]}'
GROUP BY 1;
  • jsonb stores parsed JSON: keys sorted, duplicates dropped, quick to search.
  • -> gives JSON, ->> gives text, #>> follows a path.
  • @>: does the document contain this? ?: does the key exist?
  • Mix freely with ordinary columns, joins and transactions.

Playground sections 1 and 2

Looking inside: arrays and paths

-- one row per tag
SELECT t, count(*)
FROM review,
     jsonb_array_elements_text(doc -> 'tags') AS t
GROUP BY t;

-- a JSON path: heavy workloads
SELECT count(*) FROM review
WHERE doc @? '$.workload ? (@.hours > 10)';
  • A set-returning function in FROM turns an array into rows, so GROUP BY works on its elements.
  • SQL/JSON paths come from the SQL standard: $ is the document, @ the item being tested.
  • jsonb_build_object and jsonb_agg go the other way, from rows to documents.

Playground examples 4.1 to 4.3

Key-value stores

-- get
SELECT value FROM kv
WHERE key = 'session:8f3a';

-- put: insert, or update if present
INSERT INTO kv
VALUES ('counter:logins:2027-04-27', '1')
ON CONFLICT (key) DO UPDATE
  SET value = to_jsonb(kv.value::int + 1);

-- delete
DELETE FROM kv WHERE key = 'session:91bc';
  • Three operations: get, put, delete, always by key.
  • Every request names its key, so keys spread over many machines easily (next section).
  • A question about values ("whose sessions?") means reading everything, or keeping a second key by hand.

Playground examples 5.1 to 5.3

Data on many machines

Split it, copy it, and keep the copies honest.

Up or out?

Scale up

  • A bigger server: more cores, memory, faster disks.
  • Nothing in the database changes.
  • Takes most applications a long way, then gets very expensive, and is still one machine that can fail.

Scale out

  • Many ordinary servers, each with part of the work.
  • Partition (shard) the data to share the load.
  • Replicate each part to survive failures and serve more reads.
→

Partitioning answers "too much data or too many writes". Replication answers "too many reads" and "a machine died". Real systems do both.

Sharding by hash

Playground examples 6.1 and 6.2

Choosing a shard key

  • Spread evenly. Many distinct values, none much more common than the rest. A hot key, such as one celebrity's posts, overloads its shard (skew).
  • Keep queries local. Shard by what most queries name: reviews by student, if most pages show one student.
  • Keep transactions local. A transaction across shards needs two-phase commit.
  • Hash spreads well but scatters ranges; range keeps neighbours together but can pile new keys on one shard.
  • With hash mod n, adding a machine moves most keys. Consistent hashing moves only about 1/n of them.

Replicas and quorums

Playground section 7: try W and R yourself

CAP and eventual consistency

When the network partitions the replicas into groups that can't reach each other, each request must either wait or risk being stale.

Stay consistent

  • Refuse or delay requests on the minority side until the network heals.
  • Every read sees the latest write.
  • Banking, inventory, registration.

Stay available

  • Every replica keeps answering.
  • Eventual consistency: once writes stop, the replicas agree. Conflicts must be merged later.
  • Shopping carts, likes, feeds.

A transaction across shards: two-phase commit

  • A shard that voted ready must wait for the decision, holding its locks, even if the coordinator crashes: 2PC blocks.

Takeaways

  1. 1
    Documents fit data that is read whole and changes shape.

    The schema moves into the program that reads them.

  2. 2
    PostgreSQL does documents too.

    jsonb, its operators and a GIN index, beside your tables and inside your transactions.

  3. 3
    Embed what is read together; reference what is shared.

    Every copy is an update anomaly waiting to happen.

  4. 4
    Shard to share the load, replicate to survive.

    The shard key decides which queries stay on one machine.

  5. 5
    Copies cost consistency or waiting.

    Quorums with R + W > N, or eventual consistency; two-phase commit for transactions across shards.
