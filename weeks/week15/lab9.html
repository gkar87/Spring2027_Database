Lab 9: A document store of campus events

The campus events app kept every event as one JSON document: its host, its room, its tags and everyone who said they're coming. It was quick to build. Now the app is slow, some events are overbooked, and a few documents don't look right. You find out what the documents hold, make the slow lookups fast, and decide whether the data should have been tables all along.

Files for this lab

On Windows, add -U postgres after psql. In Colab, start the line with !. Any database works, but the university database is the one you have. You need PostgreSQL 14 or newer, as in Lab 0.

What a document looks like

Event 2, laid out with jsonb_pretty, its list of 12 RSVPs shortened. It has no tags:

{
    "host": {"dept": "Comp. Sci.", "name": "Robotics club"},
    "kind": "club",
    "room": {"room": 310, "building": "Hale"},
    "rsvps": [
        {"status": "going", "student": "S0176"},
        {"status": "maybe", "student": "S0277"},
        …
    ],
    "title": "Robotics club: Weekly meeting",
    "starts": "2027-04-15T12:30",
    "capacity": 60
}
  • kind is one of talk, club, sports, career, concert and workshop. host always has a name; a department's groups also have a dept.
  • An event has a room, an online platform such as {"platform": "Zoom"}, or both.
  • tags, when present, is an array of strings. rsvps is an array, possibly empty, of objects with a student and a status, going or maybe.
  • starts is text in the form YYYY-MM-DDTHH:MI, so comparing two of them as text puts them in time order.

Look at a few yourself before writing anything: SELECT jsonb_pretty(doc) FROM event WHERE id IN (1, 2, 3);

Part A: querying documents, Q1 to Q8

Write each statement in lab9.sql under its comment, run the whole file, and copy the numbers the answers file asks for.

  1. Q1. How many events of each kind? Two columns, kind and events, most first, ties by kind.

  2. Q2. Events hosted by a Comp. Sci. group and tagged free food that start on or after April 26, 2027: id, title and start, in order of start, ties by id. Use one @> for both the department and the tag.

  3. Q3. How many events are in person only, online only, and hybrid? Use the ? operator on room and online.

  4. Q4. Every tag and the number of events that carry it, most common first, ties by tag.

  5. Q5. The five events with the most going RSVPs: id, title and the number going, ties by id. jsonb_array_elements turns the RSVP array into rows.

  6. Q6. An event is overbooked when more students are going than its capacity. First, how many events are overbooked? Then the five most overbooked: id, kind, capacity and going, ordered by how far over they are, ties by id.

  7. Q7. Some documents are not quite right. Find those with no title, or whose capacity is not a JSON number (jsonb_typeof tells you). Show the id and, in words, what is wrong, ordered by id.

  8. Q8. With one JSON path and the @? operator, count the events that start in April 2027 and have a capacity over 100. JSON paths have a starts with test for strings and && for "and".

Part B: indexes, Q9 to Q11

Every EXPLAIN in this lab uses the same options, so your output and the grader's can be compared:

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT …;

A step's buffers are its shared hit plus its read, and they include the steps indented under it, so the top step's count is the whole query's. Leave out the Buffers: line under Planning:.

  1. Q9. The events student S0042 is going to: id and title, ordered by id. Write the condition with @>, matching an element of rsvps that has both the student and the status. EXPLAIN it; create a GIN index on doc named event_doc, using jsonb_path_ops; EXPLAIN it again; then run it.

  2. Q10. The events on April 27, 2027, with doc ->> 'starts' from '2027-04-27' up to but not including '2027-04-28': id and title. EXPLAIN it, create the index that helps, named event_starts, and EXPLAIN it again. In the answers file, say why event_doc can't help this query.

  3. Q11. The size of the table event and of each of its three indexes, largest first. pg_relation_size and pg_size_pretty, as in week 10.

Part C: back to tables, Q12 to Q14

  1. Q12. Create three tables and load them from the documents with INSERT … SELECT:

    • ev: one row per event, with id, title, kind, host (the host's name), starts as a timestamp and capacity as an integer.
    • ev_tag: one row per event and tag.
    • ev_rsvp: one row per event and student, with the status.

    Give each table a primary key, the two smaller ones foreign keys to ev, and ev_rsvp a CHECK on its status. jsonb_to_recordset (playground Example 4.3) or jsonb_array_elements turns an array into rows. Q7's documents will get in your way: decide what to do about them, and say why in the answers file.

  2. Q13. Check the load with one query that returns one row of six counts: events, tags and RSVPs as counted in the documents, each beside the number of rows in your tables.

  3. Q14. Q5 again, on your tables. It must give the same five rows.

Part D: three short answers

In lab9_answers.txt, in your own words, a few sentences each. Slides 10 and 14 to 17 cover the ideas.

  1. W1. The app shows each event with its RSVPs, and each student's page lists the events they are going to. Should RSVPs stay embedded in the event documents, or be documents of their own that reference the event? Use what Q9 and Part C showed you.

  2. W2. The events are to be split over four machines. Would you shard by event id, by host or by start date? Name one query from this lab that would go to a single shard under your choice, and one that would go to all four.

  3. W3. Each event's RSVPs are kept on three replicas, and saying "going" must never overbook an event. Which R and W would you choose for the RSVP list, and what happens to RSVPs when one replica is down? When two are?

If something goes wrong

  • "lab9_events.sql: No such file or directory": the three files are not in the same folder. Move them together and run again.
  • "operator does not exist: jsonb @? unknown" or a syntax error at @?: your PostgreSQL is older than this lab needs. Check with SELECT version(); and use the Lab 0 installation.
  • "invalid input syntax for type integer": something you cast with ::int is not a number. Cast the text from ->>, not the JSON from ->.
  • A key violation while loading ev_rsvp or ev_tag: check which columns your primary key names; each student RSVPs to an event at most once, and each tag appears once per event.
  • "relation "event_doc" already exists": you ran Q9 on its own after a full run. Run the whole file; the reload removes the index.
  • Your buffer counts differ from a classmate's by a few: different versions and machines. Use your own numbers.
  • Anything else: copy the exact message and bring it to office hours, Tuesday and Wednesday 12:00–3:00 p.m., MIC room D159, or email it to me.
