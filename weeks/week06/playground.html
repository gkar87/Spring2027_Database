Week 6 design studio: from E-R diagrams to tables

Each part of an E-R diagram becomes a table, a column or a key. Here you build each one on PostgreSQL inside this page, see which changes the tables accept and which they refuse, and then map a small library design in eight checked exercises.

How to use this page

  • Each grey box is an editor. Press Run, or Ctrl+Enter (Cmd+Enter on a Mac). A box may hold several statements; each result is shown.
  • The examples start with BEGIN; and end with ROLLBACK;, so the tables they create are gone afterwards. A box runs as one unit: if any statement in it fails, none of its changes are kept.
  • table_info('name') lists a table's columns, whether each may be NULL, and the keys it belongs to. It is this page's version of \d name in psql, and the exercises end with it.
  • Reset database, at the top, puts the university and the library back as they started, and drops the library tables the exercises create.
  • Exercises have a Check answer button. It runs your statements inside a transaction and rolls them back, so checking never changes the data. Your solved exercises are remembered in this browser only.

1. Entity sets and their attributes

Slide 21. A composite attribute, name, becomes one column per part. A derived attribute, age, is not stored: a query computes it from date_of_birth, so it is never out of date. The table is called staff here because instructor already exists.

A multivalued attribute, phone_number, gets a table of its own: one row per number, keyed on the owner's key and the value together. Avery Chen has two numbers, Sam Okafor one, everyone else none, and no column is ever left empty.

2. Relationships become keys

Slides 11, 12 and 22. Try each combination of rules, and look for one where a change is accepted although the diagram forbids it. That is a rule the tables cannot enforce.

Many-to-many and many-to-one, side by side. takes is many-to-many, so its key holds both sides (and the semester and year). advisor is many-to-one from student, so its key is the student's id alone: a second row for the same student is refused.

Total participation on the many side: every librarian works at exactly one branch, so branch_id is a NOT NULL foreign key in librarian. This insert leaves it out, and PostgreSQL refuses it.

One-to-one: each department has at most one head, and an instructor heads at most one department. The foreign key i_id is also UNIQUE. Run it, then change Physics' head to '10101' and run it again: UNIQUE refuses Avery Chen as head of two departments.

3. A weak entity set

Slides 15 and 23. A section is identified by its course plus a discriminator: sec_id, semester and year. The course's key is part of the section's primary key, and ON DELETE CASCADE removes the sections when their course goes. CS-400 is a course made up for this example.

4. Specialization

Slide 24, the first mapping: a table for each set, sharing the key. Cy Diaz is both a student and an employee (a teaching assistant), which this mapping handles with one row in each subgroup table. The tables are called p_student and p_employee so they don't collide with the university's.

The third mapping: one table with a type column. No joins, but a student's salary and an employee's tot_cred are NULL by design, and a CHECK has to say which kinds exist. Overlap needs a kind of its own, here 'both'.

Studio exercises: map the library

Slides 27 to 29 revised the library's first draft. Here you turn the revised design into tables, one piece at a time. Each box starts with the line that is checked: table_info for the table you build. Write your statements above it, then press Check answer (or Ctrl+Shift+Enter). Types are not checked, but column names, NOT NULL and keys are, so use the names in the prompt. Don't write BEGIN or ROLLBACK: Check does that for you. Exercises 1 to 7 are for everyone; exercise 8 is a stretch.

A patron may have any number of phone numbers. Create patron_phone(patron_id, phone) so that each patron lists each number once, and a patron's numbers are deleted with the patron.

Hint

Example 1.2, with patron in place of instructor. The primary key is both columns.

Show a solution
CREATE TABLE patron_phone (
  patron_id char(5) REFERENCES patron ON DELETE CASCADE,
  phone     varchar(15),
  PRIMARY KEY (patron_id, phone)
);

SELECT column_name, nulls, keys FROM table_info('patron_phone');

Age is derived from birth_date, so it is not stored. Create a view patron_age with each patron's name and age in whole years, then select those two columns from it. Isla Murphy has no birth date, so her age is NULL.

Hint

The SELECT in example 1.1 computes an age. Put a query like it in CREATE VIEW patron_age AS … (week 5, example 4.1).

Show a solution
CREATE VIEW patron_age AS
SELECT name, date_part('year', age(birth_date)) AS age
FROM patron;

SELECT name, age FROM patron_age;

An author writes many books and a book can have several authors. Create writes(isbn, author_id), with each column referring to its table, so that an author is listed once per book.

Hint

Like takes in example 2.1: both keys, and the primary key is both together.

Show a solution
CREATE TABLE writes (
  isbn      varchar(17) REFERENCES book,
  author_id char(4) REFERENCES author,
  PRIMARY KEY (isbn, author_id)
);

SELECT column_name, nulls, keys FROM table_info('writes');

A patron may choose one home branch; many patrons share a branch, and choosing one is optional. Add a column home_branch to patron that refers to branch.

Hint

ALTER TABLE … ADD COLUMN (week 5, example 2.3). Partial participation means NULL is allowed: a patron with no home branch.

Show a solution
ALTER TABLE patron
  ADD COLUMN home_branch varchar(4) REFERENCES branch;

SELECT column_name, nulls, keys FROM table_info('patron');

A branch may have one manager, a librarian, and a librarian manages at most one branch. Add a column manager_id to branch that refers to librarian. Not every branch has a manager yet.

Hint

Example 2.3 puts the one-to-one in a table of its own; here it is a column. What stops one librarian from managing two branches?

Show a solution
ALTER TABLE branch
  ADD COLUMN manager_id char(4) UNIQUE REFERENCES librarian;

SELECT column_name, nulls, keys FROM table_info('branch');

The library lends copies, and a copy is identified by its book and a copy number. Create copy(isbn, copy_no, condition), where a book's copies are deleted with the book. Condition is optional.

Hint

Example 3.1: the owner's key plus the discriminator form the primary key.

Show a solution
CREATE TABLE copy (
  isbn      varchar(17) REFERENCES book ON DELETE CASCADE,
  copy_no   integer,
  condition varchar(10),
  PRIMARY KEY (isbn, copy_no)
);

SELECT column_name, nulls, keys FROM table_info('copy');

Some patrons are students, and a student patron has a school, which is required. Map the subgroup the first way from slide 24: create student_patron(patron_id, school), removed with the patron.

Hint

Example 4.1's p_student: the subgroup table's key is the parent's key, and it is also a foreign key.

Show a solution
CREATE TABLE student_patron (
  patron_id char(5) PRIMARY KEY REFERENCES patron ON DELETE CASCADE,
  school    varchar(40) NOT NULL
);

SELECT column_name, nulls, keys FROM table_info('student_patron');

A copy is out to at most one patron at a time; every loan has a patron, a loan date and a due date. Create loan(isbn, copy_no, patron_id, loan_date, due_date) for current loans. The box starts with exercise 6's copy, which loan refers to.

Hint

Loan is many-to-one from copy to patron, so its key is the copy's key alone: both columns. A key of two columns is referred to with a table-level FOREIGN KEY (isbn, copy_no) REFERENCES copy.

Show a solution
CREATE TABLE loan (
  isbn      varchar(17),
  copy_no   integer,
  patron_id char(5) NOT NULL REFERENCES patron,
  loan_date date NOT NULL DEFAULT current_date,
  due_date  date NOT NULL,
  PRIMARY KEY (isbn, copy_no),
  FOREIGN KEY (isbn, copy_no) REFERENCES copy
);

SELECT column_name, nulls, keys FROM table_info('loan');
